# 組織台帳の経済センサス較正(Wave 4 IV-1)

**問い**: シミュレーションの舞台に置いた ~1.1 万の組織は、**現実の渋谷駅前と同じ産業構成をしているのか**。

**答え(実測)**: していない。現行台帳は **IT を 26% 過小・ビルメン/人材派遣系サービスを 60% 過小・
小売を 86% 過大**に持っており、**娯楽業(ライブハウス・クラブ・カラオケ)は 1 社も存在しない**。
本バッチは令和3年経済センサスの町丁目別表から駅周辺 13 町丁目の実測値を取り出し、
台帳をその構成へ組み直せる経路(`build_orgs.py --census`)を作った。

- 実測器: `scripts/calibrate_orgs_census.py`
- 集計成果: `data/realworld/census_r3/station_area_industry.json` / `sim_vs_census.json`(gitignore)
- 生成器: `scripts/build_orgs.py --census`(**無指定なら従来と 1 バイトも変わらない**)
- テスト: `tests/test_census_calibration.py`(29 件)

---

## 1. 何が問題だったか

現行の `data/organizations_shibuya_wide11k.json` は `build_orgs.py --dist` が
`INDUSTRY_SPEC` の `share` から生成している。その `share` の出所は台帳 meta の "honesty" 欄どおり
**東京商工会議所渋谷支部が引く事業所統計(平成18・総数 30,572)** で、次の 3 点が舞台と食い違う。

| 食い違い | 現行 | 舞台 |
|---|---|---|
| (a) 調査年 | 平成18(2006) | 令和3(2021)。この15年でIT集積が進んだ |
| (b) 空間 | 渋谷区**全域**(33,284 事業所 / 581,127 人) | 渋谷駅**前**(9,872 事業所 / 222,848 人) |
| (c) 従業者 | 規模帯サンプルの**副産物**(近似) | 産業別の実測値がある |

(b) が特に効く。区全域には笹塚・幡ヶ谷・本町といった住宅地の商店街が含まれ、
小売と生活関連サービスの比重が上がる。駅前だけを切ると情報通信と事業サービスが跳ね上がる。

## 2. 面(エリア)の定義

町丁目は行政界なので「駅から半径 N m」とは一致しない。ここでは**駅至近側に寄せた 13 町丁目**の
単純和をエリア値とする(`calibrate_orgs_census.STATION_AREA`)。

> 渋谷1〜4丁目 / 道玄坂1〜2丁目 / 宇田川町 / 神南1〜2丁目 / 桜丘町 / 南平台町 / 円山町 / 神泉町

合計 = **9,872 事業所 / 222,848 人**(平均 22.57 人/事業所)。

境界の町丁目(松濤・神山町・鶯谷町・恵比寿西・神宮前6丁目 等)は**入れていない**。
この線引きは恣意的なので、集計 JSON の `_meta.area_definition.blocks` に町丁目名をそのまま
列挙してあり、後から引き直せる。

**二重計上の防止**: 丁目を持つ町(渋谷・道玄坂・神南)は原表に「町の行」と「丁目の行」が
両方あり、前者は後者の和である。集計は**末端行だけ**を足す(`leaf_blocks`)。

政府統計の利用は**政府標準利用規約(第2.0版)= CC BY 4.0 互換・商用可**。出典表記が必須で、
加工した場合はその旨も書く(集計 JSON の `_meta.attribution` / `_meta.modified_note`)。

★ **生 xlsx の取得 URL は記録が残っていない**(本バッチ着手時点で既にローカルにあった)。
捏造しないため `_meta.source_url` は `null` のままにし、代わりに検証可能な事実
(ファイル名・sha256・シート名 `ka21ta28113` / `ka21ta30113`・シート先頭の表題文字列)を残した。
再取得は e-Stat の「経済センサス-活動調査」から同じ表番号を辿ること。

**限界(集計 JSON の `_meta.caveats` と同文)**

- 「事業所」は経営主体の拠点であって建物ではない。1 棟のビルに数十事業所が入る。
- 「従業者数」は**その事業所で働く人**(昼間の就業者)で、夜間人口(居住者)とは別物。
  在宅勤務・出張・派遣先常駐の実態は反映されない(調査時点の名簿ベース)。
- 秘匿(x)・皆無(-)は `null` として数え、**0 で埋めない**(欠測セル 22,654 件)。
- 町丁目不詳の事業所があるため、町丁目の合計は区総数と一致しない(原表の注記どおり)。
- 令和3年調査は **COVID 下(2021-06-01 時点)**。飲食・宿泊は平常年より低い可能性がある。

**検算(自動)**: ①大分類の和 = 総数 ②第28表の大分類 = 第30表の大分類小計。
どちらも `True`(集計 JSON の `checks`)。この 2 本が通るので、パーサが列をずらして
読んでいないことは機械で担保されている。

## 6. 較正のやり方(`--census`)

```
python scripts/calibrate_orgs_census.py                              # ① 実測 → 集計 JSON
python scripts/build_orgs.py --census --count 9872 --night-shifts    # ② 台帳を組む
```

### 6.1 何を実測に合わせ、何を合わせないか

**合わせるもの(実測 2 列だけ)**

1. 産業別**事業所数** → 社数の割付(最大剰余法・`_quota`)
2. 産業別**従業者数** → 従業者質量の割付(最大剰余法)+ 産業内は既存の裾長サンプルの
   **相対形を保存**したまま総和だけ合わせる(`_rescale_to_quota`。各社 1 人以上)

`--count` を実測の 9,872 にすれば、社数も従業者総和も**実測と完全一致**する
(丸め残差 1 人 = 222,849 vs 222,848)。

**合わせないもの(正直な限界)**

- **規模帯(SIZE_BANDS)の分布**。町丁目別表は「産業 × 規模帯」のクロスを持たないので、
  産業内の規模分布(裾の形)は依然として全国構造からの近似である。
  較正後は**規模帯が駆動側ではなく従業者数からの派生ラベル**になる(`_band_of`)。
  これが唯一の意味変更で、台帳 meta の `honesty` にも同文を書いてある。
- **社ごとの従業者数の実表**。再現を主張しない(そもそも公表されていない)。
- **建物への割付**。従来どおり「大組織 → 高prestige/高層ビル優先」の決定論。

### 6.2 既定は 1 バイトも動かない

`--census` を渡さない生成結果は、コミット済み `organizations_shibuya_wide11k.json` の
`companies` / `schools` と**完全一致**する(`test_no_census_flag_is_byte_identical_to_committed_ledger`)。
`--night-shifts` と同じ線引き。具体的には:

- `AM` は `INDUSTRY_SPEC` **本体には足さない**(`CENSUS_EXTRA_INDUSTRY_SPEC` に分離)。
  足すと既定の産業シェアの正規化が動いてしまう。
- `LS` の職場カテゴリ差し替えは `CENSUS_SPEC_OVERRIDE` 経由で、既定モードは**同一オブジェクト**を返す。
- `SHIFT_BY_CAT["nightlife"]` は**追加キー**、`AM` の夜勤枠は別表 `CENSUS_NIGHT_SHIFT_BY_KEY`。
  既定モードでは `AM` の社が 0 件なので誰も引かない。
- `place_on_buildings(..., cat_by_key=None)` の既定は従来の `IND_BY_KEY[key]["cat"]`。
- 出力先も分けてある(`data/organizations_shibuya_census.json`)ので、正準 11k 台帳を
  事故で上書きしない。

## 7. 接客(serve)の穴 — nightlife 職場が存在しなかった問題

監査の指摘: `work.service.serve_by_cat` は客の消費カテゴリ **{food, cafe, nightlife, shop}** を
張っているのに、台帳の職場カテゴリは **{office, shop, food, service}** しか無かった。つまり

> **ナイトライフ消費は、どれだけ発生しても接客スタッフが構造的に存在しない**
> (`serve{unstaffed:true}` = agent_id -1 の記録にしかならない)

`--census` はこの穴を**データ側から**閉じる。中分類 80「娯楽業」= 254 事業所 / 4,980 人が
実在するので、これを `cat="nightlife"` の職場として生やす。較正後の台帳の職場カテゴリ内訳:

| 職場カテゴリ | 社数 |
|---|---:|
| office | 3,971 |
| shop | 2,055 |
| service | 1,972 |
| food | 1,620 |
| **nightlife** | **254** |

**nightlife 職場 = 254 社**(従業者 4,984 人)。`shift_pattern` は `18:00-02:00`
(`close < open` = 日跨ぎ)で、`world.night_economy` が ON なら既存の夜勤語彙で読める。
`--night-shifts` を併用すると `CENSUS_NIGHT_SHIFT_BY_KEY["AM"]`(22:00-05:00・share 0.40)が付く
(既定の夜勤表 `NIGHT_SHIFT_BY_KEY` は「INDUSTRY_SPEC のキーだけで閉じている」という
別レーンの不変条件があるので、センサス専用の枠は別表に分けてある)。

同時に **LS(生活関連サービス業)を `shop` → `service`** へ移した。美容室・エステ・
リラクゼーションは「物を売る店」ではなく役務提供で、`services.py` の受給側 POI カテゴリ
(service/education)と揃う = 需要(`service_use`)と供給(`serve`)が同じ接点で対になる。

### 7.1 残る seam(本バッチでは触っていない)

`work.serve_by_cat` は依然として **`service` カテゴリの消費を接客対象に含めていない**
(`{food, cafe, nightlife, shop}` のまま)。`services.py` の受給は `spend_cat="service"` で出るので、

```yaml
work:
  service:
    serve_by_cat:
      service: 役務の提供      # ← この 1 行を足すと service 職場 1,972 社に serve が帰属する
```

を足せば供給側が対になる。**本バッチは conf を触っていない**(所有レーン外・既定挙動を動かさないため)。
ledger 側の受け皿(`service` 1,972 社 / `nightlife` 254 社)は先に用意した、という分担。

## 9. 職業 → 賃金カテゴリの追記(同バッチ)

街頭・都市オペレーション・交通の新職業 13 種を `economy.WAGE_CAT` / `MONEY_INIT` へ追記した。
賃金カテゴリは**雇用形態の粗い代理**であって職種の格付けではない。判定基準は 1 つだけ:

> 固定職場を持ち雇われている = 店員/会社員 / 固定職場を持たず出来高 = 自営 / 賃金労働でない = None

| 職業 | WAGE_CAT | 日給 | MONEY_INIT | 根拠 |
|---|---|---:|---|---|
| ティッシュ配り | 店員 | 9,000 | 10,000-40,000 | 販促代理店に時給で雇われる街頭スタッフ(固定拠点なしだが被用者) |
| ストリートミュージシャン | 自営 | 10,000 | 5,000-30,000 | 投げ銭=出来高。既存「バンドマン」と同じ |
| キッチンカー営業者 | 自営 | 10,000 | 30,000-120,000 | 移動販売の個人事業主。仕入れ・釣銭の運転資金を持ち歩く |
| 路上占い師 | 自営 | 10,000 | 10,000-50,000 | 面談ごとの出来高。固定拠点なし |
| 募金スタッフ | 店員 | 9,000 | 10,000-40,000 | 街頭募金の多くは有給スタッフ(時給)。寄付金は本人の所得ではない |
| 路上支援員 | 会社員 | 12,000 | 30,000-100,000 | NPO・社会福祉法人・区委託のアウトリーチ常勤職員(固定給) |
| **街頭演説者** | **None** | 0 | 20,000-80,000 | 選挙運動は賃金労働ではない(公選法の運動員買収禁止)。政治活動に賃金を与えない |
| **路上生活者** | **None** | 0 | **0-3,000** | 定職なし。持ち金レンジだけで表現し、賃金経路には載せない |
| 清掃作業員 | 区職員 | 13,000 | 50,000-150,000 | 区の清掃事業(一般廃棄物)= 公費の現業職 |
| 救急隊員 | 消防士 | 14,000 | 50,000-150,000 | 救急隊員は消防吏員(東京消防庁)= 公安職の給与水準 |
| 納品ドライバー | 会社員 | 12,000 | 30,000-100,000 | 運輸・物流会社の被用者(ギグの「配達員」= 自営 とは別物) |
| 夜間清掃員 | 店員 | 9,000 | 15,000-50,000 | ビルメンテナンス会社の深夜現業(時給ベース) |
| 車掌 | 会社員 | 12,000 | 40,000-120,000 | 鉄道事業者の正社員。既存 L5 の「駅員/運転士」と同じ雇われ方 |

**なぜ公務員 2 種を `CIVIL_SERVANTS` に入れなかったか**: `CIVIL_SERVANTS` 経路は government の
日次ペイロール(予算 + 源泉徴収)を前提にしており、勤務地写像 `persona._pick_workplace`
(別バッチ所有)へ職業を載せないと成立しない。清掃作業員・救急隊員は city_ops が L5 の役割として
職場ごと与える層なので、通常の「勤務完遂 → 日給」経路の方が二重支給の危険がない。
給与水準だけを公務員のもの(区職員 / 消防士)から借りている。
**この 2 集合が交わらないことはテストが機械で固定**している。

`路上生活者` は `MONEY_INIT` の下限を 0 にした**唯一の職業**(所持金がほぼ無い状態の表現)。
これも「0 が他へ漏れていないこと」をテストで固定した。

**不活性の担保**: 13 種はいずれも既定ランの名簿に 1 人も居ないので、辞書への追記は
ゴールデン L1 に触れない(`tests/test_scenario.py` ほか 80 件緑で確認)。

## 10. テスト(`tests/test_census_calibration.py` = 29 件)

| 群 | 内容 |
|---|---|
| パーサ(合成 xlsx) | 表題行を見出しと誤認しない / ルビ連結 / 結合セル / 3 階層 / 皆無セル `-` は null / 注記行を捨てる / 見出し不在は ValueError |
