## 1. 何を測るか(§3 の 4 群 → L2 の 14 列)

`observer.regression.enabled: true` で L2 に生える。既定 OFF では**列が 1 つも生えない**。
すべて **rolling 窓**(既定 144 step = 1 シミュ日)の集計で、窓の定義は 1 つだけ。

| 群 | §3 の言葉 | 列 | 型 | 退行の向き |
|---|---|---|---|---|
| ① | 行動分散の単調**減少** | `reg_act_between_var` | float | ↓ |
| | | `reg_act_entropy_mean` | float | ↓ |
| | (分母) | `reg_act_agents` | int | — |
| ② | 訪問地点エントロピーの**低下** | `reg_visit_entropy` | float(bit) | ↓ |
| | (分母) | `reg_visit_nodes` | int | — |
| ③ | 語彙エントロピー**低下** | `reg_vocab_entropy` | float(bit) | ↓ |
| | n-gram 重複率**上昇** | `reg_ngram_repeat_rate` | float | ↑ |
| | (分母) | `reg_vocab_tokens` | int | — |
| | (除外量) | `reg_vocab_excluded` | int | — |
| ④ | 発火率の **0 への張り付き** | `reg_fire_zero_frac` | float | ↑ |
| | 発火率の **飽和への張り付き** | `reg_fire_sat_frac` | float | ↑ |
| | (分位) | `reg_fire_rate_p10/p50/p90` | float | — |

- ④ の 5 列は **`cognition.fire` が ON のときだけ**生える(材料の `cog_fire` が出ないため。
  0 を並べて「張り付いている」と誤読させるより列ごと消すほうが正直)。
- 「どちらへ動いたら退行か」の表は `regression.REGRESSION_DIRECTION` が**単一の源**で、
  判定スクリプトは方向を 1 行も持たない(列を足して方向を書き忘れる経路が無い)。

### 1.1 定義の要点

- **`window_steps` / `fire_sat_per_step` は Δt 変換表に登録済み**
  (`timeconv.TABLE`: 窓は STEPS = 実時間を保つ / 飽和閾値は RATE = 1 日あたりの総量を保つ)。
  Δt=10(正準)では恒等なので既存ランと 1 バイトも変わらない。
- **`reg_act_between_var`** … 個体ごとに `ACT_KINDS`(26 種の固定ホワイトリスト)上の確率
  ベクトル p_i を作り、**次元ごとの個体間分散を次元平均**する。分散は**不偏(n−1)**。
  → iid 標本なら期待値が N に依存しない(§4 の診断の前提)。
  `ACT_KINDS` に `move_segment` / `route_start` を入れないのは、1 回の移動が step 数ぶん
  増殖して分布を潰すため。次元集合を凍結するのはランをまたいで分散を比較するため。
- **母集団は「窓内に L1 イベントを出した個体」**。`sim.agents` を読まない
  (= 観測がシムを変える経路が構造上存在しない)代償で、睡眠中で無イベントの個体は
  分母から落ちる。この定義は **L1 だけから完全に再計算できる**(独立検算が可能)。
- **語彙は文字 2-gram**。形態素解析を使わないのは `scripts/analyze_specialization.py` と
  同じ判断(外部辞書に依存せず決定論であることを優先)。したがって「語」ではなく
  「文字の並び」を数えている。

### 1.2 ★第87 の申し送り: 定型応答は語彙系から除外する

第87バッチ実装記録 §5.4 の申し送り:

> 定型応答は**単一の固定文**なので、ON のランでは同じ文が発話分布に現れる。
> プロンプトの指紋ではない(世界に見える痕跡)が、**語彙エントロピー・n-gram 重複率を
> 読むときは機構由来の定数として除外が要る**(第91 の退行シグナル監視への申し送り)。

対応: `observer.regression.exclude_template: true`(既定)で `cognition.engaged.TEMPLATE`
と完全一致する発話を語彙タリーから外し、**外した件数を `reg_vocab_excluded` 列と
`summary.regression.excluded_total` に必ず残す**(黙って落とさない)。

除外しないと何が起きるか: engaged ON のランだけ、機構が撃った定型応答の本数に比例して
語彙エントロピーが下がり n-gram 重複率が上がる = **機構が退行シグナルを捏造する**。
検収では `summary.regression.excluded_total == summary.engaged.template_replies` を固定
(mini 縦煙で 46 = 46 / 6 日縦煙で 325 = 325)。

**限界**: 除外できるのは engaged の `TEMPLATE` 1 種だけである。他の機構が固定文を
世界へ出すようになったら、同じ汚染が同じ形で起きる(そのときは同じ枠へ足す)。

## 2. 各シグナルの根拠(なぜこの 4 群なのか)

### 2.1 ① 行動分散 — 分散崩壊(最重要)

- **原文書 §1**: 「LLM エージェントには**分散崩壊**の問題がある。応答の変動性が
  **人間の 20 分の 1 から 300 分の 1** という報告があり、マクロパターンは再現しても
  **個体の多様性が失われる**。パラメータの大きな単一モデルはこの問題を解決せず、
  RLHF 済みの大型モデルはむしろ均質化・過剰協調に寄る。」
- **接続 = [llm-social-sim-survey.md](llm-social-sim-survey.md) S-03**
  「平均は合うが分散が痩せる」:
  サーベイ §8.1 は LLM が「**average personality**」を示しシミュ集団の**行動的異質性を
  制限する**と指摘し、§7 は緩和策として「**異質性の意図的な組み込み**」を挙げる。
  同文書は S-03 を **未実装(既知の穴)** と自己申告し、§4.1 で
  「**分散・裾の現実比が未測定。研究課題が「裾」である以上、これが最も痛い**」と書いている。
  本バッチの ① 群はその穴の**ラン内監視**側を埋めるものである
  (現実比の照合 = `calibrate_report.py` 側は依然として未実装)。
- **設計上の含意**: 分散崩壊への対抗策として原文書 §5 は `llm.fleet`(異種モデル混成)を
  「性能の都合ではなく**多様性の実装**として」正当化している(第88 で実装済み)。
  ① 群はその対抗策が効いているかを測る計器でもある。

### 2.2 ② 訪問地点エントロピー

- 本リポの実査(`scripts/diagnose_stationarity.py` の docstring)で、反復の実体は
  **EPR(訪問回数に比例した優先的回帰・`routine.py`)+ 決定論日次予定**と判明している。
  優先的回帰は現実の人流の性質でもあるので**それ自体は正しい**が、
  探索項(`drive.boredom` の未訪問 POI 探索)が枯れると単調に縮む。
  ② はその縮みを直接見る。
- `diagnose_stationarity.py` が事後に測る「訪問先分布の日次エントロピー」と**同じ量**を、
  ラン中の rolling 窓で出しているのが本列である(事後 = 判定、ラン中 = 監視)。

### 2.3 ③ 語彙エントロピー + n-gram 重複率

- **第70バッチ(observer/echo.py)の前提**: 「同じ語が繰り返し出た」が伝播なのか
  **LLM の反復癖**なのか。エコー 5 列は「話者ごとの反復」を見るが、
  ③ は**街全体の語彙プール**が痩せていないかを見る(別の階層)。
- **既知の失敗様式**: CAMEL(Li+ 2023, NeurIPS)の
  "infinite loop of messages … repeatedly thanking each other or saying goodbye"
  (丁寧さの無限ループ)。"Too Polite to Disagree"(SIGDIAL 2026)は追従がターンとともに
  **増幅**することを示す(第87バッチ §5.2 で既に引用済み)。会話ループは
  n-gram 重複率の上昇として最も早く出る。
- 対抗策は現状 `prompts.variety_hint`(決まり文句で始めない注意書き)1 つしかない。
  ③ はその 1 つが効いているかの唯一の計器である。

### 2.4 ④ 発火率の 0 / 飽和への張り付き

- **原文書 §8**: 「最大のリスクは **θ_in の較正**であり、**低すぎれば予算崩壊、
  高すぎれば誰も考えない世界になる**。」
- 平均発火率では両端が打ち消し合う(半分が 0、半分が飽和でも平均は真ん中)ので、
  **分位と両端の張り付き率**で見る。`reg_fire_zero_frac` が上がるのは「誰も考えない世界」、
  `reg_fire_sat_frac` が上がるのは「予算崩壊」。
- 第87 の実測は「エピソード数は §8 の目標帯(4〜8/人/日)に入るが**滞在時間は超過**」で
  あった。④ は滞在ではなく**発火の頻度分布**を見るので、両者は補い合う。

## 3. 判定式(`scripts/detect_regression.py`)

    python scripts/detect_regression.py runs/smoke_tall --alpha 0.05 --min-rel-slope 0.02

**閾値は引数必須**。事前登録(U-10)・`analyze_specialization.py` と同じ流儀で、
コードに既定値を埋め込まない。

### 3.1 検定

**Mann-Kendall 傾向検定**(同順位補正つき正規近似)+ **Theil-Sen 勾配**。
ノンパラメトリックで外れ値・非正規性に強い。

### 3.2 ★自己相関の扱い(この装置で最も間違えやすい点)

L2 の監視列は rolling 窓(144 step)なので、**隣接行は窓の 99% 以上を共有する**。
この系列をそのまま Mann-Kendall にかけると有効標本数が桁で過大になり、
**どんな微小な傾きでも p<0.001 になる**。したがって:

- 既定で **窓幅ぶん間引く**(`--stride 0` = ランの `window_steps` を自動採用 = 非重複標本)。
- 既定で **先頭 1 窓を捨てる**(`--warmup -1`)。ラン冒頭は窓が満ちておらず、
  「窓が満ちていく過程」が単調**増加**として検定に載る = 退行の逆向きの偽陽性になる。
- 結果として、判定には最低でも **`warmup + 4 × stride` = 720 step(5 シミュ日)** のランが要る。
  それ未満は `INSUFFICIENT` を返す(黙って判定しない)。

### 3.3 判定は 3 条件の連言

1. `p < --alpha`
2. 傾きの符号が `REGRESSION_DIRECTION` と一致する
3. `|相対傾き| ≥ --min-rel-slope`(相対傾き = Theil-Sen 勾配 ÷ 系列平均の絶対値
   = 「1 シミュ日あたり平均の何割ぶん動いたか」= 単位に依らない効果量)

n が大きいと微小な傾きでも p は容易に小さくなるので、**効果量との連言**にしてある
(`diagnose_stationarity.py` / `analyze_specialization.py` と同じ作法)。

### 3.4 閾値の初期値(**ドラフト**。凍結は較正期の終わりに行う)

| 引数 | ドラフト値 | 根拠 |
|---|---|---|
| `--alpha` | 0.05 | 事前登録ドラフトの `p_max` と揃える |
| `--min-rel-slope` | 0.02 | 「1 シミュ日あたり平均の 2%」= 10 日で 20% の縮み。mock 縦煙の実測で最大だった シグナル(`reg_visit_entropy` の −1.06%/日)より**大きい**側に置いた=現状の健全なランを退行と呼ばない下限 |

★これは**ドラフト**である。凍結の手続きは §5 の「較正と検証の分離」に従う。

## 4. 分散崩壊診断(§3 の「統計的平滑化と区別する」)

    python scripts/detect_regression.py --variance-collapse runs/n50 runs/n100 runs/n200 \
        --alpha 0.05 --min-rel-slope 0.02 --out runs/n200

### 4.1 なぜ区別が要るか

§3 は「エージェント間分散を **N の関数としてプロット**し、**統計的平滑化(1/√N)**と
**モデル由来の均質化**を区別する」と要求する。この 2 つは見た目が似ている。

区別の鍵は **推定量の選び方**にある。個体間分散の**不偏推定量(n−1)は、
iid 標本なら期待値が N に依存しない**(N とともに縮むのは推定量の**ばらつき**であって
**期待値**ではない)。したがって「N を増やして期待値が下がる」なら統計的平滑化ではない。

### 4.2 2 本の曲線を重ねる

- **(a) 帰無帯** … *最大 N のラン*の個体集合から m 体を無作為抽出して分散を計算し、
  m を掃く。母集団が同一なので**期待値は平坦**で、幅だけが m とともに縮む
  (≈ V·√(2/(m−1)))。乱数は `numpy.random.default_rng(0)` 固定 = 決定論。
- **(b) 実測** … N の違うラン(それぞれ全個体)の分散。

**帯の向きの読み方(ここを間違えると診断が逆になる)**:

| 実測の位置 | 意味 | verdict |
|---|---|---|
| 帯の**上**(小 N のほうが多様) | 大きい集団が抽出ノイズで説明できないほど均質 = **モデル由来の均質化** | `MODEL_HOMOGENIZATION_SUSPECTED` |
| 帯の**中** | 「V は N に依存しない」と整合 | `NO_COLLAPSE` |
| 帯の**下**(N が大きいほど多様) | 崩壊の向きではない。**N ごとに母集団構成が違う**疑い | `POPULATION_MISMATCH_SUSPECTED` |

参考として log-log 上に **b=0(崩壊なし)** と **b=−0.5(1/√N)** の傾き線を引く
(`regression_variance.svg`。matplotlib 非依存の素の SVG)。

### 4.3 ★実測で最初に出た答えは「母集団構成の不一致」だった(正直に記録する)

mock で N=50 / 100 / 200(いずれも 288 step・`conf/smoke_tall.yaml`)を回して診断した結果:

| ラン | N | V(個体間分散) | 帯 5% | 帯 95% | 位置 |
|---|---|---|---|---|---|
| vc_n50 | 50 | 1.2145e-03 | 1.4027e-03 | 2.1908e-03 | **下** |
| vc_n100 | 100 | 1.3555e-03 | 1.5285e-03 | 1.9918e-03 | **下** |
| smoke_tall_mini | 200 | 1.7672e-03 | (帯の出所) | | 中 |

log-log 傾き **b = +0.27**(分散は N とともに**増える**)。verdict は
`POPULATION_MISMATCH_SUSPECTED`。

原因は判っている: 平坦名簿(300 件)を `roster[agent_id % len(roster)]` で巡回複製して
いるため、**N=50 のランはペルソナ空間の 50 件しか使っていない**。母集団構成が N ごとに
違うので、帯(= 母集団が同じという帰無)から外れて当然である。

**この装置を本気で使うときは人口構成を揃えること**:
`python scripts/gen_personas.py --pool 8000 --sample 2500 --seed 42 --out data/personas_2500.json`
で相異なる 2,500 件を作り、そこから各 N を**同じ抽出規則で**切る(または pool の
`present_cap` だけを変える)。この前処理をしない N 掃引で「崩壊した / しない」を
主張してはいけない。

## 5. 較正と検証の分離(§3 の運用要求)

§3: 「**較正**(逸脱したら停止して調整)と**検証**(較正に使っていない別の観測量での照合)は
分離し、**パラメータ凍結後に検証期へ移る**。」

### 5.1 手順

1. **較正期(パラメータは動かしてよい)**
   - `conf/smoke_tall.yaml` を回し、**最初の 1 シミュ日**で §8 の目安に入れる:
     - 1 人あたり平均エピソード数 **4〜8 /日**
     - engaged 滞在時間が**起床時間の 1〜2 割**
   - 逸脱したら止めて θ_in / `talk_idle_min` 等を調整し、**最初からやり直す**。
   - 較正に使った量(エピソード数・滞在時間)は**検証には使えない**。
2. **凍結**
   - 較正で決めた conf を `run_manifest.json` の `config_sha256` ごと記録する。
   - `--alpha` / `--min-rel-slope` を確定し、本文書 §3.4 の表を「ドラフト」から
     「凍結」に書き換える(= 事前登録と同じ手続き)。
3. **検証期(パラメータは動かさない)**
   - 退行シグナル 4 群は**較正に使っていない**ので、そのまま検証量として使える。
     これが「較正と検証の分離」を実際に成立させている点である。
   - `detect_regression.py` を通し、`REGRESSION` が出たら**その事実を報告に書く**
     (パラメータを触って消しに行かない。それをした瞬間に検証ではなくなる)。

### 5.2 較正の実測(mock・第91バッチ検収時)

`conf/smoke_tall.yaml` の縮小版(200 体・mock・seed 42)。

| ラン | 期間 | エピソード | /人/日 | §8 目安 | LLM 呼/人/日 | L1 件数 |
|---|---|---|---|---|---|---|
| smoke_tall_mini | 288 step(2 日) | 3,166 | **7.92** | 4〜8 | 23.40 | 185,843 |
| smoke_tall_6d | 864 step(6 日) | 9,429 | **7.86** | 4〜8 | 23.81 | 581,584 |

エピソード数は §8 の目標帯の**上端寄りで安定**している(第87 の実測 7.38/人/日 と整合)。
呼数 23.8/人/日 が §6 の「実効 4〜8 呼/人/日」を超えるのは第87 で既に記録済みの
不整合(原文書が §6 で「呼」・§8 で「エピソード」と書いており、1 エピソード = 1 呼では
ないため。実測 2.37 ターン/エピソード)。**本バッチはこの不整合を解消していない**。

### 5.3 watchdog から呼ぶ(ラン中の監視)

`--quick` は **1 行 JSON だけを出し、ファイルを 1 つも書かず、絶対に非ゼロ終了しない**
(監視がランを殺してはならない。P0 の `llm_health` 監視と同じ方針)。

    python scripts/detect_regression.py runs/smoke_tall --quick \
        --alpha 0.05 --min-rel-slope 0.02

- 実行中のランでは canonical parquet がまだ無いので、**完結した part だけ**を読む
  (`live_viewer.is_complete_parquet` のフッタ判定を流用)。書きかけの part は読まない。
- ★part は `live_viewer._open_shared` 経由で開く。**第77バッチの実測事故**
  (Windows の素の `open()` は `FILE_SHARE_DELETE` を立てないので、読んでいる最中の part を
  ランが `unlink` できず**シム本体が finalize で落ちる**)を踏まないため。
  「読むだけ」がシムを壊しうるという教訓の再利用である。
- `watchdog.py` には汎用の外部コマンドフックが無い(`--cmd` はテスト用の基底コマンド
  差し替えのみ)ので、当面は**別プロセスで定期実行する**:

      # PowerShell(10 分ごとに 1 行 JSON を追記)
      while ($true) {
        python scripts/detect_regression.py runs/smoke_tall --quick `
          --alpha 0.05 --min-rel-slope 0.02 >> runs/smoke_tall/regression_watch.jsonl
        Start-Sleep -Seconds 600
      }

## 6. 横煙(N=25万)の前提条件 — **実走はしていない**

`conf/smoke_wide.yaml` は「回すならこの構成」の宣言である。第91バッチでは**回していない**。
以下は調査で確定した事実と、外挿による見積である。

### 6.1 ペルソナ資産 — **足りている**

`data/persona_pool` は実測 **1,000,000 件**(L1 30,000 / L2 253,702 / L3 36,690 /
L4 678,588 / L5 1,020・ディスク約 737MB・`meta.json` の `total_generated` と一致)。
25万 ≪ 100万なので **複製・水増しの実装は不要**(`build_persona_pool.py` に複製オプションは
無いが、必要になったことがない)。25万専用の小プールが要るなら
`python scripts/build_persona_pool.py --fraction 0.25 --out data/persona_pool_250k`。

### 6.2 ★在場 25万は「日常が回る構成」にならない(presence の層優先の帰結)

`src/society/world/presence.py` の `_TIER` は
`resident(0) > duty(1) > workday_shift(2) > cadence(3) > stochastic(4)` で、
cap で溢れた層を当日ランキングで切って **break** する。したがって:

- **平日**: resident 30,034 + duty 986 = 31,020 → 残 218,980 を workday_shift(253,702)が
  埋めて cap 到達 → **cadence / stochastic が 1 人も入らない = 来街者ゼロの街**。
- **週末**: workday_shift が失格 → 在場可能なのは概算 **6 万人程度**で 25万に届かない。

横煙は「**平日 1 日ぶんのスループット/OOM 試験**」として読むこと。人口構成まで現実に
寄せるなら presence の層優先か pool 総件数を触る判断が要る(= ユーザー判断。未着手)。

### 6.3 メモリ見積(**実測ではなく外挿**)

`runs/_bench/bench_scaling.json`(P0・mock・144 step・基底 config):

| N | peak RSS |
|---|---|
| 10 | 202.2 MB |
| 100 | 269.9 MB |
| 300 | 443.8 MB |
| 1,000 | **1,454.1 MB** |

固定分を除いた傾き **(1454.1 − 202.2)/990 = 1.2645 MB/agent**。素直に延ばすと:

| N | 外挿 RSS |
|---|---|
| 1万 | ≈ 14.5 GB |
| 10万 | ≈ 145 GB |
| **25万** | **≈ 316〜363 GB** |

これに **PoolStore の索引 0.7〜1.2 GB**(`_build_index` が pool 総件数=100万ぶんの
`PresenceRec` / offsets / index を常駐させる。`present_cap` を下げても減らない)が乗る。
**単ノードでは成立しない**。

**★正直な訂正**: 「`rehearsal_pool10k`(1万体)の RSS 実測」は**存在しない**。
当該ラン(2026-07-21)の `summary.json` は `peak_rss_mb` / `elapsed_sec` を持たない
(両キーは P0 = 2026-07-29 に追加された)。残っているのは出力量だけである
(`l1_events.parquet` 174.9MB / 16,220,177 events / 18.95 呼・人・日)。
したがって 25万の見積は **N=1,000 からの外挿一本**で、1万体の実測による裏取りが無い。
**横煙を回す前に、まず 1万体の RSS を取ること**(`bench.py` の `peak_rss_mb` 経路)。

背景 SoA(`docs/plans/million-scale.md` §4.2-C の「~2.3GB」)は**未実装**なので当てにしない。
観測ストリーミング(W2-F)も未実装で、`observer/measure.load_events` は全件 RAM 展開のまま
= **回せても測れない**状態である。

### 6.4 必ず立てるスイッチ

| キー | 値 | 理由 |
|---|---|---|
| `observer.flush_every_steps` | > 0 | 既定 0 のままだと L1 バッファで即 OOM(25万 × 1.3 events/agent-step × 36 step ≈ 1,170 万件) |
| `pool.dormant_cap` | > 0 | 既定 0(無制限)は日次ローテーションで際限なく膨れる |
| `observer.regression.enabled` | **false** | 窓合計が在場個体数に比例して常駐する。退行の検出は縦煙の仕事 |
| `observer.echo.enabled` | false | 常設列だが 25万 × rolling 窓の発話タリーは純粋な重し |
| `lens.enabled` | false | 読むだけでも N 比例のコストがある |

## 7. やらないこと(と、その手順だけ)

### 7.1 バッチ推論由来の非決定性の測定(**本選 GPU 事項**)

§3: 「バッチ推論由来の非決定性(同一シードでも分岐する)は、**分岐点とその後のマクロ指標差を
測定して精度の上限として記録する**。」

これは実 LLM(vLLM の継続バッチング)でしか起きないので**測っていない**。手順だけ残す:

1. 同一 conf・同一 seed で **2 ラン**を回す(`model.backend=vllm`・`engine.batch_llm.workers>1`)。
2. `observer.state_hash.enabled: true` にしておく。チェーンが**最初に食い違う step**が分岐点。
   (第78 の装置。L1 バイト比較より軽く分岐点を特定できる。厳密判定は L1 バイト比較のまま。)
3. 分岐点以降について、本文書の 4 群 + `diagnose_stationarity.py` の TVD を 2 ラン間で比較し、
   **「同一 seed でも動きうる幅」= 精度の上限**として報告に載せる。
4. その幅より小さい条件間差は**主張しない**(サーベイ S-05 の「内在的変動を織り込む統計枠組み」)。

## 8. 正直な限界(まとめ)

1. **rolling 窓は独立標本ではない**。窓幅で間引いても完全な独立ではない(窓の境界で
   同じイベントが両側に入りうる)。
2. **Mann-Kendall は単調傾向しか見ない**。「途中で一度崩れて戻った」型の退行は検出しない。
3. **母集団は「窓内に L1 イベントを出した個体」**。睡眠中で無イベントの個体は分母から落ちる。
4. **語彙は文字 n-gram であって語ではない**。除外できる機構由来の固定文は engaged の
   `TEMPLATE` 1 種だけ。
5. **分散崩壊診断の帰無帯は「そのラン内の個体は交換可能」という仮定に立つ**。
   N ごとに人口構成が変わるランでは、帯の外れがモデル由来ではなく母集団構成の差でも起きる
   (§4.3 が実際にその形だった)。
6. **`--min-rel-slope` のドラフト値は mock 1 系列からしか決めていない**。実 LLM の
   縦煙で分布を見てから凍結すること。
7. 本文書の①〜④は**退行の必要条件を測る計器**であって、「退行していない」ことの証明では
   ない。4 群が全部平坦でも、測っていない次元(例: 発話の意味的多様性)が痩せている
   可能性は残る。
