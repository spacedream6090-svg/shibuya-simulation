**データ上おおむね健全で問題薄と確認した観点**(捏造回避のため明記):
- **モビリティ/POI利用**: mem100 は arrive が514ノードに分散(最頻でも10%)、平均で屋外1.8/屋内1.2/就寝0.3体と偏りなし。80体ランも334〜494ノードに分散、最頻ノード4%以下。**「家に籠りきり/一極集中」は観測されない**。

## 2. 各問題の詳細

### P1 — 状態飽和(最重要)

**症状(数値, mem100 / 100日)**
- `mean_grievance`: 0.100(初期)→ 10日目0.064 → 20日目0.031 → 以降ずっと **0.012〜0.038**。全stepの **17.85%** が ≤0.01(床張り付き)。
- `mean_efficacy`: 0.5 → 20日目0.773 → 100日目 **0.979**。個体は 1.000 にクリップ(id0/id2/id4 が efficacy=1.0)。
- 80体ランでも同傾向で、より速い: eco80 は1日で grievance 0.100→0.004(全stepの52%が≤0.01)、eco80_3day は2日で 0.100→0.033。
- 結果、100日目の5体の grievance は 0.000〜0.022 に密集=**個体差が消失**。

**根本原因(コード)**
- 更新則の magnitude が構造的に非対称。`src/society/factors/update.py:30-50`(`DEFAULT_MAGNITUDES`):
  - efficacy の**正**の源が多数・強い: `being_heard +0.006`(`update.py:139-145`)/ `work_done +0.012`(`:148-151`)/ `vicarious +0.004`(`:154-157`)/ `own_adopted +0.010`(`:166-172`)/ `heard_positive +0.006`。**負**は `ignored -0.004`(`:144`)のみ。→ efficacy は単調に天井へ。
  - grievance の**正**の源(congestion +0.010・heard_negative +0.020・money_pressure +0.015)は発生頻度が低く、**負**の `park -0.008`(`:160-163`)と heard_positive(-0.010)が日常的に効く。→ grievance は単調に床へ。
- `_bump` は clip [0,1] のみで**恒常性(baselineへの復帰)を意図的に入れていない**(`update.py:7,61-75` の R7 方針)。飽和を「affordance 制約」に委ねる設計だが、実データ上その制約が釣り合わず両端に張り付く。
- 飽和を破るための対抗力は**実装済みだが既定OFF**: `relative_deprivation_grievance`(`update.py:49`, 既定0.0)、`media_grievance`(`:44`, 既定0.0)、weather の `rain_grievance`。mem100 config でも全て未使用。
- 既知課題(retrospective-2026-07-07.md §2 懸念1「動機の飽和が創発を殺している」)と一致。本分析は100日ランで**定量的に再確認**し、かつ**個体差の消失**まで示した点が追加。

**修正案**
1. (即効・config)相対的剥奪を有効化: `factors.relative_deprivation_grievance ≈ 0.012`。他者所持金中央値との格差で grievance に**個体差**を復活させる(参照集団依存=飽和を破る第一手)。
2. (即効・config)日次の弱い恒常化圧を導入: `media_grievance ≈ -0.03`(在宅娯楽で気分修復)+ 生活圧側 `fixed_cost_daily`(例300)/ `rain_grievance` を有効化し、grievance を「上げ下げ両方向」に往復させる。
3. (要設計)efficacy の負フィードバック追加を検討: 例)長期の無効化(提案が通らない/無視の累積)で efficacy を漸減させる seam。ただし更新則の追加は src 変更のため主エージェント差配。
4. (要設計)efficacy/grievance に**緩い漏れ積分(baseline復帰)**を1本入れる(R7方針の再検討)。感情ハブ affect の arousal は既に漏れ積分器(`update.py:108-136`, `factors/affect.py`)なので同型で追加可能。

**リスク**
- **ゴールデン**: 既定OFF因子をONにすると L1(state_update 列)が変わり `tests/data/golden_baseline_l1.json` と不一致になる。ただしゴールデンは「全OFF」基準なので想定内。ON構成用の別ゴールデンを主エージェントが用意する前提。
- **R1(k非依存)**: grievance は drive の `state_change`(重み0.5, mem100 config `drive.weights.state_change`)にフィードバックするため、grievance 動態を変えると**発火回数(n_fires)の絶対値が動く**。ただし relative_deprivation は所持金のみ参照で writeback/belief を見ない=**k(free/off)に非依存**なので「k間で n_fires が一致」というR1不変は保たれる。実装後は `n_fires` の free==off を必ず smoke で確認。
- **決定論**: relative_deprivation/media/weather の各hookは追加RNGを引かない(_bump は乱数不使用)。中央値計算も決定論。新streamを引かなければ乱数系列は不変。

### P2 — 経済の暴走的偏在 + 来街者の恒久破綻

**症状(数値)**
- mem100(5体・口座ON): `mean_money` 20,156→2,739(最小125)。一方 `mean_account` 6,904→**49,317**(単調増加)。資産(現金+口座)の **Gini が10日目に0.79へ跳ね、以降100日ほぼ0.80で固定**。
- 最終個体別(現金/口座): **id1(居住者・フリーランス)= 13,094 / 246,587(計約26万)** に対し、**id0/id2/id4(来街者)= 0 / 0**、id3=603/0。→ **1体が資産をほぼ独占、4体は完全枯渇**。
- 原因は構成にも起因: `data/personas_80.json` は **62%(50/80)が来街者(visitor)**。mem100 は先頭5体を採用=偶然4体が来街者。
- 80体ランでも同構造が確認できる(eco80_3day, 現金のみ): 来街者の平均資産 **24,734** vs 居住者 **72,697**(約3倍差)。**Gini が3日で 0.44→0.51、n_broke 0→8** と発散の初期兆候。長期化すれば mem100 の来街者大量破綻に至る軌道。

**根本原因(コード)**
- 来街者は**口座を持たない**: `src/society/economy.py:139-148`(`split_account`)が visitor に account=0 を返す。
- 来街者の所持金は**一度きりの allowance のみ**で反復収入が無い: `economy.py:173-180`(`initial_money`、visitor は allowance レンジ)。本業賃金 `wage_amount` は職場を持たない来街者に0(`economy.py:151-158`)。
- したがって来街者は消費(`_spend`, scheduler.py:335-364)で現金が減る一方、**口座もATM引出原資も無く、下限0に達すると恒久固定**(`_atm_withdraw` は account<=0 で即return, `scheduler.py:318-333`)。生活保護等の下限所得は government OFF のため無し。
- 逆に居住者(id1)は日銭/月給が**口座へ加算**され(`_pay_wage` の `agent.account += amount`, `scheduler.py:299-315`)、支出の吸い込みが弱い: 家賃は `period_income × rent_share` のみ(`_phase_accounts_day`, `scheduler.py:1592-1599`)で mem100 では100日で rent イベント**わずか3回**、`fixed_cost_daily=0`。→ **口座が青天井で累積**。
- 補足: memory-100day-audit.md §付随観察は「n_broke は現金だけ見た誤検出の疑い」と推定したが、**本分析の口座直読(L3)では該当4体は現金も口座も0**。誤検出ではなく**真の破綻**であり、監査の仮説は棄却される(→P5)。

**修正案**
1. (config/シナリオ)長期・経済分析ランは**居住者中心の構成**にする(visitor比率を下げる、または居住者のみで keystone を観測)。少なくとも paper-grade ランでは 62% visitor をそのまま長期回さない。
2. (config)恒常支出を有効化して**haves側の青天井を抑制**: `economy.fixed_cost_daily`(例300)、家賃の下限適用。相対的剥奪(P1修正1)と併用で下層の grievance も機能する。
3. (要設計)来街者に**滞在中の少額日銭 or 帰宅→再来街での allowance 再付与**を与え、下限0固定を回避(観光消費のリアリティも上がる)。src 変更のため主エージェント差配。
4. (観測)L2 に **wealth_gini** 集計を追加(現状 `mean_money`/`mean_account`/`n_broke` のみで偏在が見えない。平均値は独占を隠す)。`observer/aggregate.py` への集計関数追加は None返しでOFF不変の作法に沿えば安全。

**リスク**
- **ゴールデン**: fixed_cost_daily>0 は spend イベントを増やし L1 が変わる(現状ゴールデンは0=不変前提)。ON構成の別基準が必要。
- **R1**: 経済量は drive の発火重みに直接は入らない(money_pressure は grievance 経由で `state_change` に間接波及)。k非依存性は保たれるが、money_pressure 頻度が変われば n_fires の絶対値は動きうる→ free==off の一致を smoke 確認。
- **決定論**: allowance 再付与を入れる場合は**新規RNG streamを追加しない**(既存stream消費順を崩さない)よう注意。wealth_gini 集計は乱数不使用で安全。

### P3 — 発話の定型化(冒頭句の反復)

**症状(数値)**
- mem100: 全1,343発話中、8文字冒頭句「**この時間の渋谷、**」が **127回(9.5%)**。冒頭句が3体以上で共有される発話が **547/1,343 = 40.7%**。長文(40〜83字)がそのまま複数回反復(同一55字文が5回、別文4回・3回…)。
- eco80_3day: 全4,172発話中、同「この時間の渋谷、」が **207回(5.0%)**、冒頭句≥3共有が **2,111/4,172 = 50.6%**(=会話の半分が一握りの定型導入)。日次 3-gram TTR は 0.166→0.156→0.154 と低く微減。
- 旧世代の day80 は冒頭句最頻でも1.9%・≥3共有24.5%と軽い。→ **新しいプロンプト構成で定型化が悪化**している疑い。

**根本原因(コード)**
- プロンプトが `時刻:` と `場所:` を明示注入し(`src/society/cognition/deliberate.py:129-130`)、対面会話分岐で「今この場所・この時間ならではの話題」を促す(`:185-187`)。モデルが時刻+場所を**そのまま情景報告文**にして「この時間の渋谷、静かで…」を量産する。
- 「場所や時刻の報告文にしない」という抑制指示は **`post`(SNS)分岐のみ(`deliberate.py:194`)** に存在し、**`social`(対面speak)/`reply` 分岐には無い**(`:185-190`)。→ 対面発話に情景報告ガードが掛かっていない。
- 反復抑制指示(`deliberate.py:181-182`)は**自分の直近2発話(`agent.said[-2:]`)のみ**を参照。他者との横断的定型化も、2発話窓を超える自己反復(100日で同一長文5回)も検知しない。

**修正案**
1. (src, 主エージェント差配)`social`/`reply` 分岐にも「場所・時刻の報告文にしない/挨拶や情景描写で始めない」ガードを追加(post 分岐 `:194` と同型の1行)。最小変更で効果大。
2. (src)反復抑制の参照窓を拡大: `agent.said[-2:]` → 直近4〜6発話、または冒頭句の重複を明示的に禁じる指示を追加。
3. (config)`model.temperature` を 0.7→0.85 程度に上げる/`presence penalty` 相当の指示強化(qwen3:8b はローカルなので指示ベースが現実的)。
4. (観測)L2 `speech_diversity` を「全発話の冒頭句ユニーク率」も見る指標に補強(P6参照)。

**リスク**
- **決定論/R1**: プロンプト文言の変更は LLM 出力を変えるが、**発火回数(n_fires)・RNG消費は不変**(プロンプト内容は発火判定に無関係)。R1(free==off の呼数一致)は保たれる。ただし LLM キャッシュ(`model.cache`)のキーが変わり過去キャッシュは無効化される。
- **ゴールデン**: golden は mock LLM ベースなら文言変更の影響は限定的(要確認)。実LLMランの再現性(seed固定でも文面は変わる)には影響。

### P4 — 自然造語がほぼ発生しない

**症状(数値)**
- eco80/eco80_3day/day80 いずれも **label_coin=1, vocab_coin=1**(=ラン全体で新語誕生が実質1回)。vocab_use は 38〜177 と「1語が広がる」挙動はあるが、**語の genesis(発生)がほぼ起きていない**。
- mem100(5体・100日)は label系/vocab系イベントが**ゼロ**(造語が一度も起きず)。

**根本原因(仮説)**
- ラベリングは `labeling.mode=constrained` + `adopt_threshold=2`(mem100 config `:171-173`)。造語の誘発が弱く、5体規模では臨界に達しない。
- 造語は「促進しない・自然発生を観察する」方針(user memory: natural-coinage-observation)なので**設計意図どおり**の面もある。ただし現状は「観察窓が閉じている(サンプルほぼ0)」ため、k\* 研究のアウトカムとして機能していない。

**修正案(観測強化寄り。促進はしない方針を尊重)**
1. まず「造語が起きる最小条件」を短ランで探索(規模・接触密度・unknown_word 発火重み `drive.weights.unknown_word=0.4` の感度)。促進バイアスではなく**発生機会**(接触・話題の新規性)を増やす方向。
2. 造語文脈のログを厚くして「なぜ起きない/起きたか」を事後分析可能に(coin_label 前後の文脈、user memory の natural-coinage-observation に沿う)。
3. 5体ランでは造語アウトカムを主指標にしない(規模不足)。造語観察は80体以上×複数日で。

**リスク**: 観測強化は L1 に列/イベントを足すが None返し作法でOFF不変を守れば golden 影響なし。促進系の magnitude を触ると研究の中立性(R4)を損なうため**触らない**。

### P5 — (訂正)n_broke の「口座無視バグ」は現行コードで解消済み

**経緯**: memory-100day-audit.md §付随観察 が「n_broke は現金だけ見た誤検出の疑い」と記載。タスク指示でも同疑いが挙がっていた。

**確認結果**: `src/society/observer/aggregate.py:200-212`(`_n_broke`)は**口座ON時に現金+口座の合算で判定**しており、口座を無視していない。
```
return sum(1 for a in sim.agents
           if getattr(a, "money", 0.0)
           + (getattr(a, "account", 0.0) if accounts_on else 0.0) < thr)
```
mem100 の L2 `n_broke=4` は L3 実データの「現金+口座 < 2000 の個体数=4」と一致。**誤検出ではなく実際に4体が現金も口座も枯渇**(P2)。よって「n_broke バグ」は**存在しない**と結論。

**残る改善**: n_broke は「破綻の頭数」だけで**偏在(Gini)を見せない**。P2修正4の wealth_gini 追加で補完すべき。**リスク: なし**(集計追加のみ、None返しでOFF不変)。

### P6 — ログ肥大と崩壊検知指標の設計限界

**症状(数値)**
- mem100 の全53,856イベント中 **traffic_flow が14,400件(=全体の27%)**。毎step 1件を無条件記録(`aggregate.py` の `n_cars` とは別に L1 へ)。5体ランで背景交通ログが最大の単一種。
- L2 `speech_diversity`(`aggregate.py:310-319`)は**各体の「直近1発話」だけ**を連結して3-gram TTR を取る設計。5体では標本5発話・毎step変動が大きくノイジーで、mem100 では 0.000〜1.000 を乱高下し**定型化(P3)の40%冒頭句反復を捉えられていない**(実測で定型化しているのに指標は崩壊を示さない)。

**修正案**
1. (config)traffic_flow の L1 記録を間引く/集計のみ(L2 `n_cars`)に寄せる。`world.traffic.max_log`/`max_cars_log` は既にあるが L1 毎step記録自体を日次サンプリングに落とす選択肢。長期・大規模ではストレージ支配要因。
2. (src/観測)`speech_diversity` を「直近N発話のウィンドウ」または「冒頭句ユニーク率」ベースに補強し、P3の定型化に感度を持たせる。現行の直近1発話依存は崩壊検知(R12)の目的に対して弱い。

**リスク**: いずれも観測層のみ。L1間引きは golden(全イベント一致)に影響するため別基準が必要。乱数・発火には無関係でR1/決定論は不変。

## 3. 優先度順・修正リスト(実装の入口)

1. **[S] 状態飽和を破る(P1)** — まず config で `relative_deprivation_grievance≈0.012` + `fixed_cost_daily≈300` + `media_grievance≈-0.03` を有効化した**短ラン(≤24step or 3日)**で、grievance/efficacy が両端張り付きを脱し個体差が戻るかを検証。効果が薄ければ efficacy 負FB/漏れ積分(src変更)を設計。
2. **[A] 経済偏在の是正(P2)** — 長期・経済ランを**居住者中心構成**へ。恒常支出ONで haves の青天井抑制。来街者の日銭/allowance再付与は要設計。並行して L2 に **wealth_gini** を追加(偏在の可視化)。
3. **[A] 発話定型化ガード(P3)** — `deliberate.py` の social/reply 分岐に「情景報告文で始めない」1行追加(post分岐と同型の最小変更)+ 反復参照窓拡大。効果は冒頭句ユニーク率で測る。
4. **[B] n_broke の訂正を反映(P5)** — 監査ドキュメントの「誤検出疑い」を「実破綻+偏在」へ更新。wealth_gini でフォロー。
5. **[B] 造語観察窓(P4)** — 80体以上×複数日で造語の発生条件を探索(促進はしない)。造語文脈ログの拡充。
6. **[C] 観測層の整理(P6)** — traffic_flow の L1 間引き、speech_diversity のウィンドウ化。

**共通の検証プロトコル(user memory: validation-runs-short 準拠)**: 各修正後はフル日LLMランを回さず、**mock または ≤24step/≤3日 smoke** で (a) 目的指標の改善、(b) `n_fires` の **free==off 一致(R1)**、(c) 追加RNG stream 未発生(決定論)、(d) OFF構成での golden 不変、を確認してから本番長期へ。
