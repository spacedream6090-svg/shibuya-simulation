# 境界流量の較正データ — 何が無料で取れて、何が取れないか

作成 2026-08-10。**全ソースを実接続で検証済み**(URL・年次・粒度・ライセンスはこの日の実測)。
対象は P4「アクターモデル移行」の境界(boundary)流量、すなわち **街と外の世界のあいだを
1日に何人がどの時間帯に出入りするか**。

関連: 実装は `scripts/rw_fetch/transport_census.py` / `scripts/rw_fetch/odpt_passenger_survey.py` /
`scripts/build_boundary_counts.py`、テストは `tests/test_boundary_counts.py`。
既存の取得基盤の設計は `docs/research/rw-data-acquisition.md`。

---

## 0. 結論を先に(3行)

1. **駅×時刻の実測表は無料では存在しない。** 第13回大都市交通センサス(2021年度)には駅別×
   時間帯の集計表が無く、第12回(2015年度)にもそれは無い。時間帯の一次表は**圏域全体の
   構成比**しかない。したがって境界流量は「**水準(駅別・実測)× 形(圏域全体・構成比)**」の
   分解でしか組めない。この限界は消せないので、消せないものとして記録する。
2. **駅の数字は素朴に足すと必ず間違える。** 事業者で数え方が違い(JR=乗車人員 / 他=乗降人員)、
   乗降人員は乗換の通過客を含み、路線別の乗車を同一駅で足すと改札内乗換が二重に入る。
3. **街に本当に出入りする人数に一番近いのは第13回の「初乗り・最終降車駅間移動人員」。**
   渋谷発 228,988 人/日・渋谷着 223,865 人/日(2021年度)。同年度の JR 渋谷の乗車人員
   248,505 に対し、渋谷を初乗り駅とする JR トリップは 87,049 = **35.0%**。
   残る 65% は他路線からの乗換で、**街には一歩も出ていない**。

## 2. 取れなかったもの(重要)

### 2-1. 駅別×時間帯の乗降人員 — **無料には存在しない**

第13回(2021年度・2023-03-28 公開)の e-Stat 収録は **8 ファイルだけ**:

- 定期券調査 2 件(うち区間別枚数の CSV は **146 MB**)
- 一件明細調査 6 件(基本ゾーン間移動人員 / 行政区間移動人員 / 初乗り・最終降車駅間移動人員 /
  所要時間別人員(発地域)/(着地域))

**このどれにも時間帯の軸が無い。** 第12回で時間帯を持つのは
「目的別乗車降車時刻分布」(圏域全体・駅の次元なし)と
「路線別着時間帯別駅間輸送定員表」(輸送定員 = 供給側)、および
「ターミナル別乗換え人員表」のピーク時1時間値(窓は固定)だけ。

→ **駅×時刻は分解で近似するしかない。** その分解が §4。

### 2-2. 街路側の実測(スクランブル交差点の横断者数など)

スクランブル交差点の「1回の青で約3,000人」「平日26万人」といった数字は報道・観光資料に
出るが、**機械可読で再取得できる無料の一次ソースが見つからなかった**。値を拾って
ハードコードすることはしていない(出典と再現性が担保できないため)。

街路側については、既に取得済みの
**渋谷区オープンデータ Location Analyzer 通行/滞在人口**(`scripts/rw_fetch/shibuya_jinryu.py`・
CC BY 4.0・2018-01〜2024-12 の月次)が使える。ただし時間帯・平日休日の軸が無いので、
境界流量の**時間帯の形**には使えない(`docs/research/rw-data-acquisition.md` R8)。

## 3. ライセンスと再配布の立場

### 3-1. 国土交通省サイト(`mlit.go.jp`)= PDL1.0

<https://www.mlit.go.jp/link.html>(2026-08-10 実取得)より原文:

> 国土交通省ウェブサイトで掲載・発信している情報（以下「コンテンツ」といいます。）の
> 著作権は、特記されていない限り国土交通省に帰属し、権利表記の記載がない限り
> 「公共データ利用規約（第1.0版）」（PDL1.0）に準拠した利用条件の下で、利用することができます。

> ア コンテンツを利用する際は出典を記載してください。出典の記載方法は以下のとおりです。
> （出典記載例）出典：国土交通省ウェブサイト（当該ページのURL）
> 出典：「○○調査」（国土交通省）（当該ページのURL）など

`robots.txt` は 404(= クロール制限の宣言なし)。取得は静的ファイルの単発 GET のみ。

### 3-2. e-Stat = 政府標準利用規約(第2.0版)= **CC BY 4.0 互換**

<https://www.e-stat.go.jp/terms-of-use>(2026-08-10 実取得)より原文:

> 当サイトで公開している情報（以下「コンテンツ」といいます。）は、どなたでも以下の
> １）～６）に従って、複製、公衆送信、翻訳・変形等の翻案等、自由に利用できます。
> 商用利用も可能です。

> ウ 本利用ルールは、クリエイティブ・コモンズ・ライセンスの表示 4.0 国際
> （https://creativecommons.org/licenses/by/4.0/legalcode.ja に規定される著作権利用許諾条件。
> 以下「CC BY」といいます。）と互換性があり、本利用ルールが適用されるコンテンツは
> CC BY に従うことでも利用することができます。

> イ コンテンツを編集・加工等して利用する場合は、上記出典とは別に、編集・加工等を
> 行ったことを記載してください。

→ **センサス由来のデータは再配布可**(出典 + 加工した旨の明記が条件)。
`_meta.attribution` と `_meta.modified_note` がこれを満たしている。

### 3-3. ODPT = 公共交通オープンデータ基本ライセンス → **再配布しない**

`ckan.odpt.org` のデータセット頁が名乗るライセンスは
**「公共交通オープンデータ基本ライセンス」**(<https://developer.odpt.org/terms>)。
規約全文は JavaScript で描画される頁にしかなく機械取得できなかったため、
**原文の引用はここに置かない**(取れていないものを引用したことにしない)。

立場は既存の `odpt_rt` と同じく**厳しい方に倒す**:

- チャレンジ枠(JR東日本・東急・京王)は**再配布不可の可能性**があるものとして扱う。
- `data/realworld/` は .gitignore 済み。**生データはコミットしない・第三者に渡さない・
  論文や提出物に添付しない**(載せてよいのは集計値とグラフのみ)。
- 出典表示「本データは公共交通オープンデータセンターのデータを利用して作成。」は必須。
- `data/realworld/odpt_passenger_survey/README.md` に同じ内容を置いてある。

**そのため `boundary_counts.json` の `_meta.redistribution` は `restricted` に倒してある**
(センサス単体なら `ok` だが、ODPT が混ざるファイルなので全体を厳しい方に合わせる)。

## 4. 二重計上の分解 — 改札外 / 乗換

### 4-1. 罠は3つあり、どれも別物

| # | 罠 | どこに出るか | counts の印 |
|---|---|---|---|
| 1 | 事業者で数え方が違う | JR=乗車人員 / 東急・メトロ・京王=乗降人員 | `measure` が `boarding` か `boarding_alighting` か |
| 2 | 乗降人員が通過客を含む | 直通運転・改札内乗換 | `double_count: through_passengers` |
| 3 | 路線別の乗車を同一駅で足す | 駅別発着表 | `double_count: intra_station_transfer` |

### 4-2. 罠3の実測(第12回・2015年度)

渋谷の路線別「乗車」(合計券種・上下計、人/日):

| 路線 | 乗車 | | 路線 | 乗車 |
|---|---:|---|---|---:|
| 山手線 | 315,658 | | 銀座線 | 134,091 |
| 埼京線 | 39,186 | | 半蔵門線 | 251,397 |
| 湘南新宿ライン | 36,564 | | 副都心線 | 134,489 |
| **JR 3線計** | **391,408** | | 井の頭線 | 220,843 |
| | | | 東横線 | 262,816 |
| | | | 田園都市線 | 382,097 |

同年度(FY2015)の ODPT の JR 渋谷 乗車人員は **372,234**。
→ 路線別合計 391,408 は **+5.15% 過大**。この差が「山手線↔埼京線↔湘南新宿ラインの
改札内乗換を二重に数えた分」である。**JR 内だけでこの大きさ**なので、
事業者をまたいで全部足せば桁で狂う。

### 4-3. 乗換の大きさ(第12回 表4・渋谷 = ターミナル No.120)

ピーク窓は表側で固定 **7:45〜8:44**。

| | 終日(人/日) | ピーク時(人/時) |
|---|---:|---:|
| 初乗り計 | 6,863 | 3,112 |
| 最終降車計 | 170,181 | 55,911 |
| **乗換え計** | **337,369** | **151,641** |
| 合計 | 514,413 | 210,664 |

→ 渋谷の駅内流動の **65.6%(337,369/514,413)が改札内の乗換**。

**ただしこの表の絶対水準は使ってはいけない。** 「初乗り計 6,863 人/日」は、山手線だけで
乗車 31 万人/日 という駅別発着表の水準と桁が合わない。これは乗換施設の実態調査に基づく
**部分集計**(調査対象の乗換動線を通った移動しか覆っていない)だからである。
→ counts では全レコードに `double_count: partial_survey` を付け、
**乗換シェアなどの比率にのみ使う**と明記している。

### 4-4. 改札外流動の直接測定(第13回・2021年度)

「初乗り・最終降車駅間移動人員」は**トリップの最初に乗った駅と最後に降りた駅**の OD なので、
乗換の通過客が原理的に入らない。渋谷を端点とする合計:

| 事業者 | 初乗り(街→駅) | 最終降車(駅→街) |
|---|---:|---:|
| 東日本旅客鉄道 | 87,049 | 85,873 |
| 東急電鉄 | 83,461 | 45,938 |
| 東京地下鉄 | 26,159 | 62,542 |
| 京王電鉄 | 32,319 | 29,512 |
| **計** | **228,988** | **223,865** |

同年度の ODPT の JR 渋谷 乗車人員 248,505 と突き合わせると
**87,049 / 248,505 = 35.0%**。つまり **JR で渋谷から乗る人の3人に2人は
他路線から乗り換えてきただけで、街に出ていない**。

**これが境界流量として使うべき数字。** 街と駅のあいだの総交換量は
228,988 + 223,865 = **452,853 人/日**(2021年度・COVID 下)。

> ⚠ 第13回は **2021年度 = COVID 下**の調査。同じ年度の ODPT を見ると JR 渋谷の乗車人員は
> 平常時 366,128(FY2019)に対し 248,505(FY2021)= **67.9%** まで落ちている。
> FY2024 は 324,414 = FY2019 比 **88.6%** まで戻った。
> 改札外流動を読み替えるなら、JR の同駅同指標の比でおよそ
> **FY2024 相当なら ×1.31**(324,414/248,505)、**COVID 前の FY2019 相当なら ×1.47**
> (366,128/248,505)。
> **この補正は取得器も counts も一切していない**(生値のまま置いてある)。使う側で明示的に
> 掛けること。倍率の根拠は JR のみなので、他事業者に当てるのは追加の仮定になる。

### 4-5. 年度の regime を混ぜない

| | 第12回 | 第13回 |
|---|---|---|
| 調査年度 | 2015年度 | 2021年度 |
| regime | `pre_covid` | `post_covid` |
| 駅別水準 | あり | 駅間 OD のみ |
| 時間帯 | 圏域構成比のみ | **無し** |

counts の全レコードが `regime` を名乗る。**regime が違うレコードを同じ系列に並べてはいけない。**

## 5. counts ファイルの形と、シミュの出入口への当て方

### 5-1. スキーマ

出力は `data/realworld/boundary_counts.json`(.gitignore 済み)。
MATSim の `counts.xml` の意味論を平たい JSON にしたもので、`counts` は **1本の配列**。
必須欄は6つ、残りは判断を読む側に残すための付帯情報:

```jsonc
{
  "_meta": { /* 出典・ライセンス・caveats・notes・portal_mapping */ },
  "counts": [
    {
      "counter_id": "station.shibuya.gate.all.gate_entry",  // 一意な観測点名
      "location":   "station:shibuya:gate",                 // 場所
      "time_bin":   "daily",            // daily | hour:08 | hour:le06 | band:… | peak_hour:…
      "observed_count": 228988,         // 値(欠測は null で残す。偽の値で埋めない)
      "source":     "transport_census.station_od13",
      "year":       2021,
      // ↓ 以下は付帯情報(必須ではないが全レコードに入っている)
      "measure":    "gate_entry",       // 何を数えたか
      "unit":       "persons_per_day",
      "kind":       "observed",         // observed | derived
      "double_count": "none",           // §4-1 の罠のどれが乗っているか
      "portal":     "station",          // station | edge
      "operator":   "", "regime": "post_covid", "day_type": "weekday",
      "source_detail": "…", "derived_from": [], "note": "…"
    }
  ]
}
```

`double_count` の語彙(5語・これ以外は `_rec()` が例外を投げる):

| 値 | 意味 |
|---|---|
| `none` | そのまま使える(改札外の実移動・構成比) |
| `through_passengers` | 直通・改札内乗換の通過客を含む(乗降人員) |
| `intra_station_transfer` | 路線別の乗車で、同一駅の他路線からの乗換を含む |
| `supply_not_demand` | 輸送定員 = 供給側で、実乗客数ではない |
| `partial_survey` | 乗換施設調査の部分集計で、駅の全流動を覆っていない |

`(counter_id, time_bin, year, source)` の**一意性は検証で強制**している
(`validate_counts()`)。ここが衝突すると別の観測が同じ名前で静かに潰れるため。

実測の規模: **1,050 レコード**(line_capacity 456 / time_dist 228 / transfer 212 /
odpt 52 / station_flow 54 / station_od13 10 / derived 38)。

### 5-2. 時間帯の区分

センサスが持つ区分をそのまま使う(勝手に等間隔化しない):

- 時刻分布(`time_dist`)= **19 区分**。`～6時台` → `hour:le06`、`7時台`〜`23時台` →
  `hour:07`〜`hour:23`、`0時台～` → `hour:ge00`。
- 輸送定員(`line_capacity`)= **19 区分だが幅が不均一**(`始発～6:59`, `7:00～7:29`,
  `7:30～7:59`, …, `11:00～12:59`, …, `24:00～終発`)。`band:` 接頭辞で区別する。
- 乗換(`transfer`)= 終日 + **固定ピーク窓 1 時間**。`peak_hour:7:45～8:44`。

### 5-3. 水準 × 形 = 時間帯別(`kind: "derived"`)

`derive_hourly()` が「改札外流動の日合計(第13回)」×「時刻構成比(第12回)」を掛けて
時間帯別の推定流量を出す。**観測ではないので `kind: "derived"`** とし、
材料を `derived_from` に列挙する。

> ### ★ 目的の選び方で日変化の向きが逆になる(実測で確認した罠)
>
> 既定の `--derive-purpose 合計` の**乗車**構成比は朝 7–8 時に山がある。これは
> **住宅地から出る側**の形なので、**目的地側**である渋谷の「改札入場(街→駅)」に当てると
> 入場が朝ピーク(7時台 44,188 人/時)という**現実と逆向き**の日変化になる。
>
> 渋谷の入場は帰りの流れなので `--derive-purpose 帰宅` が近い。実際に当てると
> ピークが **18時台 47,288 人/時** に移り、形が素直になる:
>
> ```
> hour:07   708      hour:15  13,300      hour:19  29,004
> hour:08   996      hour:16  19,464      hour:20  20,304
> hour:12  6,645     hour:17  40,618      hour:21  12,775
> hour:14  9,075     hour:18  47,288 ←    hour:23   3,501
> ```
>
> 逆に「改札退場(駅→街)」は通勤の到着なので `通勤` の**降車**構成比が近い
> (既定の `合計` でも 8時台 47,036 人/時 にピークが立ち、向きは正しい)。
>
> **既定は素の `合計` のままにしてある**(取得器が勝手に賢いことをしない方針)。
> 選択は呼び出し側の明示に委ねる。

この按分の弱点は正直に書いておく:

- 形は**首都圏全体**の構成比で、渋谷固有の偏り(深夜の厚さ・週末の山)が入っていない。
- 水準は 2021年度、形は 2015年度で **年度がそろっていない**。
- 平日のみ。休日の形は別(センサスに休日の時刻分布は無い)。

### 5-4. シミュの出入口(portal)への対応

シミュ側の境界は `src/society/cognition/plan_boundary.py` の `gateway`(conf の
`world.…boundary.gateway`)で、2種類ある:

| portal | シミュ側 | 当てる counts |
|---|---|---|
| `station` | `gateway: station` = **駅ノード1点** | `station:shibuya:gate` の `gate_entry` / `gate_exit`(第13回・改札外流動)。時間帯を入れるなら `kind=derived` の hourly。 |
| `edge` | `city.gateways` = **徒歩で圏外へ出る縁** | **鉄道の counts は当てない。** 街路の実測が別途必要で、無料の時間帯別一次ソースは未取得(§2-2)。 |

つまり **`station` 側は数字が付いたが、`edge` 側は空のまま**である。これは分かっていて
空にしているので、`_meta.portal_mapping` にもそう書いてある。edge 側を埋めるなら
渋谷区の通行人口(月次・時間帯なし)か、街路の実測を別途探す必要がある。

**この counts ファイルをシミュ本体は読まない。** `src/` からの参照はゼロ、`conf/` への
キー追加もゼロ(`tests/test_boundary_counts.py::test_src_does_not_read_these_modules` が機械検査)。
用途は較正(ラン前)と事後検証(ラン後)だけ。

## 6. 運用上のメモ

### 6-1. 日次スケジューラには結線していない

センサスは5年に1度、ODPT の乗降者数は年1回の更新なので、
**`scripts/rw_fetch_daily.py` にも Windows タスク `shibuya-rw-fetch-daily` にも触っていない**。
`tests/test_boundary_counts.py::test_not_wired_into_daily_scheduler` が機械検査する。
取得は単発:

```bash
python scripts/build_boundary_counts.py --offline               # 取得計画だけ(0リクエスト)
python scripts/build_boundary_counts.py --fetch --with-od13     # 取得 → 正規化
python scripts/build_boundary_counts.py --report                # 中身の要約
python scripts/build_boundary_counts.py --derive-purpose 帰宅   # 按分の形を選ぶ
```

既取得のものは `--force` を付けない限り**リクエストを出さずに**飛ばす。

### 6-2. URL が動いたときの再発見手順

MLIT の `/common/00XXXXXX.xlsx` は表題を持たない連番なので、リンク切れが起きたら:

1. <https://www.mlit.go.jp/sogoseisaku/transport/sosei_transport_tk_000035.html> を開く。
2. 「鉄道調査 報告書資料編」の表 3 / 表 4 / 表 9、「参考表」の表 5 の**首都圏**列の
   リンク先を取る(表題は本文の表組みにあり、リンク文字列は `首都圏` だけ)。
3. `TABLES` の `url` を差し替える。パーサは見出し行を語で探すので、
   列の順番が変わっても壊れない(見出しが消えたら `ValueError` で落ちる)。

第13回は e-Stat の `statInfId` 直リンク。動いたら
<https://www.e-stat.go.jp/stat-search/files?page=1&toukei=00600020&tstat=000001103355>
から「第13回 → 一件明細調査 → 初乗り・最終降車駅間移動人員」と辿る。

### 6-3. xlsx を openpyxl 無しで読んでいる

この環境に `openpyxl` も `xlrd` も入っていないため、`read_xlsx_rows()` は
**標準ライブラリの `zipfile` + `xml.etree` だけ**で xlsx を読む(共有文字列表・
結合セル由来の欠番列に対応)。依存を1つも増やしていない。

### 6-4. セルのルビ

センサスの xlsx はセル本文に**ルビが連結**されている(`駅名エキメイ`、
`東海道本線トウカイドウホンセン`)。`strip_ruby()` は末尾のカタカナ列を、
**それが残りの文字列と同じかそれ以上の長さのときだけ**ルビとみなす。
これにより `湘南新宿ライン` の `ライン` を路線名の一部として残せる
(単純に末尾カタカナを削ると `湘南新宿` になってしまう)。
時間帯の見出しだけは例外で、`始発～6:59シハツ` のようにルビが短いため
`clean_time_label()` がカタカナを全部落とす(時刻表記にカタカナは出ないので安全)。

### 6-5. 保存物は渋谷に絞ってある

`station_flow` を首都圏全駅で展開すると 4 万件を超えるので、JSON は
**渋谷に触れる行だけ**にしてある(`_meta.station_filter` に明記)。
生 xlsx は `data/realworld/transport_census/raw/` に無加工で残してあるので、
他の駅が必要になったら `fetch_one(..., stations=(...))` で絞り直せる。

## 7. 残っている穴(次に手を付けるならここ)

1. **街路側(`edge` portal)の実測がゼロ。** スクランブル交差点の横断者数に相当する、
   機械可読・無料・時間帯別の一次ソースが見つかっていない。
2. **駅×時刻の実測が原理的に無い。** §4 の分解で近似するしかなく、渋谷固有の時間帯の
   偏りは入らない。ODPT のリアルタイム在線(`odpt_rt`)を長期に貯めれば、
   間接的に時間帯の形を推定できる可能性はある(未着手)。
3. **COVID の regime 補正をしていない。** 第13回(2021年度)の改札外流動は平常時より
   3割ほど低い。counts には生値のまま入れてあり、補正は使う側の判断に委ねている(§4-4)。
4. **休日の形が無い。** センサスの時刻分布は平日のみ。
5. **ODPT の京王が 2024年度からしか無い。** 長期系列の比較は JR/東急(2013–)に限られる。
