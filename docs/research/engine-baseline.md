# エンジン実測ベースライン(W2 P0)— 非LLM単価 c の規模別実測とホットスポット

- 作成: 2026-07-20 / 担当: Opus 4.8(実行)/ 種別: **実測レポート**(推定ではない)
- 位置づけ: [`docs/plans/w2-execution-plan.md`](../plans/w2-execution-plan.md) §4 **P0**。
  P1(背景SoA化・可否ライン)の投資判断の土台。全試算の前提だった
  [`scale-feasibility.md`](scale-feasibility.md) §4 の「非LLM 0.00183〜0.060 の 33倍レンジ」を
  **本番プロファイル + mock で実測して確定**する。
- 測定器: [`scripts/profile_engine.py`](../../scripts/profile_engine.py)(engine・conf・既定挙動を
  一切変更しない読み出し専用の計測。名簿100体は engine の `agent_id % len(roster)` 巡回で N 体へ拡張)。
- 生データ: `runs/_profile/engine_baseline.json`(gitignore 済み・非コミット)。

> **一行の結論**: 本番プロファイル(全リアリズム機能ON・広域地図 wide_v7)の非LLM単価は
> **c ≈ 0.00042(N=300)→ 0.00075(N=1000)→ 0.00166(N=3000)秒/agent-step** で、参考値レンジの
> **リーン端(0.00183)近傍〜以下**に着地した(full 0.060 は大幅な過大評価だった)。ただし **c は N に
> 対して超線形(step 総時間 ∝ N^1.5→1.7・悪化傾向)**。密度結合項(SNS タイムライン順位付け・
> 感情価スコア・知覚近傍)が超線形の源泉で、これが **P1 の SoA化・ベクトル化の主対象**。
> 0.0002 目標に対し最小 N でも 2.1倍・N=3000 で 8.3倍離れており、**密度結合項の平坦化 + 定数項の
> 半減の両方**が要る。

## §1 実測方法

- **プロファイル**: `conf/production.yaml`(第37バッチ本番ON編成・3パック全ON・広域地図
  `data/shibuya_osm_wide_v7.json`)。**mock バックエンド**(`model.backend=mock` を明示上書き。
  実LLM呼び出しゼロ)。よって測るのは「LLM をスタブ化した Python step 処理の単価」= 非LLM c。
- **規模拡張**: `run.n_agents` を 300/1000/3000 に上書きするだけ。名簿(`personas_100_civic.json`・
  100体)は `simulation.py` の `roster[agent_id % len(roster)]` と `organizations.attach` の
  `agent.id % n_roster` が既に巡回対応するため、**計測専用の合成名簿は作っていない**(engine の
  既定機構をそのまま使用=挙動を変えない)。
- **単価の測り方**: Simulation 構築(1回限りのセットアップ=c に含めない)→ warmup 2 step(計時外=
  初日境界・キャッシュ充填の一過性を除外)→ 残り 22 step を `time.perf_counter` で1 step ずつ計時。
  **c = Σ(step wall) / (N × 計時 step 数)**。イベントは RAM バッファに溜まるだけ(ディスク flush は
  finalize のみ=計時外)。cProfile は単価計測とは**別ラン**(プロファイラ overhead を c に混ぜない)。
- 各ラン 24 step(=シミュ内 4 時間・day0 の朝〜昼)。**早期(day0)の測定**である点は §5 の限界に明記。

### 既知の現況(測定対象の正直な状態)
- **from_roster が選挙へフォールバック中**: `personas_100_civic.json` に occupation=議員 の住民が
  0人のため、議会が名簿制ではなく従来の選挙機構で回る(w2-execution-plan §3.5 の既知宿題=P5 で
  議員名簿投入予定)。**これは現行本番プロファイルの実挙動そのもの**なので、そのまま計測した
  (選挙機構のコストも現況として c に含まれる。ただし選挙は稀イベントで step 支配項ではない)。

## §2 規模別 c の実測(本番プロファイル + mock・24step・warmup 2)

| N | 計時step | build [s] | 総step wall [s] | **c [s/agent-step]** | ms/step | events/agent-step |
|---:|---:|---:|---:|---:|---:|---:|
| 300  | 22 | 0.20 | 2.774   | **0.000420** | 126.1  | 3.29 |
| 1000 | 22 | 0.48 | 16.475  | **0.000749** | 748.9  | 4.63 |
| 3000 | 22 | 1.18 | 109.573 | **0.001660** | 4980.6 | 6.21 |

### N に対するスケーリング — 超線形(かつ悪化)
step 総時間 = N×c が **∝ N^p** に従うとして、実測点から p を求めると:

| 区間 | N比 | step総時間比 | **指数 p** | 1体あたり c の指数 (p−1) |
|---|---:|---:|---:|---:|
| 300→1000  | 3.33x | 5.94x  | **1.48** | 0.48 |
| 1000→3000 | 3.00x | 6.65x  | **1.73** | 0.73 |
| 300→3000  | 10.0x | 39.5x  | **1.60** | 0.60 |

- **線形(p=1)ではなく p≈1.5〜1.7 の超線形。しかも区間が上がるほど指数が増大**(1.48→1.73)=
  N が増えるほど密度結合が強まる。同一面積(wide_v7 ≈ 2×2km)に N を積むと密度が上がり、
  「speaker あたり hearer 数」「タイムライン候補投稿数」「同席者数」が増える → 1体の step 仕事量
  自体が N とともに増える構造(scale-feasibility §4.3 が警告した「固定面積に N を積むと O(N²) へ
  劣化しうる」の実証)。
- **events/agent-step も 3.29→6.21 と単調増**。相互作用・SNS反応・被発話イベントが1体あたり増える
  =超線形の直接の裏付け(記録量も超線形に膨らむ=P4 観測ストリーミングの必要性も補強)。

## §3 cProfile ホットスポット(N=1000 × 24step・cumtime 上位)

self時間(tottime)で見ると **`valence`(7.75s)と `dict.get`(6.04s)と networkx A*(2.08s)** が
CPU を実際に食っている三強。cumtime のツリーでは **SNSタイムライン順位付けの一群(合計 ~12.5s ≈
step の約1/3)** が最大の塊。上位を機能クラスタに束ねて解釈する。

| # | 関数(cumtime / tottime / ncalls) | クラスタ | 解釈と最適化の型 |
|---|---|---|---|
| 3 | `sentiment.py:91 valence`(13.3 / **7.75** / 149,191) | **感情価** | 純Pythonのテキスト走査で1回文字列を舐める。**決定論=文字列に対し冪等** → **メモ化 / 投稿ごとに1回だけ事前計算**すれば呼数を桁で削れる。self時間の断トツ首位。**ベクトル化/キャッシュの最優先対象**。 |
| 5–9 | `infoenv.timeline`→`internet.ranked_timeline_for`→`sorted`+`internet:179 <lambda>`→`infoenv.score_of`(各 ~12.4 / 137,884 回) | **SNSタイムライン順位付け** | 閲覧する各エージェントが候補投稿を**全数スコアリング**して並べ替え。O(閲覧者数 × 投稿数)で N とともに両方増える=**超線形の主犯**。投稿の基底スコアは step 内で一度だけ算出し、エージェント固有の整合(alignment)だけを**ベクトル演算**にする=SoA化の中核。`score_of` は `valence` を呼ぶので #3 と同根。 |
| 4 | `scheduler.py:1485 _phone`(13.2 / 0.07 / 7,085) | **携帯/閲覧フェーズ** | 上のタイムライン順位付けを駆動するフェーズ。ここの呼数(閲覧確率×在場)が密度で増える。 |
| 11 | `~ dict.get`(6.04 / **6.04** / **50,702,922**) | **辞書引き** | 5,070万回の汎用辞書引き(config/ノード/記憶/知覚に遍在)。**SoA化で多くが配列添字に置換**され、残りは下の config 巻き上げで消える。self時間2位。 |
| 12,14,15,21 | networkx `_call_if_no_backends_installed`(5.58)+`astar_path`(5.40 / 2.08 / 2,500)+`routing.h`(1.89 / 1M) | **経路探索** | `route()` 毎に networkx が**バックエンド有無を毎回走査**する純オーバヘッド(#12 の 5.58s は丸ごと無駄)。**経路キャッシュ / 自前の軽量A* 置換**で削れる。移動数に比例=N 線形項。 |
| 18,22,26 | OmegaConf `dictconfig._get_impl`(2.40)+`__getattr__`(1.86)+`basecontainer._resolve_with_default`(1.57) | **config アクセス** | step ループ内での `cfg.*` 深いキー読みの解決コスト(合計 ~5.8s の純オーバヘッド)。**構築時にプレーンな属性/辞書へ巻き上げれば消える**(sim は多くのブロックで既に実施済=残りの hot な cfg 読みを潰す)。**SoA不要で取れる早期の得点**。 |
| 20,24,28 | `memory._retrieve_actr`(2.10)+`_recall_noise`(1.71)+`_stream`(1.53 / 0.80) | **記憶想起** | 発火ごとの ACT-R 活性化記憶の想起+想起ノイズ。発火数に比例(N 線形+密度で発火機会増)。スリム状態化(P1)と記憶上限で有界化する対象。 |
| 27 | `perception.py:135 hearers_of`(1.57 / 0.72 / 30,506) | **知覚近傍** | 発話の可聴者探索。空間グリッド索引済みだが**密度が上がると近傍セル内の件数が増える**=超線形リスクの一つ。SoA位置配列+ベクトル近傍判定の対象。 |
| 30 | `map.py:87 node_xy`(1.25 / 0.58 / **2,054,839**) | **座標引き** | 205万回のノード→座標辞書引き。**SoA位置配列**にすれば添字1回に落ちる。 |
| 23 | `rng.py:22 stream`(1.82 / 0.90 / 64,433) | **RNGストリーム** | 決定論ストリームの文字列キー→ハッシュ派生。発火/知覚ごとに引く定数項。 |

### top-10 の要約(SoA/ベクトル化 vs 純オーバヘッドの仕分け)
1. **`sentiment.valence`** — self時間首位。文字列に冪等 → **メモ化/事前計算**(呼数を桁で削減)。
2. **SNSタイムライン順位付け(timeline/ranked_timeline_for/score_of/sorted)** — cumtime 最大の塊
   ・O(閲覧者×投稿)の**超線形主犯**。**投稿スコアの事前計算+alignment のベクトル化**(SoA中核)。
3. **`dict.get`(5,070万回)** — 遍在の辞書引き。**SoA配列添字化**で大半が消える。
4. **経路探索(networkx A* + バックエンド走査オーバヘッド)** — #12 は丸ごと無駄。**経路キャッシュ/
   自前軽量A***。SoA不要で取れる。
5. **OmegaConf config アクセス(~5.8s の純オーバヘッド)** — **構築時に属性へ巻き上げ**。SoA不要の早期得点。

**仕分け**: (2)(1)(#27 知覚)(#30 座標)= 密度結合・アルゴリズム項 → **P1 の SoA化/ベクトル化が本丸**。
(4)(5)+ `dict.get` の一部 = **純オーバヘッド(全 step 時間の推定 3〜4割)**で、SoA 投資の前でも
メモ化・config 巻き上げ・networkx 置換だけで取れる**先行しての早期削減候補**。

## §4 0.0002 目標への距離

| 規模 | 実測 c | 目標 0.0002 に対する倍率 |
|---|---:|---:|
| N=300  | 0.000420 | **2.1x 超過** |
| N=1000 | 0.000749 | **3.7x 超過** |
| N=3000 | 0.001660 | **8.3x 超過** |

- **最小 N(密度最小)でも 2.1倍**離れている。つまり密度をゼロにしても残る**1体あたりの定数仕事**
  (経路・記憶・プロンプト構築・config・RNG)だけで既に目標の 2倍。定数項の**約半減**が必要。
- その上に **超線形の密度項が乗る**。実測指数(300基準で c ∝ N^0.60、直近区間では N^0.73)を
  素朴に外挿すると、在場 25万(N=300 の 833倍)では c ≈ 0.000420×833^0.60 ≈ **0.023 s/agent-step**
  = 目標の **~100倍超**(直近区間の指数 0.73 を使えば更に悪化)。
  → **★この外挿は「固定面積 wide_v7 に N を積んだときの密度スケーリング」であり、80倍以上の
    範囲外挿で不確実(密度が実際にそこまで上がり続ける保証はなく、presence ローテーションで
    在場分布も変わる)。数字の絶対値ではなく「線形床 2倍 + 超線形の壁」という構造を読むこと。**
- **結論(P1 への含意)**: 目標 0.0002 は現行アーキのチューニングでは届かない。(a) 密度結合項
  (SNSタイムライン順位付け・valence・知覚近傍)を**ベクトル化して N 依存を平坦化**し、(b) 1体
  あたり定数項(座標/辞書引き・経路・config オーバヘッド)を **SoA + 巻き上げ + 経路キャッシュで
  半減**する — この**二正面**が P1 の設計要件。まずは §3 仕分けの「純オーバヘッド(3〜4割)」を
  先に潰すのが投資対効果の高い最初の一手。

## §5 限界・正直な明記

1. **早期(day0)測定**: 24 step は day0 の朝〜昼。実行が進むと記憶(episodes)・関係台帳・SNS投稿・
   スケジュール帳が累積し **1体あたり step コストは経時的に増える**。したがって本 c は**長期ランの
   下限**。参考値のリーン 0.00183 が本測定(N=300 の 0.00042)より高いのは、あちらが 100日=14,400
   step の平均(累積成長込み)であることと整合する。
2. **固定面積の密度**: 超線形指数は wide_v7(≈2×2km)上に N を積んだ密度スケーリング。本番は
   presence ローテーションで在場分布が変わるため、指数の絶対値はそのまま 25万へは持ち込めない。
   向き(超線形・悪化)は堅い。
3. **mock の行動分布アーティファクト**: mock は決定論スタブなので発話・投稿の中身はリアルでないが、
   **step の計算量(移動・知覚・順位付け・記録の回数)**は config と在場数が支配するため、非LLM
   単価の測定としては妥当(calibration-toolkit の「機械系は mock で十分」と同じ立場)。
4. **選挙フォールバック**: §1 の from_roster 未投入により議会が選挙機構で回る現況を含む。稀イベント
   ゆえ step 支配項ではないが、P5 で議員名簿を投入後は再測が望ましい。
5. **観測 I/O は含まない**: c は RAM バッファへの記録までで、parquet 書き出し/スナップショット JSON 化
   の破綻(scale-feasibility §4.3・P4 の対象)は別軸。step ループの単価のみを測っている。
