## どんなシムか

2 次元グリッド上に収容上限つきの「場所」(既定は左右のバー各 1、capacity 12 / 10)を配置し、LLM エージェント群(20 体)が活動する。途中で火災イベントが指定ステップに発生し(fire_1: step 15、intensity 0.8、radius 15 / fire_2: step 40、intensity 0.5、radius 8)、知覚半径内のエージェントにだけ**位置・強度・半径・距離という定量情報のみ**が配信される(知覚モデル B = 距離依存、半径外は `None`)。「危険」「避難せよ」といった定性的記述・行動指示は一切与えない。エージェントは毎ステップ LLM で Message / Memory / Action を生成し、4 方向移動＋滞在の離散行動と近傍へのメッセージ送信を同期実行する。通信は通信半径内かつ「**両者とも場所外**」または「**両者とも同じ場所内**」でのみ成立し(異なる場所間・場所内外は不可)、場所内エージェントだけが占有率を直接受け取る。この構造が情報非対称性を機械的に生む。Memory フィールドは LLM 自身が書いた内容が次ステップの `Previous Memory` として自己フィードバックされる。

## 講評の要点

### 強み(A9.0 / D9.0 の理由 = 本チーム最大の学習対象)

**A. 創発設計 9.0 の根拠**(講評が挙げた 7 点):
- `agent.py` の `fire_entry` テンプレが `Position / Intensity / Radius / Distance` **のみ**。定性的形容詞ゼロ。
- `place_status_template` も `Number of agents here / Capacity / Occupancy rate` のみ。
- `_build_fire_section` のコード内コメントに「Only quantitative data is provided ... No qualitative descriptions」と**明記**されている(= 設計思想がコード内に自己文書化されている)。
- `get_fire_info_for_agent` は知覚半径外に `None` を返す(Model B)。
- `get_nearby_agents` の通信ルールが「両方とも場所外」or「同一場所内」のみで成立。
- README に「生の数値データのみを提供し、行動指示や定性的評価(「危険」「快適」等)は一切与えない」と宣言。
- 観察ログで「Agent 0 が intensity 0.8 を自発的に "manageable" と再解釈」= 規範の逸脱の正常化の実証。

講評は「行動空間(move/stay × 4 方向、任意メッセージ、自由形式メモリ)は完全に開かれており、戦略は LLM に完全委任」「情報の非対称性という強い創発トリガを**構造的に**作っている」と評価。**ルーブリック A の最高帯「9-10 precise + raw data」に該当**する条件は「世界ルールの精度が高い」×「行動自由度が高い」の**両立**であり、片方だけでは 9 に届かない(→ 姉妹リポの A4.0 と対照)。

**D. 技術実装 9.0 の根拠**:
- **2 フェーズプロンプト分割**: Phase 1(メッセージ決定、**位置情報を渡さない**)と Phase 3(行動決定、位置情報あり)を分離。メッセージ生成時に座標を見て「先回りした計算結果」を漏らすことを防ぐ。講評が「秀逸」と名指しした工夫。
- JSON 固定スキーマ + ネストブレース対応・文字列内ブレース無視・エスケープ対応の堅牢な抽出器、失敗時は方向キーワードのフォールバックパーサ。
- 小型 LLM 向けサンプリング調整(temperature 0.2 / repeat_penalty 1.1 / min_p 0.05 / repeat_last_n 128)。
- メモリ: `memory_limit`(保存上限)と `memory_size`(プロンプトに使う直近件数)を**分離**、`message_history_limit` と `message_context_size` も独立。受信メッセージは送信元 ID つきで `from Agent X: ...` 形式に整形。「単なるログダンプではなく、エージェントが内省的に書き直した記憶が次ステップの推論を駆動する」。
- 厳密な 4 フェーズ同期実行(メッセージ決定 → 送信 → 行動決定 → 移動)で順序の意味がコメントに明記。
- `output/messages.jsonl` と `output/memory_reasoning.jsonl` の一次データ体系的ロギング。

### 弱み

- **B 7.0**: 「2D フィールドに複数のバー + 火災」は災害シムの一典型で独創性は中庸。場所の `type`(bar/cafe/library)は**文字列ラベルのみで type 固有の機能差が未実装**。「これは何の現実問題のミニチュアか」(避難訓練設計、SNS デマ拡散、商業施設の混雑制御 等)の対応関係が README にない。
- **D の減点 -1**: **乱数シードを固定する仕組みがない**(`config.yaml` に `seed` キーなし)。同一条件 3-run でも発話量が 1390 → 756 → 996 と大きく揺れる。**テストコードが同梱されていない**。
- **C の指摘**: 日本語切替は `agent.py` に大きな辞書を追加する後付けハックであり、「拡張点として設計された」ものではない。ビジネス・社会科学へのマッピング構想まで踏み込んでいない。
- 講評の改善提言: fire_2 は半径 8 では知覚エージェントが少なすぎる → 「目視は近距離だが煙は遠距離まで届く」など**知覚モデルの多層化**を提案。

### `_eval_review` 所見

**総合判定「支持」・スコア修正不要**。引用された行範囲は最大 4 行程度のズレがあるが対象関数・テンプレ・コメントはすべて実在し、README 引用 3 箇所は逐語一致、観察ログの語彙統計(634/584/477/443)と発話量(1390→756→996)も該当ファイルに完全一致で存在。冒頭の責任分界注記(原作 = 兵頭氏、追加 = Su 氏)は「ハッカソン提出物の特殊な性質を評価する上で重要な透明性を確保している」と評価された。唯一の留保は C について「`PROMPT_TEMPLATES` 後付けは拡張点として設計されたものではなく制約下でのハック」だが「`simulation.py` 不変で実現できた事実は拡張性の十分な間接証拠」として 8.0 を支持。

## コード実査で面白かった点

1. **「数値のみ」原則がテンプレ単位で機械的に守られている**。設計思想を README のポエムで語るのではなく、プロンプト断片テンプレートという**最小単位に落とし込み**、その隣のコメントに「No qualitative descriptions are included」と書いてある。審査者が根拠として引用しやすい形になっており、A9.0 の直接原因はこの**引用可能性の設計**にある。

2. **Phase 1 で位置情報を意図的に渡さない**。会話フェーズで座標を与えると LLM は「(15,10) から離れるべき」という計算結果をそのまま喋ってしまい、情報伝播が「計算の共有」に堕する。位置を隠すことで、何を共有するかが LLM の内部知識と記憶に依存するようになる。**情報伝播を観察したいなら、伝播元に答えを持たせてはいけない**という一般則。

3. **通信可能条件の代数的単純さ**: 「両方とも場所外」or「同じ場所内」。この 2 条件だけで、(a) 屋内外の情報遮断、(b) 場所どうしの情報遮断、(c) 場所が情報のサイロになる、という 3 つの社会的性質が同時に立ち上がる。ルールの少なさに対する創発の多さの比が高い。

4. **`memory_limit` と `memory_size` の分離**(および `message_history_limit` / `message_context_size` の分離)。「保存しておく量」と「毎回プロンプトに載せる量」を別パラメータにするのは地味だが、長期保存と短期参照を独立に掃引できる = **メモリ実験の設計変数が 1 個増える**。

5. **観察レポートの規範「実データに書かれた文字列のみを引用」**。Su 氏の `SUBMISSION_*.md` は語彙出現数の生カウント表(火災 1682 / 安全 1551 / 危険 376 / 避難 26 / 探索 1107 …)と、`grep` してヒット 0 件だった項目(`fire_2` / `(-10,-10)` / `0.5` / `第二` / `二つ目` が 3 run すべてで 0 件)を**両方**書いている。**否定的結果を明示的に記録**する姿勢。

6. **同一条件 n=3 で「別々の共有現実」に分岐した記録**(`SUBMISSION_ja_d50_qwen25_7b.md` §5):
   - run 1 → 「小さな窓」147 / 「音楽」253 / 「静かな」395 という空間ディテールの共有
   - run 2 → step 9 に agent 15 が右バーに「大きな舞踏場」「秘匿性の高い個室」があると語り、それが後続の記憶・推論に残った(舞踏場 65 / 個室 68)
   - run 3 → 「出口」634 / 「消防」584 / 「煙」477 / 「温度」443 / 「視界」451 という**プロンプトに存在しない防災チェックリストの創発**

   これは**幻覚(hallucination)が単発のエラーではなく、会話を通じて集団に定着し共有現実になる**過程の一次データである。しかも同じ config・同じモデルで 3 通りに分岐した。

7. **モデル横断の観察軸テーブル**(§6): 「発話量 / 火災認知 / 共有フィクション / 反生存クラスタリング / fire_2」の 5 軸 × 2 モデル(qwen3:4b vs qwen2.5:7b)の比較表。qwen3:4b は「心の鏡・呼吸・スカーフ・報酬」という詩的/ゲーム的フィクションに、qwen2.5:7b は「バー内部構造・防災設備」という実務的フィクションに向かう、という**モデル別の創発の質の違い**を記述している。

8. **「反生存的クラスタリング」という現象名**: qwen3:4b の run 2 で、火災半径内に入る right_bar に 7 名が集まった。逃げるどころか危険源に集合する。qwen2.5:7b では最大 2 名で再現せず。

9. **改変制約を自分に課してから拡張する作法**(`PROMPT_LANGUAGE.md`): 着手前に「既存 config.yaml は 1 バイトも変更しない」「simulation.py / ollama_client.py / visualization.py は触らない」「未指定時は英語にフォールバック」「英語モードの出力はバイト単位で既存と一致させる」の 4 制約を宣言し、最後に `git diff config.yaml simulation.py ollama_client.py visualization.py` が空を返すことを検証結果として掲載。**制約 → 実装 → 検証コマンドの出力**という順で書かれており、講評が「拡張容易性の実証」として加点した。

10. **多言語プロンプトの構造ルール**: プロンプトの自然言語部分だけを差し替え、JSON のキー名(`message` / `reasoning` / `action` / `direction` / `memory`)と `direction` の値(`up`/`down`/`left`/`right`)、数値フォーマットは**全言語で英語固定**。日本語プロンプト内の引用符は半角 `"` のみ(JSON 構造を壊さないため)。これにより言語を変えてもパーサは一切変更不要。

## shibuya-simulation に活かせそうな点

- **A9.0 の再現条件は「世界ルールの精度」×「行動自由度」の両立**。姉妹リポ(A4.0)との対照から、片方だけでは半分以下に落ちることが実証されている。shibuya-simulation の no-fingerprint 原則は正しい方向だが、**それがコード内の最小単位(プロンプト断片テンプレート)で引用可能な形になっているか**を点検する価値がある。審査者は README の宣言ではなく `agent.py:50-56` を引用してスコアを付けている。

- **プロンプト断片の隣に設計原則コメントを置く**。「Only quantitative data is provided. No qualitative descriptions are included.」という 2 行が A9.0 の根拠 3 番目として引用された。shibuya の観測分離・no-fingerprint も同様に、該当箇所へ**根拠コメント**を置けば審査者が引用しやすい。

- **フェーズ分離による情報漏れ防止**は shibuya のラベル伝播研究に直結する。発話生成フェーズで「その語がどこから来たか」「誰が知っているか」の内部状態を渡していないか点検すべき。渡していると、伝播ではなく**全知の共有**を観測してしまう。

- **語彙出現数の生カウント表**は、shibuya のラベル伝播計測の最も安価で説得力のある提示形式。「プロンプトに存在しない語が集団に定着した」ことを、grep カウント + ヒット 0 件の否定リストで示せる。shibuya には既に `coin_label` 観測があるので、この**提示形式**を輸入できる。

- **同一条件 n=3 の分岐記録**は、shibuya の R²(k) 掃引において「決定論的でない部分がどれだけあるか」を正直に示す手段。shibuya は CRN + ゴールデンテストで決定論を確保しているが、**LLM 温度を変えた n 反復での分岐幅**を 1 表で示すと、k* の推定に伴う不確実性の記述が強くなる。

- **否定的結果の明示記録**(fire_2 語彙 0 件、`grep` した 5 語すべて 0)。shibuya の devlog プロトコルと相性が良い。「観測されなかったもののリスト」を成果物に載せるのは、捏造禁止規範の可視化としても効く。

- **知覚モデルの多層化**(講評の提言): 「目視は近距離だが煙は遠距離まで届く」= **同じ事象に複数の到達距離の異なるチャネルを持たせる**。shibuya の噂/ラベル伝播に応用すると、「直接目撃(近距離・高信頼)」「SNS(遠距離・低信頼)」「口伝(中距離・減衰)」の 3 チャネルを同一事象に張れる。

- **`memory_limit` / `memory_size` の分離**を shibuya のメモリ設計でも掃引変数として扱えるか点検する価値がある。

- **多言語プロンプトの構造ルール**(JSON キーと列挙値は英語固定、自然言語部分のみ差し替え、半角引用符のみ)は shibuya が日本語舞台である以上そのまま使える実務知見。

- **審査対策**: B の減点理由「これは何の現実問題のミニチュアかの対応関係が README にない」は shibuya にも該当しうる。渋谷という舞台が**何の一般問題の縮図なのか**(都市の情報伝播、組織の自然形成、規範の創発)を README 冒頭に明示すると B が上がる。

- **反面教師**: シード固定なし・テストなしで D が -1 された。shibuya は決定論/ゴールデンテストを既に持っているので、これは**明示的にアピールすべき差別化点**。
