## どんなシムか

AGI が社会実装された近未来の労働市場を扱う **Web キャリアシミュレーター**。シード連動乱数で 100 人の仮想プロフィール(21 職種 × 11 業界 × 年齢 × 7 スキル軸)を生成し、定型業務性・身体性・資格依存度・人間的要素などから「AGI 適応力スコア」と「代替リスクスコア」を決定論的な加重和で算出、`resilient` / `transforming` / `vulnerable` の 3 類型に分類する。ユーザーが AGI 進展度スライダー(Low/Medium/High)を動かすと `AGI_LEVEL_MULTIPLIERS` により分布がリアルタイムに変化する。個人をクリックすると NVIDIA NIM API(Llama 3.1 70B)が「会社側の評価・本人の内心・やりたいこと・今後のアクション・発言」を 1 回だけ生成する。「なにわ男子」風の固有ペルソナ(道枝駿佑(風)・大橋和也(風))も混ぜてある。

## 講評の要点(なぜ減点されたか)

**A=2.0。担当 6 チーム中の最低点(meta-pop-agent を除く)。理由は一行で言える——シミュレーションが存在しない。**

講評:「本作には**シミュレーションループ、エージェント間相互作用、メモリ、時間発展のいずれも存在しない**」「エージェントは世界を観測したり他者と通信したりしない」「LLM はテキスト整形器として機能している」「設計上、集団的創発が起こる余地が構造的に無い」。

- `src/app/api/agent/route.ts:31-53` のプロンプトは「以下の 6 点を出力してください ①現在のステータス…②会社の評価…③本来やりたいこと…④これからのアクション…⑤思考…⑥発言…」と**出力項目を完全指定**。返る JSON は `status`/`company_decision`/`what_i_want_to_do`/`future_plans`/`thoughts`/`dialogue` の固定フィールドで、行動選択の自由度がゼロ。
- LLM 呼び出しは `messages: [{role:'user', content: prompt}]` の単発。履歴もメモリも渡らない。
- `src/lib/scoring.ts` の `scoreProfiles` は純粋な決定論的加重和で、**LLM の出力は分類に一切影響しない**(一方向の従属関係)。つまり LLM は結果に対して読み取り専用のナレーターであり、世界に作用しない。
- README にはエージェント同士の対話・観測・行動選択の記述が皆無。「LLM がリアルタイムに生成してロールプレイを行います」とあるが、**ロールプレイ=ナレーション生成であり、世界に作用しない**(講評の指摘)。

**D のメモリ項目は実質ゼロ**。`ProfileDetail.tsx:39` の `const agentCache: Record<number, AgentData> = {};` はモジュールスコープの揮発キャッシュで、重複呼び出し回避以上の意味がない。_eval_review の内訳推定では **Mem(3点満点)= 0.5**。

**C=5.0**: コード拡張性は良好(`OccupationConfig` に 1 要素追加すれば新職種が型安全に増える、`SCORING_WEIGHTS` に係数集約)。しかし README に「**LLM ハッカソンなどの発表用モックアップとして作成されました**」と用途を自ら限定し、**将来構想セクションが存在しない**。設定は全て TypeScript リテラルで外部設定ファイル(YAML/JSON)なし。

**_eval_review 所見**: 「元評価の結論(『フロントエンドモックとしては高品質だが、マルチエージェントシミュレーションとしては構造的欠落』)は完全に裏付けられた。合計 19.5 点はソースの実態に対し妥当」。読み違い・捏造は検出されず。注意点として「**3 回実施予定が 2 回で打ち切り**(Run3 が `-` のまま)」を挙げるが、ばらつきが小さく結論は変わらないと判断。

講評の一言コメント:「ハッカソンモックとしてのフロントエンド完成度とテーマ性は高いが、『マルチエージェントシミュレーション』という評価軸では構造的に不足が大きく、**現状は LLM 駆動の動的ペルソナ可視化ダッシュボードと位置付けるのが正確**である」。

## それでも光る点

1. **プレゼン資料の完成度が担当 6 チームで断然トップ**。7 ページの完全なピッチデッキ形式(HACKATHON PITCH → PROBLEM 02/07 → SOLUTION 03/07 …)。ダークテーマ・アクセントカラー・ページ番号・フッターの英語キャプション("Problem framing: abstract, static, emotionally flat"、"Core value: macro trend + micro narrative in one screen")まで統一されている。**プロダクトピッチとしては本ハッカソンで屈指**。

2. **問題設定のフレーミングが的確**。PROBLEM ページの 3 点:
   - 「誰が危ないのか見えない」— 職種レベルの議論は多いが、年齢・スキル・業界まで落ちた個人の解像度が足りない
   - 「変化の途中を試せない」— AI が進んだらどう変わるか、スライダーのように操作して比較できる体験がほとんどない
   - 「数字だけでは切実さが弱い」— リスクスコアだけでは、人事評価や本人の焦りまで伝わらず、記憶に残りにくい

   キャッチコピー「**抽象的な AI 不安を、操作できる未来シミュレーションへ**」「今の議論は『社会の話』で止まりがち。このプロダクトは『あなたの未来』まで落とし込む」。

3. **「マクロ分布 + ミクロの語り」を 1 画面に同居させる価値提案**(スライドのフッター "macro trend + micro narrative in one screen")。100 人の散布図(集団の傾向)と、クリックした 1 人の内心・発言(個人の語り)を同時に見せる。**統計と生の声を同じ画面で往復させる**のは、シミュレーション成果の提示形式として非常に強い。

4. **API キー未設定時のモックモード**。両 API ルートに `isMock` 分岐があり、スライドにも「**モックモードでもそのままデモ可能**」とバッジが立っている。講評も優れている点に挙げた:「評価者やデモ環境での動作確認を容易にする**実務的配慮**」。審査員が手元で動かせるかどうかは D と印象に直結する。

5. **シード再現性が実装済み**(`generateProfiles.ts` の `createRng`)。100 人の生成は決定論的で、同じシードなら同じ集団が出る。下位 6 チーム中、シードを明示的に実装しているのはこれと risk-gap の 2 つだけ。

6. **世界パラメータの設計が丁寧**。21 職種それぞれに `baseRoutineLevel`/`basePhysicality`/`baseCertificationDependence`/`hasHumanElement` と対応業界を割り当て、`AGI_LEVEL_MULTIPLIERS` で世界レベルの圧力(リスク倍率と適応力減衰)を定義。**世界側の圧力を 1 個のグローバル変数で表現し、それを動かすと全個体の帰結が変わる**という構造は、shibuya-simulation の k 掃引と発想が同じ。

7. **`scoreProfiles` が純粋関数、全ドメイン型を `types.ts` に集約、Next.js 16 / React 19 / TS strict**。コード品質(CodeQ)は _eval_review 推定で 1.8〜2.0 / 2.0 とほぼ満点。

## shibuya-simulation への教訓

- **⚠ LLM が世界に作用しないなら、それはシミュレーションではなくナレーション。** 本作の致命傷は「決定論的スコアリング → LLM が結果を語る」という**一方向の依存**。shibuya-simulation は LLM の行動が世界状態を更新するので構造的に安全だが、**この一方向性がどこかに紛れ込んでいないかは点検する価値がある**。具体的には「LLM 出力が次ステップの世界状態に到達する経路」を持たない LLM 呼び出し(例: 内省・要約・ラベル付けのみに使われる呼び出し)がどれか棚卸しし、**それが観測系なのか行動系なのかを明示的に分類してドキュメント化する**。観測分離の原則の説明としてもそのまま使える。
- **⚠ 出力項目を①〜⑥で完全指定するプロンプトは A を殺す。** shibuya-simulation も構造化出力(JSON スキーマ)を使う場面があるはずだが、**「何を出力するか」の指定と「何を選ぶか」の指定は別物**。前者(形式)は必要、後者(内容)は禁止。プロンプト監査では「形式指定と内容指定を分けてカウントする」観点を持つ。
- **⚠ README に「モックアップです」と書くと C の上限が決まる。** 自己限定の一文で将来展望が評価不能になった。渋谷側の README は逆に、**研究計画としての射程(k* 探索・相転移・組織創発)を最初の 10 行で言い切る**。
- **✓ モックモードは実装する価値が高い(D と印象に直結)。** API キー・GPU・LLM サーバなしで**リポを clone して即座に動く**経路があると、審査員が実際に触る。shibuya-simulation は既に mock backend を持っているので、**README のトップに「LLM なしで動くコマンド」を 1 行で置く**だけで効く。既存資産をアピールに変換する、コストゼロの得点源。
- **✓ 「マクロ分布 + ミクロの語り」を 1 画面に置く提示形式は真似する価値が高い。** R²(k) 曲線や KPI の集計値だけを出すより、**k* 付近の 1 個体の生ログ(発話・内省)を隣に並べる**と、「何が起きたか」が一目で伝わる。既存の viewer/HTML レポートに「この点をクリックすると、そのランのその個体の生ログが出る」導線を足すのは、実装量に対して説得力の増分が大きい。
- **✓ プレゼン資料の型: PROBLEM → SOLUTION → 機能 → 価値**。下位でもスライドの完成度だけは突出していた。8/30 提出のスライドは、**研究の内容(何を発見したか)とプロダクトの型(なぜ重要か)の両方**を持たせる。フッターに 1 行の英語キャプションを置くだけでも密度が上がる。
- **✓ 世界レベルの圧力パラメータ 1 個で全個体の帰結が変わる、を見せる UI**。`AGI_LEVEL_MULTIPLIERS` を Low/Medium/High で切り替えると分布が動く、というインタラクションは、**k を動かすと R² が動く**という渋谷側の主張の見せ方そのもの。**k スライダー付きのインタラクティブ結果ビューア**は、静的なグラフより圧倒的に伝わる(既存 `make_viewer` の拡張候補)。
- **審査プロセスの豆知識**: この評価は「実施回数 3 回」が規定なのに 2 回で打ち切られており、_eval_review がそれを注意点として記録している。**同じ提出物でも Run ごとに ±1 点は動く**(mars は A/B/D が同点で C だけ 6→5、agi は A/C/D 同点で B が 6→7)。1 点差を狙うより、複数評価者が確実に見る箇所(README・スライド・動くデモ)を固める方が期待値が高い。
