## どんなシムか

**品川駅周辺 160m × 160m の実在街区**を舞台に、「**企業協力型 学外教育プログラム**」を再現する。生徒 10 人(高校生版のほか社会人版・小学生版の 3 バリアント)と、品川駅周辺**実在 12 社の企業担当者ホスト**(人物設定は架空)が登場。

**3 フェーズ構成**:
- **Phase A(教室での座学・30 step)** — 品川の歴史・地形・再開発を学び、生徒は「品川の未来像」と「FW で確かめたいこと」を各自言語化する。
- **Phase B(品川駅前フィールドワーク・50 step)** — 111 places、`scene_3d`(roads / decks / stairs)、navigator による walkable mask 上で実際に歩き、企業担当者と対話する。必須 2 社訪問。
- **Phase C(シミュ後アンケート)** — 生徒 10 + 企業担当者 12 = 22 名にアンケート。**観察者 LLM が各エージェントの memory を読み、「この人物がアンケートにどう答えるか」を推測する**方式。

生徒ペルソナには **school_fit='不適応'(学校不適応)**、**mobility='wheelchair'(車いす利用)**、**nationality='western/asian'(外国籍 3〜4 名)** を必ず含める。研究上の問いは「多様な子どもたちの参加スタイルが成立する学習環境になっているか」「まちは知識を実感に変えるか」「企業対話は問いをどう深めるか」。

LLM は **Gemini 2.5 flash-lite**(`llm_client_factory` で Claude / OpenAI / Gemini を YAML から透過切替可能)。

## 講評の要点

### 強み

**B. 世界設定 9.0**(検証者は「やや過小評価気味、9.5 も許容」と上方修正を示唆):
- 実在の品川(旧東海道宿場、JR / 京急 / 新幹線の結節、リニア中央新幹線 2027 開業、TAKANAWA GATEWAY CITY 再開発、御殿山緑地、食肉市場)の歴史・地形・**進行中の再開発**を具体的な context として注入。
- **`perceive_pass` / `perceive_enter` を place ごとに 42 件記述**(検証者が実数を確認)。「横断歩道脇から見えること」と「中に入って気づくこと」を**分けて**事実ベースで書いている。
- 多様な生徒(不適応 / 車いす / 外国籍)を必ず含めることで「参加スタイルの差はどう生じるか」を直接モデル化。
- **検証者が指摘した加点漏れ**: README に明記されている**佐藤航陽氏(Singulab 代表)を「触媒人物」とする教室シミュの条件 A/B 比較設計**が講評に拾われておらず、B の独創性評価を押し下げている。

**D. 技術実装 9.0**(検証者「本ハッカソン提出群の中でも最上位」「9.5 も許容」):
- **Gemini CachedContent の hash ベース再利用**: `sha256(system_prompt)` を key にした **double-checked locking**。
- **structured output の自動選択**: `_pick_gemini_schema` が system_prompt に `action_type` があるかを見て message / message_with_memory / action のスキーマを自動で選ぶ。
- rate-limit 時の**指数バックオフ**(1→2→4→8s、`MAX_RATE_LIMIT_RETRIES=4`)。
- **truncation 検知**: `_is_truncated_response` がブレース不整合を検出し `MAX_RETRY_TOKENS=1500` で再試行。
- **3 層メモリ**: (1) `initial_memory`(Phase A からの handoff = 未来像 + FW 意図 + 確かめたい問い)を起動時 prepend、(2) rolling raw memory(`memory_size=5` / `memory_limit=20`)、(3) **`archived_summaries`**(5 step ごとに直近 5 件を LLM で 1 文要約して push、**固定保管で消えない**)。
- さらに `working_state`(現在進捗・未解決問い)を**別経路で system_prompt 末尾に固定挿入**し、rolling buffer の押し出しに依存させない。
- **ループ抑制の二段構え**: (a) per-partner 直近 3 発話履歴の可視化 + ⚠ 警告、(b) **Jaccard 4-gram 類似度 ≥ 0.50 の後フィルタで強制 silent 化**。
- `random.seed` + `np.random.seed` の**dual seed**、per-sink `threading.Lock` で JSONL 書き込み保護、`ThreadPoolExecutor` で `parallel_workers=16`。
- **7 系統の JSONL ログ分離**: messages / memory_reasoning / actions / should_speak_log / awareness_propagation_log / event_awareness_log / relationships_timeline。
- **behavior_layer**(transit / dwelling / interacting)判定で、transit 中は `cache_intent` を最大 5 step 再利用して LLM call を節約。

**C. 発展性 8.0**: LLM プロバイダ切替が `create_llm_client()` で透過的。`place_types.py` は registry pattern(dict 1 行追加で新 type)。`tools/` に 21 個のユーティリティ(config builder / persona generator / report renderer / 3D viewer bundler / scene exporter / survey runner)。**「Phase A 固定 → B, C 独立」のアーキテクチャ方針**(Phase A 出力を YAML として凍結し Phase B/C を独立に試行錯誤できる)を README に明示。

### 弱み(A6.0 — 担当群で 2 番目に低い)

講評は「世界ルール 8/10 × 行動自由度 4-5/10 のバランスで中位」と判定。減点根拠:

- **`_build_working_state_block` が毎 step user_prompt に注入する内容**: 「必須 N 社 / 未訪問の企業担当者リスト(max 6 件)/ まだ確かめていない問い(max 3 件)/ 終盤戻りリマインダ」。**やることリストを毎ターン突きつけている**。
- **`current_goal` の直接指示**: 「序盤(前半 30 step)は積極的に動いて広く歩き回ること」「同じ場所を何度も再訪することは避け」。
- **残り 5 step 以下で LLM 出力を無視**して `action_type='walk_toward'` / `target_place='東西自由通路'` に rule-based 強制上書き。
- **host(企業担当者)は Phase 3 を完全スキップし `action_type='stay'` 固定**(LLM call なし)。
- **`school_fit='不適応'` の persona には「自分からは話しかけない(挨拶も自発的にはしない)」と system_prompt に固定挿入**。
- 検証者の追加指摘: `simulation.py:1326-1346` に **host が学生近接していないと即 silent を返す追加 gate** があり、講評は未言及。
- 検証者の追加指摘: 「3 経路 awareness 伝播」のうち **Path 2(conversation)は coarse なキーワード一致のみ**(コード内コメントに "Deliberately coarse" と明記)であり、講評はこの限界に触れていない。

講評の提言が的確: 「これらを『**世界ルール側の制約**』(例: host は受付カウンタという物理的場所に拘束されるので動けない、終了時刻になったら帰る判断は agent 側に委ねる)として**表現し直す**と評価軸 A のスコアが伸びる」。さらに persona 属性については「『自分からは話しかけない』のような**対人行動指示**は、LLM が解釈で振る舞いを再生産する形に寄せられるとなお良い(例: **過去の対人成功体験の少なさを memory として与え、talkativeness 値だけを下げる**)」。

## コード実査 / 説明資料で面白かった点

### 1. 実装上の失敗事例カタログ「事象 A〜F」(本チーム最大の資産)

72 ページ資料の「やまちゃそ考察」に、**170 以上の試行錯誤(issue 検知 → 修正 → 再 smoke)**の末に観察された失敗モードが、**原因 → 対策案 → 副作用 → その後の検証結果**という 4 点セットで並んでいる。LLM マルチエージェントを作る者にとって実質的な**既知バグ一覧**。

| 事象 | 内容 | 原因 | 副作用つき対策 |
|---|---|---|---|
| **A** | Phase A で 1 度も発話できない生徒が出る(桜井さん = 30 step 全部で発話 0 件・memory ログ 0 件) | 確率ゲート(社交性 × 関係性 × 距離 × ブースト)で partner が決まらないと silent 確定。30 step 短期 + 教室密集で確率分布が偏り、**全 step 外す**ことが起きる | 強制割当を入れると**不適応 persona(silent でいたい)まで毎 step 強制発話**して persona 表現が壊れる。**構造的に未解決の残課題** |
| **B** | 話しかけたのに返ってこない — **Phase A 全 36 発話中 29 件 = 80% が「片想い」** | 4 重の構造的要因: ①双方向同時発話排除で id 大が silent → 翌 step で LLM が別話題に行く ②opener gate の確率 skip ③Jaccard ≥ 0.50 後フィルタで silent 降格 ④rolling buffer(直近 5 件)押し出しで「step N で何を聞かれたか」を忘れる | 閾値を緩めると同テーマ連投が増える。**未検証** |
| **C** | 後半で思考も移動も止まる(中島さんは reasoning に「東西自由通路に戻る」と書きながら **13 step 連続 stay**) | ①必須課題を完了すると**次の動機が agent から消える** ②「対話継続 vs 移動開始」の trade-off で stay を選びがち ③navigation で goal との距離が 1 step 移動量内だと `moved=0` になり実質その場停止 | 対策②③を強くすると「対話控えて移動」と LLM が学習し、**序盤から学生発話が激減する regression(大量沈黙化)**が出た |
| **D** | 企業担当者が持ち場を放棄(host 12 人中ほぼ全員が配置を離れ、中村は 27/50 step 移動。訪ねて来た生徒が会えない) | host も `decide_action` で walk_toward を選び、学生に応答するうち別の場所まで同行 | host 不動を強制したら「不在問題は解消したが**入口で固定される host と中の学生で会話が起きない**」という別課題が発生 |
| **E** | 双方向同時発話排除の副作用で**すれ違いが固定化**(篠田 → アンナは 3 回 partner 設定したが**一度も対話成立せず 0 回**) | 「双方向同時排除」と「opener gate」の組合せで「お互い相手を partner にしたが受信トリガー無しで両方 silent」状態が**ロック**。最初の opener が来ない限り stay が固定 | 「両方発言残し応答 step を 1 ずらす」に変えると同時発話の混雑感で turn-take が崩れる。**未検証** |
| **F** | 同じ人に同じテーマを繰り返す / 移動が片寄る | **LLM は自分の発話を内省できず、微妙な言い換えで同テーマを連投**(「品川って色々混ざってる感じ」を 5 step にわたり相手を変えて繰り返す)。移動は歩道制約で国道 15 号を渡れず東側歩道で詰まる | Jaccard 後フィルタが強すぎると**同テーマの深掘りまで silent 化**されてしまう |

**すべての対策案に副作用が明記されている**のが白眉。「直したら別のところが壊れた」を隠していない。

### 2. 事象 A〜F の根本原因を「アーキテクチャの問題」と診断している

資料はこう総括する — 事象 A〜F は突き詰めると「**各エージェントを 1 つの巨大な LLM プロセスでまとめて管理している**」ことに起因する。step ごとに全 agent の発話/行動を 1 つのオーケストレーターから並列に呼び出し、agent ごとの状態(記憶・関係性・直近受信)を user_prompt に毎回詰め直す構造では、**agent 個々が「自分の脳」を持って自律的に振る舞っているわけではない**。

具体的な副作用として:
- **記憶の押し出し**: rolling buffer からこぼれた記憶は 5 step ごとの圧縮要約に頼るしかない。個別 agent が「自分の文脈は自分で管理する」形になっていない。
- **turn-take の不自然さ**: 双方向同時排除や opener gate は、本来「相手が話したから自分も応答する」という**非同期メッセージング**で自然に解決するもの。全員を同 step で同期処理するアーキテクチャに「人間っぽい turn-take」を**後付け**しているため、片想い・すれ違いが構造的に残る。
- **silent 制御の二重化**: 確率ゲートと LLM 任せ判断が二重に効いて挙動が読みづらい。

提案されたネクストアクション: 各 agent が API 側でコンテキストを保持した独立スレッドを持つ構成(moltbook のような Discord 風チャンネル、あるいは **A2A プロトコル**による agent 間メッセージング)にすれば、事象 A〜F の相当部分が**アーキテクチャレベルで吸収される**。発話は「相手の Thread にメッセージを post」する非同期通信になり、同 step 制約が消える。

### 3. 観察者 LLM 経由のアンケート(Phase C)— 忖度バイアス回避

`tools/run_survey.py` は、エージェント本人に「あなたはどう感じましたか」と聞くのではなく、**観察者 LLM に agent の memory を読ませて「この人物がアンケートにどう答えるか」を推測させる**。講評が B の根拠として「(本人忖度バイアス回避)」と明記した。

**LLM に自己申告させると必ず肯定的に答える(sycophancy)**という問題への、実装レベルの回答。

### 4. `perceive_pass` / `perceive_enter` の二層記述

各 place について「**通りすがりに見えること**」と「**中に入って初めて気づくこと**」を分けて事実ベースで記述(42 件)。エージェントが場所の前を通っただけか、中に入ったかで**得られる情報が構造的に違う**。実在地点の知識を、知覚の粒度に対応づけて格納している。

### 5. awareness 伝播の 3 経路

`direct`(直接知覚)/ `conversation`(会話経由)/ `notification`(通知経由)。さらに **`phone_check_rate` で persona ごとに通知到達率を変える**。同じ出来事が 3 つの異なる経路で、異なる速度・異なる歪みで届く。

ただし検証者の指摘どおり **Path 2(conversation)は coarse なキーワード一致のみ**で、コード内に "Deliberately coarse" と自認コメントがある。**限界をコードコメントに書いている**のは誠実。

### 7. 3 視点の考察構成

**全体考察(シミュ結果ベースの観察)/ えびねこ考察(教育観点)/ やまちゃそ考察(シミュ実装観点 + まちづくり観点)** の 3 本立て。**同じ結果を、ドメイン専門家の目と実装者の目で別々に読む**という構成。チーム 2 名の役割分担がそのまま資料構造になっている。

### 8. 正直な失敗の報告(結果セクション)

- 必須拠点に「向かった」のに**一度も中に入れなかった生徒が 4 名**(中島・西野・アンナ・リー)。アンナは 2 拠点とも入れず。
- これを「バグ」ではなく「**まち側の受け入れ体制や物理的アクセスの課題**」として読み替え、教育・まちづくりの知見に転化している。
- 結論も抑制的: 「まちは知識を実感に変える学習環境になり得る手応えが得られた一方で、**『自分もまちに関われる』という主体感までは届ききらず、観察者ポジションに留まる場面が残った**」「**多様な生徒を配置するだけでは多様な学びにはならない**」。

### 9. まちづくりへの応用構想

「デジタルツイン上で**そのまちが完成する前に**ユーザーの声を拾う」。多様な persona を再開発計画地の上で動かし「**誰がどこで詰まるか / 誰が来ないか / 誰の動線が交差しないか**」を計画段階で可視化する。計画案 A / B / C を**同じ persona セット**でシミュレートして「どの案が誰にとって過ごしやすいか」を比較定量化する。**ボトムアップ型都市計画**の素材提供。

## shibuya-simulation に活かせそうな点

### 最優先 — 失敗事例カタログを予防的に使う

shibuya-simulation は屋内 SFM 人流・会話・関係性内生化を持つので、**事象 A〜F はほぼそのまま起こりうる**。特に:

- **事象 A(発話ゼロ個体)**: 確率ゲートで partner を決める設計だと、短期 × 密集で「全 step 外す」個体が出る。shibuya の会話相手選択にも同型のリスク。**「N step 連続で発話 0 の個体数」を L2 指標として常時監視する**だけで検出できる。
- **事象 B(片想い 80%)**: 発話が返ってこない構造的要因が 4 つ重なる。shibuya のラベル伝播で「語が伝わらない」原因が**伝播の失敗ではなく turn-take の失敗**である可能性を常に疑うべき。**「発話 → 応答」成立率**を計測指標に入れる価値が高い。
- **事象 C(目標消尽後の停滞)**: 予定を達成した後に動機が消え stay を連発する。shibuya の日次計画/予定帳簿で**「今日の予定を終えた後の行動」が空白になっていないか**点検。reasoning には「移動する」と書きながら実際は動かない**発話と行動の乖離**も、ログ突合で検出できる。
- **事象 E(相互 silent のデッドロック)**: 双方向排除 + opener gate の組合せで、**両者が相手と話したがっているのに永久に話さない**状態がロックする。shibuya の joint/invite 機構に同型のデッドロックがないか要点検。
- **事象 F(LLM は自分の発話を内省できない)**: 微妙な言い換えで同テーマを連投する。**shibuya のラベル伝播研究にとって致命的**— 「同じ語が繰り返し出現した」のが伝播なのか単なる LLM の反復癖なのかを区別できないと、伝播率がまるごと汚染される。Jaccard 類似の後フィルタは有効だが、**強すぎると深掘りまで消す**という副作用も報告されている。shibuya では**フィルタで消すのではなく、反復を反復として計測して伝播カウントから除外する**方が観測分離の原則に合う。

- **副作用まで書く作法そのものを輸入する**。shibuya の devlog は既に詳細だが、「対策 → 副作用 → 未検証/検証済み」の 3 点セットで残すと、後から読む自分と審査員の両方に効く。

### アーキテクチャ上の論点

- **同期 step × 単一オーケストレーター vs エージェント別非同期スレッド**という論点は、shibuya にとっても本質的。ebiyama チームは「turn-take の不自然さは後付けでは解けない、非同期メッセージングが構造的な解」と診断した。shibuya は決定論・CRN・ゴールデンテストを重視しており、**非同期化は決定論と真っ向から衝突する**。ここは shibuya が意識的に**別の道(同期 + 決定論を守る)を選んでいる**と位置づけ、その代わりに turn-take の不自然さをどう抑えるかを明示できると、設計判断として強い。**トレードオフを自覚して選んでいることを書く**のが審査でも効く。

### 観測設計

- **観察者 LLM 経由のアンケート**は shibuya にそのまま輸入すべき。shibuya は既に sycophancy 対策を意識しているが、**「本人に聞かず、ログを読んだ第三者 LLM に推定させる」**という具体的手段は、内省・満足度・態度の測定すべてに使える。しかも「本人忖度バイアス回避」という一言が講評の加点根拠になった。
- **`perceive_pass` / `perceive_enter` の二層知覚**は shibuya の屋内/屋外・POI 設計に直結。「前を通っただけで得られる情報」と「入って初めて得られる情報」を分けると、**移動が情報獲得の意味を持つ**ようになる。現在の shibuya が場所に入るか否かで情報差を作っていないなら、低コストで大きな効果。
- **awareness 伝播の 3 経路(直接 / 会話 / 通知)+ persona 別の通知到達率**。shibuya の噂/ラベル伝播に「SNS 通知をどれだけ見るか」の個人差を入れると、同じ情報が個体ごとに違う経路で届く。Alberia の `spread_radius` / `online_reach` 分離と組み合わせると強い。
- **7 系統の JSONL ログ分離**。特に **`should_speak_log`**(発話しようとして発話しなかった記録)と **`awareness_propagation_log`**(誰が誰から何を知ったかの辺リスト)は shibuya の伝播研究にそのまま要る。**「発話しなかった」を記録する**のは事象 A の検出に必須。

### 技術・コスト

- **prompt caching の効かせ方**: system_prompt に静的部分を集約し user_prompt に動的部分を分離、`sha256(system_prompt)` を key に double-checked locking で CachedContent を再利用。Phase B で **cache hit 81.4%**、cache_read は input の 1/4 価格。shibuya は本番で大規模・長時間を想定しているので、**キャッシュ hit 率を L2 指標として計測する**価値がある(ebiyama は phase ごとに hit 率を実測公開している)。
- **truncation 検知 → トークン増で再試行**(ブレース不整合を検出し `MAX_RETRY_TOKENS=1500`)。JSON が途中で切れる事故への実務的対処。
- **behavior_layer による LLM call 節約**: transit(移動中)は意図を最大 5 step キャッシュして LLM を呼ばない。**「呼ぶ回数を減らす」最適化だが、判断をルールで代替していない**(移動中は前の意図を継続するだけ)ので、A を毀損しにくい形の最適化。姉妹リポの反面教師(ルールで判断を代替して A4.0)と対比すると、**安全な最適化と危険な最適化の境界**が見える。
- **dual seed**(`random.seed` + `np.random.seed`)。shibuya は既に決定論を持つが、numpy 側の seed 漏れがないか点検の価値。

### 反面教師 / 審査対策

- **A6.0 の原因は「毎 step の TODO リスト注入」**。`WORKING STATE` ブロックで「必須 N 社 / 未訪問リスト / 残り step / 終盤戻りリマインダ」を毎ターン渡すのは、進行を保証するには有効だが**行動の scaffolding**として減点された。shibuya の日次計画/予定帳簿が、**エージェント自身が作った計画を見せている**のか、**環境が指示を出している**のかを区別して書く必要がある。前者なら創発、後者なら指紋。
- **persona 属性の与え方**: 「不適応だから自分からは話しかけない」と**行動を直接指定**すると減点される。講評の代案が具体的で優秀 — 「**過去の対人成功体験の少なさを memory として与え、talkativeness 値だけを下げる**」。**属性 → 行動の対応づけを LLM の解釈に委ね、環境は履歴とパラメータだけを渡す**。shibuya のペルソナ設計にそのまま適用すべき原則。
- **「host は動かない」を強制する代わりに「受付カウンタという物理的場所に拘束される」と世界ルールで表現し直せ**という講評の提言は、**行動制約を物理制約に翻訳する**という一般技法。shibuya で「店員は店から出ない」を実装するなら、prompt で禁じるのではなく**勤務中は移動可能領域が店舗内に限られる**と世界側で表現する。
- **限界をコードコメントに書く**("Deliberately coarse")。検証者はこれを見つけて「限界に触れていない」と講評の側を批判した。**正直な自己申告は評価者に発見され、加点方向に働く**。
- **B の加点漏れ(佐藤航陽氏を触媒人物とする条件 A/B 比較)**が検証者に指摘された。**やった実験は README で明示的に見出しを立てないと拾われない**。
