## どんなシムか

「2D 火事シミュレーションのベースコードを起点に、**『火』と『避難』を取り除いた**」(スライド)作品。残ったのは春の公園・散る桜・3 体の存在だけ。エージェントは 3 体のみ:

- **いち子** = 言葉を持たない「現象」。message も reasoning も必ず空文字、memory に体の物理変化だけを 2〜3 語(「指先、止まる。」)。
- **犬** = 匂いと温もりだけの「本能」。reasoning はひらがな 3 語以内、論理語は禁止。
- **観測者** = ベンチに座る「人間的回路」。二者の交差を詩として記録する。

qwen2.5:3b(Ollama ローカル)で 30 step 動かし、step 29 で観測者 LLM が全記録を **起承転結 4 幕の英文シネマプロンプト**(Yugen / Wabi-sabi 指定)に変換する。これが「作品」。研究シミュレーションというより **LLM 参加型の映像詩**。

## 講評の要点(なぜ減点されたか)

**A=3.0。減点理由が本グループで最も教訓的——README と実装が正面から矛盾していることを審査員に発見された。**

README 冒頭(概要):
> エージェントには生の数値データ（占有率、火災の強度・距離等）のみを提供し、**行動指示や定性的評価（「危険」「快適」等）は一切与えない**。

同じリポの `config.yaml`(犬ペルソナ):
> においがするかぎり、北（up）へ一歩あるけ。**actionは "move" + "up" を選べ。**

観測者ペルソナ:
> **4. actionはstayのみ。**

講評の根拠欄はこれを直接並べて書いている:「README.md — "…行動指示や定性的評価は一切与えない" と謳うが、**実コード/Config はこれと矛盾**」。

さらに三重の行動制御が重なる:
1. **ペルソナで行動を直接指定**(上記)。
2. **コードで LLM 出力を無視して強制**。`agent.py:892-904` の `parse_action_response` は `id==0`(いち子)なら LLM が何を返しても `{"action": "stay", "direction": None}` を返す。`simulation.py:321-329` は id=0 を桜の木の中心に、id=1 を (0,-4) に固定配置。
3. **200 行超の出力フィルター層**。`_purify_reasoning`(agent.py:531-697)+ `_clean_memory`(699-748)= 実測約 215 行に Phase 15〜Phase 44 の ad-hoc 正規表現(50+ パターン)が積層し、LLM の出力分布を強制的に狭める。`_filter_dog_message` は犬が人間語を喋ったら切り落とす。

加えて **README の「定量情報のみ」原則も実装で破られている**: `_compute_sensory_data`(agent.py:275-327)が「ほとんど感じない」「かすかに感じる」「強い」という**定性ラベルを生成してプロンプトに渡している**。しかも `if self.id == 1` で犬専用の温もり/重さ計算が分岐している。

そして **`config.yaml:17` が `fires: []`**。README とデモ動画が売りにしている火事の「知覚モデル B」は精密に実装されているのに、提出 config では一度も発火しない。講評:「火事の Model B 知覚は精密実装だが、`fires: []` のため未起動」。

講評の一言コメント:「『LLM マルチエージェントを使った映像詩』としては独創的で完成度が高い一方、ハッカソンが想定する『LLM の自律性から創発を観察する』基準では、**世界設計の精度がペルソナとフィルター層の行動制御で大きく相殺されており**、創発設計のスコアが伸びにくい構成になっている」。

**C=4.5**: `if self.id == 0/1/2` 分岐が至る所にあり、新エージェント追加に全箇所修正が必要。README に places 拡張例(cafe/library)はあるが、**Future Work 節がない**(_eval_review が追加指摘)。テスト・CI・シード管理の計画もなし。

**D=6.0**: JSON の brace-matching 抽出、画像プロンプトの品質チェック+3 回リトライ+違反フィードバック注入、観測者専用 LLM クライアントの分離は平均以上。一方 `random.seed` はプロジェクト全体で未使用(初期位置が毎回ランダム)、agent.py 1060 行・simulation.py 951 行でテスト・型チェックなし。

**_eval_review 所見**: 20.5 を妥当と確定。「元評価は引用精度・指摘方向ともに非常に高水準」。誤りは行番号の軽微なズレ 3 件のみ(`config.yaml:64,68` の引用にいち子ペルソナ 37 行の文言が混在、`_run_image_prompt_generation` の開始は 421 行、`_generate_initial_positions` の開始は 265 行)。「結論への影響はゼロ」。

## それでも光る点

1. **世界設定 B=7.0 は本グループ最高タイ**。「春の公園、最古の桜、散る花びらの境界の時間」に「不動の現象=いち子」「本能=犬」「観測者=詩を打つ存在」のトライアドを配する構成は、避難デモ一色のハッカソンで完全に浮いている。Yugen / Wabi-sabi の明示、Wong Kar-wai 風のシーン定義("The Ghost Stirs"、"Language Dissolves")。**題材の差別化だけで B は 7 点取れる**という実証。

2. **「削る」ではなく「そもそも存在しない」という設計転換**(Phase 41)。スライド:「犬の memory フィールドが汚染され続けた理由は、**ペルソナに memory の定義がなかったから**でした。フィルターを足すのではなく『**犬に memory は存在しない**』と設計し直しました」。**出力を後段で削るのではなく、そもそも生成する必要のない構造にする**——フィルタが 200 行に膨れた本人が到達した、正しい方向の反省。

3. **「体験から作品を自律生成する」という問いの立て方**。スライド:「LLM は『問いに答える道具』として使われています。しかし、**体験し、感じ、そこから何かを作る存在**として使ったとき、何が起きるか」。30 step の経験を起承転結 4 幕に変換するパイプラインは、**シミュレーションの出力を集計値ではなく作品にする**という珍しい発想。

4. **意図と違う出力を受け入れた宣言**。「4 枚の画像プロンプトにも、いち子と犬が出たり出なかったりする瞬間がありました。ただ、それも含めてエージェントの自律的な動きを優先しました。**自分の意図とは違う出力であっても、それがエージェントが自律的に選んだことであれば、それでいい**と判断しました」——結果的にはフィルタで縛っていたので実践できていないが、姿勢としては正しい。

5. **「花びら、膝。」**——30 step 中に一度だけ出た言葉。「説明も、文脈もない。ただ、情景が浮かびました」。**低頻度の 1 回を成果として提示する**姿勢は、shibuya-simulation の natural-coinage 観察と発想が同じ。

6. **「汚染か、創発か。」**——qwen2.5:3b が感情的に高まり突然中国語(母語)を漏出した瞬間について、「フィルターで弾くべきバグなのか、それとも『AI が初めて自分の言葉で叫んだ瞬間』なのか——**この問いはコードの外にあります**」。観測対象とノイズの境界が原理的に決められない、という観測分離の核心を突いた記述。

7. **画像プロンプトの品質チェック+リトライ+違反フィードバック注入**(`simulation.py:568-607`)。LLM 出力を検証し、違反内容をフィードバックして再生成させる 3 回ループ。LLM 出力の品質ゲートとして素直に使える型。

8. **メモリの保存量と参照量を分離**(`memory_limit` vs `memory_size`、`message_history_limit` vs `message_context_size`)。これはベーステンプレ由来だが良い設計。

## shibuya-simulation への教訓

- **⚠⚠ 最重要: README の主張と実装が矛盾していると、審査員はそれを減点根拠として名指しで引用する。** 本チームは「行動指示は一切与えない」と書きながら config に「actionは "move" + "up" を選べ」を置き、A=3.0 になった。**shibuya-simulation の no-fingerprint 原則はまさにこの形の主張**であり、同じ検査を受ける。対策は 2 つ:
  1. **主張を機械検査可能にする**。「プロンプトに入る全文字列に行動指示・定性評価語が含まれない」ことを **テストとして実装し、テスト名とパス結果を README に載せる**。既存のゴールデンテスト基盤に「fingerprint 検査テスト」を明示的な名前で追加し、README から参照する。審査員が主張を検証しにいったとき、矛盾ではなくテストが出てくる状態にする。
  2. **禁止語リストをデータとして持つ**。「危険」「快適」「避難すべき」「〜しなさい」「〜を選べ」等を config 化し、プロンプト生成時に assert する。
- **⚠ README がベーステンプレの使い回しになっていないか確認する。** 本チームの README は元の火事シミュレーションのまま(「デフォルトでは左側と右側にバーが 1 つずつ」「火災イベントも発生する」)で、**提出物の中身(春の公園・桜・3 体)とは別物を説明している**。しかも config は `fires: []` で火事は起きない。shibuya-simulation は独自実装だが、**README の記述が現行実装と一致しているかの定期監査**(記述された機能が config で有効か、記述されたファイルが実在するか)は 8/30 前に必ず 1 回やる。
- **⚠ 「実装したが config で無効」は加点にならない。** 火事の知覚モデル B は精密実装なのに `fires: []` で未起動 → 講評は「未起動」と書いて評価から外した。**提出用 config は、自慢したい機能が全部 ON になっている状態にする**。渋谷側でいえば、関係性の内生化(現在 `relations.endogenous_invite` 既定 OFF)のような **既定 OFF の目玉機能を、提出用 config では ON にした構成を用意し、その実行ログを提出物に含める**。
- **⚠ LLM 出力を後段の正規表現で削るのは負けパターン。** 215 行のフィルタは C(拡張性)と A(自由度)を同時に削った。本人の Phase 41 の気づき「**削るのではなく、そもそも存在しない設計にする**」が正解。渋谷側で LLM 出力の後処理が増えてきたら、それはプロンプト/世界設計側の負債のサイン。**後処理行数を技術的負債メトリクスとして見る**。
- **`if agent.id == N` のハードコード分岐は C を直撃する**。特定個体だけ特別扱いする分岐が散在すると「新エージェント追加に全箇所修正が必要」と評価される。渋谷側は個体差をデータ(プロファイル)側に持たせ、コード分岐にしない。
- **`random.seed` 未設定は毎回名指しで減点される**(本チーム・mars・psychology の 3 チームすべて)。渋谷側は決定論を持っているので、**「シード固定で完全再現する」ことを README のトップレベルで主張し、再現手順を 1 コマンドで示す**と、下位チームとの差が最も分かりやすく出る。
- **題材の詩性だけで B は 7.0 取れる**。ただし A/C/D が伴わないと合計 20.5 で 28 位。渋谷側は題材(渋谷・世界を変える個体)が強いので B は取れる前提で、**A(自由度)と C(将来展望)に投資する**のが得点効率が良い。
- **「汚染か、創発か」問題は渋谷側にも来る**。LLM の異常出力(言語漏出・形式崩れ)を「バグ」として除去するか「観測対象」として記録するかは、観測分離の設計判断そのもの。渋谷側は既に fallback/unparsed を分離する方針を取れるので、**異常出力を捨てずに専用ログへ隔離し、事後に人が判断できる形で残す**のが最も安全(psychology-simulation の「パース失敗を PANIC に計上」の逆)。

## web リサーチ

- Yugen(幽玄)/ Wabi-sabi(侘寂)は日本の伝統美学概念で、能楽論・茶道に由来する。Stanford Encyclopedia of Philosophy の日本美学項目: https://plato.stanford.edu/entries/japanese-aesthetics/
- 「LLM が体験から作品を生成する」方向は、Generative Agents(Park et al. 2023)の記憶ストリーム→リフレクション→計画のループを、出力を作品側に接続して使う発想。原論文: https://arxiv.org/abs/2304.03442
- 小型モデル(3B)特有の code-switching / 母語漏出は、多言語 LLM で観測される既知の現象。多言語モデルの言語混同については Marchisio et al. 2024, "Understanding and Mitigating Language Confusion in LLMs": https://arxiv.org/abs/2406.20052 — スライドの「汚染か、創発か」は、少なくとも機構としては言語混同として説明できる(が、作者の問いの価値は別のところにある)。
- Wong Kar-wai(王家衛)の映像文体を LLM のシーンプロンプトに使う手法は、text-to-video 分野で「監督名によるスタイル指定」として一般的。ただし固有名詞によるスタイル指定は再現性が低いことが知られる: https://arxiv.org/abs/2401.09047 (video generation survey)
