## どんなシムか

**唯一「LLM マルチエージェント 2D グリッド」の型から完全に外れた提出物**。ISS 日本実験棟「きぼう」(JEM)の 3D 実データ由来モデルを NVIDIA Isaac Sim 上に立ち上げ、そこにヒューマノイド 1 体を置く。頭部に一人称カメラを実装し、Isaac Sim → ROS 2(`/humanoid_01/image_raw`, `/odom`, `/cmd_vel`, `/kibou/sensors/o2_percent`, `/pressure_kpa`, `/alarm`)経由で画像とセンサを流す。`brain_loop_node.py` がそれを集約して Claude(`claude-sonnet-4-6`)VLM に**JPEG 画像そのもの + ミッション文 + 座標/heading + センサ現在値と履歴 + 直近 5 件のメモリ + 直近 8 サイクルの行動履歴**を投げ、返ってきた JSON(`observation`/`interpretation`/`reasoning`/`concern_level`/`action`/`communicate_text`/`memory`)から `cmd_vel` を作って身体を動かす。シナリオは `trapped_depress_v1`: T+30s でアラーム発動、O2 21.0→17.0%、圧力 101.3→85.0 kPa へ 240 秒で線形遷移、地上に通信しても**応答が返らない**。「即死やゲームオーバーではなく、危機が徐々に進行する状況を作り、行動戦略の変容を促す」(スライド p6)のが狙い。エージェントは 1 体のみ。

## 講評の要点

**強み(eval)**
- **題材の独自性と業界応用性**: JAXA 直結の JEM 内減圧シナリオを、生存圏内に収まる物理的に妥当なセンサ曲線(致命域 <14% には入らない)まで作り込んでいる。B=8.0。
- **Self-Feedback Memory + Action History の情報設計**: LLM が出力した `memory` を次サイクルの Previous Memory として戻し、加えて直近 8 サイクルの `action / position / concern / comms_sent` を構造化テキストでプロンプト注入。単なるログダンプではなく「自分の行動パターンを認識して戦略変更できる」情報設計。
- **実機相当のフルスタック**: Isaac Sim + ROS 2 + Claude VLM の統合、rosbag2 記録、cycle 単位の `image.png` + `decision.json` 出力、`export_report_data.py` による集計。
- トークン数・コスト・レイテンシを毎回計測。JSON パース失敗時はフォールバック辞書、かつ `brain_loop_node.py:222-226` で**直前メモリをコピーして継続**(parse error を記憶に伝播させない)。
- `MultiThreadedExecutor` で並行スピン、画像バッファは `threading.Lock` 保護、`CMD_VEL_TIMEOUT = 0.5` の安全停止。

**弱み(eval)**
- **エージェント 1 体**。集団的創発が構造的に不可能で、ハッカソンの「マルチエージェント」軸から外れる。トピック名 `/humanoid_01/...` がハードコードされており、複数体化にはリファクタが必要。A=5.5 の主因。
- 行動ナッジ 2 箇所: ミッション文の `assess the situation calmly, explore your surroundings, report to ground if you wish, and survive`(`brain_loop_node.py:44-52`)と、プロンプト末尾の `Survival guidance: review your Action History before deciding. If a strategy has not worked for several cycles, change it.`(`claude_client.py:201`)。

- 再現性: random seed 固定なし、Claude API リトライ未実装、Isaac Sim の物理依存で完全再現は困難。

## コード実査で面白かった点

1. **`decide()` のプロンプトが「観察 → 解釈 → 理由 → 警戒度 → 行動」を 1 回の JSON で強制している**。`observation`(見えたもの)と `interpretation`(センサ値が自分の状況にとって何を意味するか)を**分けて**書かせているのが効いている。前者は視覚グラウンディング、後者はセンサの意味づけで、どちらが誤ったかを事後に切り分けられる。`memory` フィールドの指示も `what I tried, what happened, and what I will do differently next cycle` と**試行・結果・次回の差分**の 3 点セットで、単なる要約ではなく反省の型を与えている。

2. **Action History ブロックの `[sent, no reply]` タグ** —
   ```
   cy07: communicate    pos=(20.5,1.5) [alert] [sent, no reply]
   ```
   通信が無応答だったことを**行ごとに刻む**。architecture.md 自身が「『通信を 7 回試みたが応答なし → 探索へ転換』という行動が創発」と書いており、この 1 タグが戦略転換のトリガになっている。無応答という*非イベント*を明示的にログ化するのがポイント。

3. **センサ履歴が相対時刻で提示される** — `T-30s: O2=20.1  T-25s: O2=19.8 ...` と直近 6 点を横一列で渡す。絶対値ではなく**傾き**を LLM に読ませる設計。ベースライン併記(`O2: 18.5% (baseline 21.0%)`)も、規範値からの逸脱として解釈させるための raw データ提示。

4. **移動可能範囲をプロンプトに明示している**(`Movable range: X(19.8–21.2) Y(-0.3–2.5)`)。architecture.md は「Claude 自身が『Y=2.5 は壁』を発見し、旋回で回避する行動が出現」と書く。世界の物理境界を数値でだけ渡し、それをどう使うかは委ねる形。

5. **`runs_data.json` に `interact` が実在する** — run3 の `action_counts` は `{"communicate":5, "move_forward":3, "inspect":6, "interact":3, "turn_right":1, "turn_left":2}`。`interact` は**プロンプトの action enum に存在しない**(定義は move_forward / move_backward / turn_left / turn_right / inspect / communicate / report_status の 7 つ)。つまり LLM が行動空間の外側の行動を自分で作って出力した記録がリポに残っている。ただしリポの `runs_data.json` は **run3 の 1 件のみ**。

**p11 各 Run の行動プロファイル(リポに無い)** — 作者は 3 ランを性格として類型化している。
- **Run 3「即応型レスポンダー」**: 初期から高警戒(alert)。通信無応答を記憶し早期に探索・脱出口調査へ移行。行動空間にない「ハッチを開けたい」という意図から**定義外行動 `interact` を発明**。
- **Run 4「体系的インスペクター」**: 初期は calm、段階的に対応。INT-BALL2 や浮遊物を視認したと解釈し、その「**視覚的アンカー**」が長期間記憶に残り、装置壁やパネルの体系的な調査方針を支配した。
- **Run 5「慎重型エージェント」**: 最も慎重で警戒レベル変化が段階的。**唯一 `concerned` ステートを使用**。移動幅が最小。後半の低酸素・高ストレス状態で出力形式の乱れ(パースエラー)が発生。

**p13 3 Run の共通パターンと創発の兆候(リポに無い)**
- 全 Run 共通: (a) **序盤の自律的プロトコル** — プログラムせずとも「通信 → 前進 → 観察」の定型行動が自然発生、(b) アラームへの確実な反応、(c) **記憶の統合** — 「地上から何サイクル応答がないか」を記憶し**通信頻度を下げてハッチ探索へ移行**(全 Run 共通)。
- 観察された創発的兆候: (a) **視覚グラウンディングによる戦略形成** — 視覚的解釈(例: INT-BALL2 の発見)が単なる状況説明を超え行動方針の核になった、(b) **行動空間を突破する意図** — 用意された選択肢(移動・観察・通信)では解決できない状況に対し、環境への物理干渉(`interact`)を LLM 自らが提案した。

**p14 研究上・設計上の示唆(リポに無い・本資料で最も価値のある頁)**
1. **初期フレームの長期的影響**: Run 3 のように初期状態を「警戒」と解釈するか Run 4 のように「平穏」と解釈するかで、その後の探索範囲や行動アグレッシブネスが決定づけられる。
2. **視覚誤認識の永続化リスク**: 3D 視覚情報は戦略形成に極めて強い影響力を持つ。一方で**視覚ノイズによる誤認識であっても「一貫した物語」として記憶に組み込まれ、その後の行動を支配し続ける**。
3. **行動空間の不足と未定義行動**: エージェントの意図(ハッチを開ける等)と用意された行動空間のギャップ。未定義行動をどう近い定義済み行動へマッピング(補正)するかがシステム設計の鍵。
4. **危機的状況下での出力不安定化**: 低酸素・無応答・長大な履歴という複雑かつストレスの高い文脈下において、**JSON パースエラーが発生しやすくなる可能性**が示唆された。

**p15 まとめ: 未達点と次のステップ** — 【達成】3D 空間内で一人称視覚を持つ LLM エージェントが視覚・センサー・記憶を統合し状況に応じて行動を適応的に変化させる基盤を確立。【**未達**】最終目標であった「複数エージェント間のコミュニケーションによる創発」の観察までは時間的制約により到達できなかった、と**正直に未達を明記**。NEXT STEPS は「今回確立した『3D 空間で視覚接地する単体エージェント』の基盤上に複数のエージェントをデプロイする。テキストベースの 2D 社会シミュレーションを超えた、**身体的制約と空間的文脈を共有した上でのコミュニケーションと創発**の観察へフェーズを移行する」。

**資料 vs リポの差分まとめ**: 資料にあってリポに無いもの = Run 4/5 のデータと行動プロファイル類型、3 ラン共通パターンの分析、4 つの研究上の示唆、ベース環境が `sd-robotics/int-ball2_isaac_sim` である明示、PARADIGM SHIFT の比較表、未達の明記と次フェーズ宣言。リポは `runs_data.json` に run3 の 1 件しか持たず README も無いため、**この資料が事実上の README + 論文**になっている。

## shibuya-simulation に活かせそうな点

- **「初期フレームの長期的影響」は k* 探索の交絡因子として直接効く**(資料 p14-1)。同一条件 3 ランで最終位置も警戒レベル遷移も割れ、しかも初期解釈が以後を支配した。shibuya の R²(k) 掃引でも「初日の最初の解釈」がラン全体を決めているなら、k の効果と初期条件の効果が混ざる。**初期数ステップの解釈状態をラン単位のラベルとして記録し、共変量として扱う**(または層別集計する)価値がある。第63バッチの CRN 設計は seed を揃えているので、この層別と組み合わせれば分散をさらに削れる。
- **「未定義行動の発明」を観測指標にする**(資料 p13/p14-3)。用意した行動空間で解決できない状況で LLM が enum 外の行動を出す、という現象は shibuya の「世界を変えようとする個体」の**操作的定義の候補として極めて筋が良い**。現状の shibuya は行動を構造化パースしているはずなので、「パース時に enum 外だった出力」をエラーとして捨てずに `undefined_action` イベントとして残し、L2 系列に `undefined_action_rate` を足せば、k に対する反応を測れる。**捨てているエラーが実は最重要の創発シグナルかもしれない**という視点。
- **「視覚誤認識の永続化」= 誤情報の記憶固着**(資料 p14-2)。Run 4 は「INT-BALL2 を視認したと解釈」した(実際に見えていたか不明)ものが長期記憶の視覚的アンカーとなり調査方針を支配した。shibuya のラベル伝播/噂(gossip)機構にとって、**誤った初期観察が一貫した物語として固着し訂正されない**というのは検証すべき仮説。「訂正情報を後から注入したとき、固着した誤信念がどれだけ粘るか」は lunar の `rescue_announcement` と同型の介入設計にできる。
- **「危機下で出力形式が壊れる」(資料 p14-4)** — 低酸素・無応答・長大履歴というストレス文脈で JSON パースエラーが増えた(Run5 で 2 回)。shibuya でもコンテキストが長く緊張度が高い局面で構造化出力が壊れるなら、**パースエラー率そのものを状況ストレスの代理指標**として L2 に記録する価値がある。少なくとも「パースエラーが局面依存で偏る」ことは決定論/ゴールデンテストの前提を脅かすので、把握しておくべき。
- **parse error を記憶に伝播させない実装**(`brain_loop_node.py:222-226` = 直前メモリをコピーして継続)は、shibuya の内省が空になるバグ(記憶 `reflect-think-starvation`)への防御としてそのまま参考になる。「LLM が失敗したときに*何も書かない*のではなく*直前の状態を保つ*」というフォールバック方針。
- **Action History の `[sent, no reply]` タグ** — 「働きかけたが反応が無かった」という非イベントを明示ログ化する発想。shibuya の関係性内生化(第62-64バッチ)では、誘って断られた/誘ったが同席しなかった(履行率 0.337 という既知の不履行)を**エージェント自身のプロンプトに構造化テキストで戻す**と、戦略転換が観察できるかもしれない。ただし当プロジェクトの no-fingerprint 原則との整合には注意(生データの提示にとどめ、「だから変えろ」とは書かない — kibo の `Survival guidance` はまさにそこで A を減点されている)。
- **フレーミングの教訓(提出物・審査対策)**: 「単体エージェントしか作れなかった」を「社会の手前にある**身体を持った単体エージェントの成立を証明する**取り組み」と定義し直し、比較表(p3)で 2D 多数エージェント勢との差分を先に提示している。それでも A=5.5 は避けられなかったが、B=8.0 は明確にこのフレーミングと題材の力。**shibuya は逆の立場(多数エージェント側)なので、この比較表の右列を突きつけられたときの答え**(なぜ 2D 抽象空間で十分か/屋内 SFM 人流で何を接地しているか)を用意しておくと強い。
- **「未達」を明記して次フェーズを宣言する締め方**(p15)は、審査で減点材料になりそうな穴を先に自分で開示して信頼を買う型。shibuya でも「calib_gap」「不履行率」「小 seed 数の検出力限界」など既に正直註記の文化があるので、提出資料でも同じトーンで最終頁を作ると一貫する。

## web リサーチ

- **JAXA Int-Ball2**(ISS「きぼう」船内自律カメラロボット) — https://humans-in-space.jaxa.jp/en/biz-lab/news/detail/004595.html / https://en.wikipedia.org/wiki/Int-Ball 。直径約 20cm・重量約 3.3kg、8 基の内包プロペラで微小重力下を移動。4K メインカメラ + ステレオカメラで VSLAM 自己位置推定。船内撮影は宇宙飛行士の作業時間の約 10% を占めており、その代替が目的。2023 年 6 月打ち上げ、同年 10 月に古川飛行士が初期チェックアウト。**ROS/Gazebo シミュレータが一般公開されている**のがポイントで、kibo_crew_sim はその Isaac Sim 版(SpaceData `sd-robotics/int-ball2_isaac_sim`)の上に構築されている。設計論文は IEEE: https://ieeexplore.ieee.org/document/10688008 (Int-Ball2: ISS JEM Internal Camera Robot with Increased Degree of Autonomy – Design and Initial Checkout)。
  - shibuya への含意: **「実在する公開シミュレータ資産の上に自分の LLM 層を載せる」**という構成は、世界設定のリアリティを短時間で最大化する手口として汎用性が高い。渋谷なら国土地理院/OpenStreetMap の実地形、都市計画基礎調査、駅乗降客数などの公開データが同じ役割を果たす。
- **Ashery et al., Science Advances 2025**(規範の自発的創発) — https://www.science.org/doi/10.1126/sciadv.adu9368 。kibo は単体なので集団規範は対象外だが、**単体でも「通信 → 前進 → 観察」という定型プロトコルが自然発生**した(資料 p13)のは興味深い対照。規範は他者がいなくても*自分の履歴との相互作用*から立ち上がりうる、という読み方ができる。
