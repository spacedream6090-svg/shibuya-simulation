## どんなシムか

雪山登山を舞台に「客観リスク R_obj と主観認識 R_subj のギャップ(Risk Gap)」と「止まれない意思決定の力学」を可視化する Web デモ。世界側は Python の純粋な数値シミュレータで、`R_obj = w1*env_avg + w2*human_avg + w3*time_pressure`、`R_subj = R_obj − bias`、`Gap = R_obj − R_subj`、加えて「引き返しコスト」`cost_stop` を状態変数として持つ。ユーザーは `/api/advance` で 1 step 進め、`/api/decide` で `continue`/`llm_stop` を選ぶ。LLM(ホストの Ollama・既定 llama3.2)は 4 種のガイドペルソナ(`safety_first`/`pace_push`/`optimist`/`weather_watch`)に応じて、リーダー発言とパーティ2名のセリフ、リスクの説明文を生成する。背景には軽井沢スキーバス転落・知床遊覧船沈没・那須雪崩という実在事故 3 件が置かれ、「善意ある判断者が構造的バイアスで誤る」構造を再現する。

## 講評の要点(なぜ減点されたか)

**A=3.0 が本グループ最低クラス。減点の構造が極めて明快で、しかも自業自得の側面がある。**

1. **設計思想として LLM を判断主体から外した**。`docs/presentation/v2.md`「**判断はルール、納得はLLMが担う**」、`docs/design/high_level_design_v2.md`「**LLMは：その歪みを露出させる装置**」。ハルシネーション対策としては正しいが、ハッカソンの A 軸(創発設計=世界ルール精度×行動自由度の調和)では自由度側がゼロに近くなる。
2. **行動空間が `trek`/`rest` の二択**。`app.py:616-651` の `_ollama_guide_plan_next_step` は LLM に二択のみを問う。
3. **単一意思決定者**。エージェントは事実上「引率」1 体のみ。パーティ隊員 2 名は `_ollama_party_chat_lines` の **1 回の LLM 呼び出しで `leader`/`member_a`/`member_b` の 3 人分セリフを一括生成**しており、独立性・自律性がない(_eval_review が実コード line 587-610 で確認)。
4. 発話の主体はテンプレ。`_leader_fallback_line`(345-413)/`_party_member_lines`(415-498)は条件分岐＋固定プールからの乱択。

**そして最大の構造的問題**: README に自ら書いている——「**`sample/` ディレクトリは `.gitignore` によりリポジトリに含めません。** 2D マルチエージェントの参考実験用コードなどは、各自ローカルで配置してください」「参考実装(ローカルのみ)`sample/multi_place_sim/` … **Git にはコミットせず**、必要な人だけローカルで保持します」。実際 `.gitignore` の 1 行目が `# 参考実装・ローカル実験用（リポジトリには含めない）` / `sample/`。**マルチエージェント実装は存在したが、リポジトリの整頓方針で提出物から外され、審査対象にならなかった。** 講評の一言コメント:「**マルチエージェント LLM シミュレーションという評価軸では、エージェントの複数性・自律性・相互作用が薄く、創発設計の評価は伸び悩む**」。

**C=6.5** は _eval_review が「やや高め・あえて減点するなら 6.0」と評した。`app.py` 804 行にテンプレ・LLM クライアント・API・チャット整形が同居。将来展望は書かれているが「既存テーマの深化に留まり、他ドメイン・相互作用・A/B テスト等の本質的拡張は限定的」。

**D=7.0** は本グループ最高。`except Exception: pass` による観測性の弱さ(`app.py:246-247`)と、FastAPI 状態がモジュールグローバル `_sim`(app.py:165)で並行性に弱い点が指摘された程度。

**_eval_review 所見**: 合計 23.5 を妥当と確定。誤りは 1 件のみ——元評価が `risk_simulator.py:165-166` としたグローバル `_sim` は実際は `app.py:165`(ファイル名誤記)。見落としとして「`_judgment_trigger_reason` 等の多段判断トリガは A 軸を僅かに押し上げる要素だった」と補足するが、「多段判断トリガを加味しても A は 3〜4 の範囲」と結論。

## それでも光る点

1. **「LLM は判断装置ではなく説明装置」という役割分離が一貫**。数値指標を Python 側に固定し LLM に触らせないので、**ハルシネーションで指標が壊れない**。講評も優れている点の筆頭に挙げた。プロンプトには「数値は捏造しない」を明示(`app.py:605` 付近)。
2. **`metrics()` が副作用なしの純関数**+`rng_seed: int = 20260504` でシード固定+`_scale` で max_steps に応じてステップ毎悪化量を正規化。再現性の作り込みは下位チームで突出。shibuya-simulation の決定論方針と同じ発想。
3. **`temperature` を用途別に 3 段切替**: 説明文 0.3 / 会話 0.7 / 判断 0.35。用途ごとに揺らぎ量を変える運用は素直に真似できる。
4. **JSON 抽出の多段フォールバック**(`{...}` 抽出 → 正規表現 → 決定論フォールバック)で、Ollama が落ちても「6 ステップごとの休憩+テンプレチャット」に退行し UX が壊れない。
5. **題材の骨太さ(B=7.0)**。軽井沢スキーバス・知床遊覧船・那須雪崩という実在事故を「構造は全く同じ」と抽象化し、サンクコスト・役割圧力・ゴール近接性の 3 因子で「続行バイアス」をモデル化。安全工学・運行判断という業務価値への接続が明確。
6. **ナラティブ層と数値層の分離**。`rp_zone()` が数値状態を `yama → mori → kouya → home/mori_yoru/umi` という物語ゾーンに写像し、アウトカム別に分岐する。数値を壊さずに語りを載せる設計。
7. **判断トリガの定数化**。`JUDGMENT_MAX_STEPS`/`LATE_GAP_DANGER`/`FLAG_*_TOGGLED` を定数として外出しし、「フラグの真偽反転」も判断発火条件にしている。単純な step 到達だけでない多段トリガ。
8. **ドキュメント整備**が下位チーム随一。高レベル設計 v1/v2・RP 設計・vNext ロードマップ(フェーズ A〜C)・Docker 運用メモ・デバッグログまで揃い、引き継ぎ可能。

## shibuya-simulation への教訓

- **⚠ 最重要: 提出物に入っていないものは存在しないのと同じ**。このチームは「リポを綺麗に保つ」ためにマルチエージェント実装を `.gitignore` で外し、**そのままハッカソンの主軸(A 軸)を落とした**。shibuya-simulation は公開ミラー運用+gitignore 除外の掟があるため、**同じ事故が起きうる構造をすでに持っている**。8/30 提出前に「審査 4 軸それぞれについて、根拠となるファイルが提出リポに実在するか」をチェックリストで機械確認する。特に「ローカルにはあるが未コミット」「実験成果物が gitignore 配下」は要監査。
- **「LLM に判断させない」は安全だが A を殺す**。ハルシネーション耐性と創発性はトレードオフ。渋谷側は「世界の数値は Python が持つ・行動選択は LLM が自由に決める」という現在の分離を維持しつつ、**LLM の行動空間を列挙型に潰さない**。二択・五択に落とした瞬間、A が 3〜4 点帯に落ちる(本チーム A=3.0、psychology-simulation A=4.5 も同じ理由)。
- **N 人分の発話を 1 回の LLM 呼び出しで一括生成してはいけない**。「1 プロンプトで leader/member_a/member_b を出力」は、コスト削減としては合理的だが、**エージェントの独立性がゼロになり、審査上マルチエージェントとみなされない**。渋谷側で会話バッチ最適化を入れるときは、「同一プロンプト内で他エージェントの発話まで生成する」形にしないこと(1 エージェント 1 呼び出し、または少なくとも他者発話は入力としてのみ渡す)。
- **temperature の用途別分離は取り入れ価値あり**。説明・要約系は低温、発話・行動は中温、判断は中低温。渋谷側の LLM 呼び出し種別(行動決定・発話・内省・記憶要約)ごとに温度を分けて config 化すると、再現性と多様性のバランスを調整しやすい。
- **決定論フォールバックで UX/実験を壊さない**。LLM 失敗時に無音で止まるのではなく、決定論的な既定挙動へ退行し、その事実をログに残す。渋谷側は既に fallback を持つが、**fallback 発火率を L2 KPI として常時出す**(mars 側の教訓とも合流)。
- **`except Exception: pass` を書かない**。講評で名指しされる。失敗頻度・要因が測れないのは実験系として致命的。
- **単一シナリオの深掘りは C(発展性)で頭打ちになる**。「既存テーマの深化に留まる」と評された。渋谷側の将来展望は「渋谷を深くする」だけでなく、**他都市・他ドメインへの一般化可能性、対照条件の追加、A/B 機能**まで書く。
