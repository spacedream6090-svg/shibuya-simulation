## どんなシムか

原作と同じ 2 次元グリッド・左右のバー(capacity 12 / 10)・15 エージェント・2 火災(fire_1: step 35 / intensity 0.8 / radius 15、fire_2: step 45 / intensity 0.5 / radius 8)・90 ステップ。原作からの最大の改変は「**ハイブリッド知性**」設計 = 「安全判断はルールエンジン、曖昧な社会的判断は LLM」という**二段ゲート構造**。火災情報の伝播には `known_fires` の信頼度階層(`direct` / `sys_warn` / `agent_report`)・`confirmed_count`・`last_seen_step` による減衰・幻覚フィルタ・ユニーク報告者追跡・`canonical_fire_id` による位置ベース正規化という、極めて丁寧な機構を実装している。62 テストの TDD、Ollama ローカル実行で API コスト 0 円。README は「避難成功率 15/15 (100%)」「平均実行時間 0.57 分(ベースライン比 **-97.6%**)」を実績として掲げる。

## 講評の要点

### 強み(D8.0 の理由 — 技術実装は提出群でも上位クラス)

- **信頼度階層つきメモリ**が講評に「本提出群中でも極めて精密」と評された。`known_fires` に情報源(`direct` / `sys_warn` / `agent_report`)・裏づけ数・最終目撃ステップを持たせ、`STALE_STEPS=8` で非直接知覚を減衰させる。
- **幻覚フィルタ**: LLM が報告した火災のうち、フィールド境界外の座標や radius 欠落のものを棄却する。
- **ユニーク報告者追跡**: 同じ情報が中継チェーンで戻ってきたときに `confirmed_count` を二重計上しない。**エコーチェンバーによる確信度の水増しを構造的に防ぐ**機構。
- **Canonical Fire ID**(講評「秀逸」): 直接知覚者が付ける名前と LLM 伝聞者が付ける名前の差異を、**位置ベースの正規 ID** に統一する。「幽霊火災」(同一火災が別物として二重計上される)を根絶。
- LLM 呼び出し最適化の体系性: warmup によるコールドスタート回避、Qwen 向け `/no_think` プレフィックス、fast/smart 二段モデルルーティング、cooldown、飽和スキップ、近傍受信者ゼロ時スキップ、Phase 3 context-skip。
- レース条件回避: バー占有スナップショットを同フェーズで一括取得。
- 62 テストの TDD による回帰保護。

### 弱み(A4.0 の理由 = 本チームから学ぶべき核心)

講評の指摘は容赦がない。「エージェント行動の自由度が**極端に低い**」「LLM は事実上**テキスト整形器**として機能している」。根拠として挙げられたのは:

- `decide_action_by_rule()`(`agent.py:1585-1857`、**約 270 行**)が意思決定の大半をルールで決定 — 場所内での組織的ドリフト、火災時の合成反発ベクトル、避難バー選択のすべて。
- LLM は「**曖昧ゾーン**」かつ「**火災言及メッセージあり**」という**二重ゲート**を通った場合のみ呼ばれる。
- **LLM プロンプト自体が答えを予告している**:
  - `_build_evacuation_decision_guidance()` — 「Computed optimal escape: {DIRECTION}. Move in this direction to maximize distance from fire.」(**計算済みの最適方向を明示**)
  - `_build_fundamental_purpose()` — 「Priorities: 1. Survive 2. Warn others 3. Coordinate」(**価値の順序を与えている**)
  - 「PRIORITY: Move to maximize distance from fire」
  - 「STAY HERE unless BAR SAFETY STATUS shows this bar as DANGER」(**直接の行動指示**)
  - メッセージプロンプトが「1. 火災位置 2. 強度と半径 3. あなたの避難方向 4. 他のエージェントへの推奨」と**発話の内容構造まで規定**
- 講評の採点式: 「世界ルール軸 ≒ 8、行動自由度軸 ≒ 3 で**調和平均は 5 未満**」。**A は両軸の調和平均に近い振る舞いをする**(= 片方が低いと全体が引きずられる)ことが読み取れる。
- README の「安全判断はルール、曖昧な社会的判断は LLM が担当」という自己記述が、そのまま減点根拠として引用された。**設計者自身の意思として LLM の自由度を縮小したことを README が証言してしまっている**。

その他の弱み:
- **B 6.0**: 火災避難シム自体が典型題材。README が「創発的役割分化: 指揮者・情報中継者・生存確認者など役割が自然発生」と主張するが、講評は「**設計上の役割付与は確認されず**」と留保(`_eval_review` が `grep` で `role|指揮者|leader|coordinator` の該当 0 件を確認済み。つまり主張は事後観察であって仕込みではない = 主張自体は正当だが、根拠の提示が弱い)。
- **C 7.0**: README に「将来展望」「Future Work」セクションが**ない**(`grep` 0 件で実証)。`agent.py` が 2,083 行と肥大化。
- 講評の総評: 「ハッカソンの『創発性・自律性の発現』という目的に対しては**逆効果**」「LLM に数値データのみを提示し、判断・指示語("STAY HERE", "Move in this direction")を排除すれば、設計上の創発ポテンシャルは**飛躍的に高まる**」。

## コード実査で面白かった点

1. **`visualization/emergent_role_detector.py` が本リポ随一の好アイデア**。`messages.jsonl` を事後解析し、**通信グラフの次数・タイミング・中継パターンから役割を帰納的に決定**する独立ツール。役割体系は 6 種:

   | 役割 | 判定基準(docstring より) |
   |---|---|
   | `pioneer` 先駆者 | 最初に火災情報を発信した |
   | `hub` 情報拠点 | 送信・受信ともに多く情報の中心 |
   | `broadcaster` 発信役 | 主に送信、受信が少ない |
   | `relay` 中継役 | 受信後に再転送 |
   | `listener` 受信役 | 受信のみ、発信なし |
   | `evacuee` 自力避難 | 通信なし |

   重要なのは**これがシミュレーション本体から完全に分離した後付けの観測器**であること。役割はエージェントに与えられておらず(`grep` で確認済み)、out_degree / in_degree / first_send_step / first_recv_step という**生の通信統計だけ**から induced される。`ROLE_PRIORITY` で複数該当時の優先順位を決め、`ROLE_COLORS` / `ROLE_LABELS_JA` で可視化に接続する。**観測分離の原則を、本体が A4.0 なリポの中で最も忠実に実践している部分**という皮肉。

2. **エコーチェンバー対策としてのユニーク報告者追跡**。A が同じ噂を B と C から聞き、B と C は元々 A から聞いていた場合、素朴な `confirmed_count` は 3 になる。本実装は報告者集合をユニークに保つことでこれを防ぐ。**情報伝播シムで確信度を扱うなら必須の機構**だが、実装しているものは少ない。

3. **Canonical Fire ID の問題設定が鋭い**。直接目撃者は「(15,10) の火災」と正確に言えるが、伝聞者は LLM が生成した曖昧な名前で呼ぶ。同一実体が複数 ID に分裂すると、伝播率の統計がすべて狂う。**位置ベースの正規化キーで実体同一性を回復する**。これは shibuya のラベル伝播で「同じ噂の言い換え」をどう同一視するかという未解決問題と同型。

4. **`STALE_STEPS=8` による非直接情報の減衰**。直接見た火災は減衰しないが、伝聞は 8 ステップで信頼度が落ちる。**情報源によって減衰率を変える**という設計。

5. **`evacuation_history` で PTSD 的回避バッファ倍率を変える**。一度避難を経験したエージェントは、次から火災に対してより大きな安全マージンを取る。**過去の経験が空間的行動パラメータを永続的に変える**という長期記憶の結合の仕方。アイデアとしては面白いが、これも「創発させるのではなく作り込んだ」例。

6. **最適化の体系性**: Phase 3 context-skip(火災文脈がなければ LLM 呼び出しごとスキップ)、SYS-WARN 即時伝播(検知と同ステップで近傍全員へ)、Transitive relay(検証済み `known_fires` を連鎖中継)、Path lookahead(8 ユニット先を投影して火災回避を早期計画)、Organic drift(避難後の 3 層同心円軌道 tier0/1/2 で「自然な動き」を演出)。**実行時間をベースライン比 -97.6%(34 秒)まで削った**のは純粋に見事。

7. **しかし「Organic drift で自然な動きを演出」という言葉遣いが病理を象徴している**。創発を観察するのではなく、自然に**見える**動きを演出している。README の「避難成功率 15/15 (100%)」も同様で、**タスク成功率を KPI に据えた時点で創発研究ではなくなる**。

8. **62 テストの内訳が「機能テスト」であって「創発テスト」ではない**: 火災 ID 正規化 7 / 全体認知度管理 7 / SYS-WARN 即時伝播 5 / 経路先読み 10 / LLM スキップ最適化 7 / ルールベース航法 11 / 情報飽和検出 6 / 情報源信頼度保持 4 / 中継 SYS-WARN 5。**ルールエンジンを厚くしたからこそテストが書けた**という因果関係がある(LLM の自由な出力はテストしづらい)。テスト数と創発スコアのトレードオフが生じている。

レビューリポ `slides/23-52-2d-multi-places-simulation-on-fire.pdf`(6 ページ・**テキスト層なしの画像 PDF**のため PNG 化して視覚読解)。

**表紙が KPI ダッシュボードになっている**。大きな数字 4 つが横並びで:

| **100%** | **−97.6%** | **¥0** | **62** |
|---|---|---|---|
| 避難成功率<br>15/15 全試行達成 | 実行時間削減<br>0.57 分(ベースライン比) | API コスト<br>完全ローカル Ollama | テスト全通過<br>TDD 9 ファイル |

キャッチコピーは「LLM が定量情報のみから危機を解釈し、日本語で協調して**全員を安全に避難させる** 自律的マルチエージェントシミュレーションシステム」。

**これは製品ピッチの構造であって、創発研究の構造ではない**。「全員を安全に避難させる」がゴールとして宣言された瞬間、観測対象は「創発したか」ではなく「達成したか」に変わる。講評が A4.0 を付けた理由が、コードを読む前に表紙で予告されている。

その他のスライド内容:
- **最適化フェーズ別の実行時間比較**(3 ページ目)が engineering として見事: ベースライン 12.75 分 → SYS-WARN 後 2.77 分(21.7%)→ Canonical ID 後 1.33 分(10.4%)→ 最終版 0.57 分(4.5%)。**どの施策がどれだけ効いたかを段階的に分解**している。この提示形式自体は優秀。
- **「ハイブリッド知性アーキテクチャ」の 3 層図**: SENSOR LAYER(直接知覚 / SYS-WARN 即時伝播 / Transitive Relay / LLM メッセージ解析)→ DECISION LAYER(**Rule Engine「高速・確実」= 火災回避 / バー選択 / 経路先読み** ↔ LLM Engine「文脈・創発」= 曖昧判断 / 日本語メッセージ生成、+ Context-Skip、Global Awareness)→ ACTION LAYER(move/stay / 日本語メッセージ送信 / Organic Drift / 生存確認・安全報告)。**Rule Engine が黒背景で最上段、LLM Engine がその下**という図の序列まで、実際の権限関係を正直に描いている。
- **「LLM COMMUNICATION DESIGN — 日本語メッセージ設計」の表**が決定的。状況 × ガイダンス種別 × **出力例**の 5 行:

| 状況 | ガイダンス種別 | 出力例 |
|---|---|---|
| 直接火災知覚 | 火災緊急メッセージ | 「Fire at (15, 10)、強度 0.8、距離 7。左に逃げています!左か下へ!」 |
| 避難移動中 | 移動状況報告 | 「(1, 2) 地点、left_bar へ向かっています。経路は今のところ安全です。」 |
| 避難完了後(経験者) | 生存確認メッセージ | 「left_bar で無事!Agent 5 もいます。Agent 9 を見た人はいますか?」 |
| 安全場所からの観察 | 安全確認報告 | 「left_bar は安全!外の仲間は大丈夫?早く合流してください!」 |
| 火災情報の中継 | 情報中継メッセージ | 「Fire at (15, 10) で報告あり。右は危険、left_bar へ向かってください。」 |

**発話の内容が状況ごとに設計されている**ことを、提出者自身が「設計」として誇らしく提示している。講評の「LLM は事実上テキスト整形器」という評価は、この表を見れば争えない。

> **shibuya への含意**: **表紙に何を置くかで評価軸が決まる**。「達成率」「成功率」「削減率」を大きく出すと、審査者は工学成果として読み、創発設計の評価軸から外れていく。shibuya の表紙に置くべきは達成率ではなく、**観測された創発現象そのもの**(例: 「プロンプトに存在しない語が N 個、M 人の集団に定着した」)。同じ数字でも「タスク成功」ではなく「予期しなかった出来事」を出す。

## shibuya-simulation に活かせそうな点

### 反面教師として(最重要)

- **「性能を上げる改変」が「創発スコアを壊す改変」と一致しうる**。同一原作から出発して、実行時間 -97.6%・避難成功率 100%・62 テストという**あらゆる工学指標で上回った**にもかかわらず、総合は 33.0 → 25.0、A は 9.0 → 4.0。shibuya-simulation の性能最適化(LOD、キャッシュ、並列化)を進める際、**「LLM の判断をルールで代替する」形の最適化だけは A を直接毀損する**と自覚すべき。LOD の落とし方は「呼ぶ回数を減らす」ではなく「**呼ぶ相手の解像度を下げる**」方向に限定するのが安全。

- **プロンプトに書いてはいけない語のブラックリスト**が、この講評から具体的に抽出できる。shibuya の no-fingerprint 点検リストとして使える:
  - 計算済みの最適解の予告(「Computed optimal escape: X」)
  - 価値の順序づけ(「Priorities: 1. Survive 2. Warn others 3. Coordinate」)
  - 直接の行動指示(「STAY HERE unless...」「Move in this direction」)
  - 優先度の宣言(「PRIORITY: ...」)
  - **発話の内容構造の規定**(「1. 位置 2. 強度 3. 方向 4. 推奨」)← これは見落としやすい。「何を喋るか」の枠を与えるのも指示である。

- **README の自己記述が減点根拠として逐語引用される**。「安全判断はルール、曖昧な社会的判断は LLM が担当」という一文が A4.0 の根拠 6 番目になった。shibuya の README で、実装の正直な説明が創発の否定に読めないか点検する価値がある。**正直さは維持したまま、何が創発で何が機構かを分けて書く**。

- **「役割が自然発生する」と主張するなら証拠を同梱する**。本リポは主張したが根拠を出さず、講評に「設計上の役割付与は確認されず」と**留保つきで**扱われた(実際には仕込みがないので主張は正当だったのに、証拠不足で加点にならなかった)。皮肉なことに `emergent_role_detector.py` という証拠生成ツールを持っていながら、**その出力を README/提出文書に載せていない**。shibuya は観測器の出力を必ず提出物に載せること。

- **「将来展望」セクションの欠落だけで C が減点される**。`grep` で 0 件と実証された。低コストで確実に効く対策。

### 積極的に取り込む価値がある点

- **通信グラフからの役割の事後induction**(`emergent_role_detector.py` の設計)。shibuya は組織の自然形成とファウンダー成立条件を研究目標に掲げている。**pioneer / hub / broadcaster / relay / listener / isolate という 6 分類を、発話ログの有向グラフから完全に事後的に導出する**観測器は、「世界を変えようとする個体」の候補抽出にそのまま使える。特に `pioneer`(ある情報を最初に発信した者)は**ラベル伝播研究の起点特定**そのもの。重要なのは、shibuya では既に観測分離の原則があるので、これを本体に混ぜず独立ツールとして持つ形が正しい。

- **ユニーク報告者追跡によるエコーチェンバー水増し防止**。shibuya のラベル/噂伝播で「何人から聞いたか」を確信度に使うなら、**伝播元をユニーク集合で持たないと循環参照で確信度が発散する**。これは実装上の必須注意点。

- **Canonical ID による実体同一性の回復**。shibuya の新語伝播では「同じ語の表記ゆれ・言い換え」を同一ラベルとみなす必要がある。位置ベースではなく**語の正規化キー**(あるいは埋め込み近傍)で同じ問題を解く必要がある。本リポは「観測時に正規化する」というアプローチを取っており、**エージェントには曖昧なまま持たせ、観測器だけが正規化を知っている**という分離が正しい形。

- **情報源別の減衰率**(直接知覚は減衰なし / 伝聞は 8 ステップで減衰)。shibuya の噂の風化モデルに直接使える設計変数。

- **`evacuation_history` → 空間バッファ倍率**のような、**経験が行動パラメータを永続的に変える**結合。shibuya で「一度組織化に失敗した個体はその後どう変わるか」を見るなら同型の仕掛けが要る。ただし**倍率を決め打ちせず、LLM の内省結果から出す**形にすれば創発を毀損しない。

- **バー単位アラーム**(`_eval_review` が加点余地ありと指摘した工夫): 建物の火災報知器のアナロジーで、場所内にいる全員に一斉に情報が届く。shibuya の屋内空間で「館内放送」「駅の電光掲示板」のような**場所依存の一斉配信チャネル**を持つと、個体間伝播とは別の伝播経路として観測が面白くなる。
