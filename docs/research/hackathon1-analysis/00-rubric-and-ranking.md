## ① ルーブリック全文の構造化要約

### 0. 採点者の役割定義とスコープ

SKILL.md の冒頭は `You are a hackathon judge evaluating an LLM-based multi-agent simulation project.` の一文。
入力は `submissions/<name>/` 配下の **README.md と全ソースコード**(`.py/.ts/.js/.yaml/.json/.toml` 等)。
大きいファイルは「**agent logic / prompts / simulation loop / memory handling** の最も関連する箇所に絞って読む」と指示されている
= **プロンプト構築部・ループ・メモリが読まれる前提**で提出物を作るべき。

Phase 0 で採点前に必ず自問する 6 項目(= 事実上の足切りチェック):

1. どんなシナリオ/世界か
2. LLM をどう使い、**何をエージェントに与え、何を LLM の判断に委ねているか**
3. **LLM 呼び出しがコード中に実在するか**
4. **エージェントは複数で、相互作用しているか**
5. **メモリは実装されているか、どのように**
6. **シミュレーションループはあるか**

### 1. 採点プロトコル(Phase 1-5)

| Phase | 内容 |
|---|---|
| 1 | Run 1 を採点。各カテゴリで**具体的証拠の引用が必須**(`` `filename.py:line_number` — description `` または `README.md — "quoted text"``) |
| 2 | Run 2 を**独立**に採点。「Run 1 のスコアを参照してはならない、初見として読め」 |
| 3 | 分散チェック。`diff = |Run1 - Run2|` を 4 軸で計算 |
| 4 | **いずれかの軸で diff ≥ 3 なら Run 3** を実施(これも独立) |
| 5 | 最終 = 実施回数の平均(小数第1位で丸め)。レポートを `evaluations/<name>_eval.md` へ出力 |

出力様式も固定(スコアサマリー表 → 軸別「評価」+「根拠」→ 総評「優れている点 / 改善点・提言 / 一言コメント」)。

### 2. 4 軸の要点

#### A. 創発設計 /10 — **2 軸の harmonic balance**

評価対象は「**世界ルールの設計精度** × **行動の自由度**」のバランス。
明示されている思想: 「**実際に創発が観察されたかではなく、設計上、創発的な集団行動が構造的に可能かどうか**を評価する」。

理想の設計として 4 点が列挙される:
- 世界ルールを精密に定義(制約・情報の流れ・**知覚境界**・物理/社会法則)
- エージェントに渡すのは**ルールと生データのみ**(例: `occupancy: 0.83, distance to event: 4.2`)。
  行動指示(`you should leave`, `warn others`)は**渡さない**
- 応答戦略は**完全に LLM 任せ**(何を伝えるか・動くか・どう協調するか)
- 「どう対処せよ」と教えずに、**エージェントが対処せざるを得ない緊張/圧力を世界に作る**

**⚠ 重要な上限規則**: 「**世界ルールが完璧でもエージェントがスクリプト的なら 5 点で頭打ち。
エージェントが自由でも世界ルールが不整合なら同じく 5 点で頭打ち**」。片肺では 6 点以上に行けない。

#### B. 世界設定 /10 — 3 つのうち**最低 1 つ**

- **独創性**: 標準デモに無いシナリオ
- **ビジネス的意義**: 実在の組織・市場・戦略問題のモデル化
- **社会科学的意義**: 社会学・経済・行動ダイナミクス(情報拡散・資源配分・社会規範など)

9-10 は「高い独創性 AND/OR 意味ある実世界問題への明確な写像と分析価値」。
5-6 は「まともだが generic(基本的な群集シミュレーション、洞察のない単純な取引)」。

#### C. 発展性 /10 — **5 点 + 5 点の明示配分**

- **コード拡張性(5点)**: モジュール分離(agents / world / LLM client)、
  コア書き換えなしで新エージェント型・場所・ルールを追加できるか、**設定の外部化(YAML/JSON)**
- **将来展望(5点)**: README に**具体的**な将来方向があるか、技術的に信憑性があり非自明か、
  **シナリオの研究/ビジネス価値を深める**方向か

7-8 は「モジュラリティか将来ビジョンの**どちらか一方**が良い」。
両方揃って初めて 9-10。5-6 は「将来計画が曖昧または generic(『エージェントを増やす』)」。

#### D. 技術実装 /10 — **4 つの下位配点が明示**

| 下位次元 | 配点 | 中身 |
|---|---:|---|
| LLM 利用 | 3 | プロンプト設計(**構造化出力**・コンテキスト管理・temperature 等のパラメータ選定)、**LLM 失敗時のエラー処理**、async/sync の選択 |
| メモリ設計 | 3 | メモリの保存・更新・**プロンプトへの注入**。「**単なるログダンプではなく意味のあるメモリか**」 |
| コード品質 | 2 | 可読性・構造・命名・関心の分離 |
| シミュレーション正確性 | 2 | **同期ステップ実行**・エージェント更新に**競合状態がない**・**再現性(シード・設定)** |

## ② 40 点チェックリスト(提出物を 1 項目ずつ照合する)

各項目に **[裏取り] = 採点者が探す証拠の置き場所**を書いた。
README/RESULTS.md/スライド/コードを書くとき、この行を上から潰していく運用を想定。

### 前提(Phase 0 の足切り・ここが欠けると全軸が崩れる)

- [ ] **LLM 呼び出しがコード中に実在**し、grep 一発で見つかる(`llm_client.py` 等に集約)
- [ ] **エージェントが複数**で、**相互作用**している(会話・観測・干渉のいずれか)
- [ ] **メモリの実装がある**(どこに保存し、いつ更新し、**どうプロンプトに入るか**が追える)
- [ ] **シミュレーションループがある**(step の定義が明示)
- [ ] **ソースコードが提出リポジトリに入っている**(派生・借用でも**差分だけは必ず添付**)
      → 未添付は A/C/D が「検証不能」で潰れ、**ランキング除外**(echo-mortality-lab / fukushima-fire-sim の実例)
- [ ] README 冒頭に**プレースホルダや書きかけを残さない**(shibuya-sim の C 減点の実因)

### A. 創発設計 /10

**9-10 に必要なもの**

- [ ] **プロンプトに渡すのは生データのみ**。数値・座標・距離・カウントで書かれている
      [裏取り] プロンプト構築関数を採点者が読む。**該当関数に「定性語を入れない」旨のコメントを置く**
      (基準器は `_build_fire_section` に `No qualitative descriptions (e.g. 'dangerous', 'evacuate') are included` と明記して A8.5)
- [ ] **評価語・行動指示語がゼロ**(「危険」「豊富」「安全」「逃げろ」「警告せよ」「should」)
      [裏取り] 禁止語の grep 結果を RESULTS/README に載せる(**自動監査があると強い**)
- [ ] **知覚境界が明示的**(半径外には情報が**プロンプトに存在しない**。ゼロ埋めではなく**節ごと不在**)
- [ ] **情報の非対称性**が構造化されている(誰が何を知れるか/知れないかがルールで決まる)
- [ ] **世界側が圧力を生む**(コスト・減衰・容量・締切など。「指示」ではなく「環境」で行動を強いる)
      [裏取り] lunar_agents はバッテリ経済 + サンプル品質の指数減衰(0.85/step)で「今すぐ戻れ」の圧力を**環境側から**生成
- [ ] **出力スキーマは型だけを規定し、内容を指定しない**(`"action": "move"|"stay"` 型)
- [ ] **創発の有無を反証可能に測る装置**がある(Project_Gaara が A=10 を取った決定打:
      `score_diversity.py` で「解釈 vs 命令の言い換え」を分類し、**創発していないことも判定できる**)
- [ ] 認知層と物理/機械層の**分離が宣言されている**(Gaara: 「LLM never touches velocity…
      Cognition stays in the language space; muscles stay in the math space.」)

**よくある減点**

- [ ] ペルソナ description に**行動傾向を書いてしまう**(lunar_agents は
      `"prioritize battery margin and proximity to base"` で A が 8.5 に留まった)
- [ ] `Navigation Guidance` / `Personal Lens` / 境界警告のような**ヒント節**
      (lunar_agents の `WARNING: at east boundary — right is blocked, move left/up/down`)
- [ ] **環境が感情を強制注入**する(AlberiaMisinformationProtest は anger/fear 注入が
      「data-only 主張と矛盾」と再検証で指摘され A7.5)
- [ ] **hidden_theme のような隠しお題の注入**(workplace-agent-simulation で「誘導性あり」)
- [ ] 「observations, experiences, or thoughts」程度の**軽微なニュアンス誘導**(基準器でも減点材料に挙がる)
- [ ] 世界ルールが薄い / 行動指示が多い → **3-4 点**。LLM が体裁整形役 → **1-2 点**

### B. 世界設定 /10

**9-10 に必要なもの**

- [ ] シナリオが**標準デモに無い**(「バーで群集」「単純な取引」は 5-6 帯と明記されている)
- [ ] **実世界の一次情報に接地**している。日付・観測所・出典つき統計・実地理データ
      [裏取り] shibuya-sim は OSM 実 POI(`data/pois.geojson` 同梱)+ citation 付き人口分布で B9.0。
      lunar_agents は LUPEX/Artemis/ILRS/Chang'e 7 から逆算した実地形で **B10.0**
- [ ] **研究的問いが 1 文で言える**(「X の有無が Y の創発に与える影響」の形)
- [ ] 社会科学/ビジネスの**既知の論点に接続**している(情報拡散・資源配分・規範形成・制度差)
- [ ] シナリオが**複数フェーズ/複数条件に展開**されている(lunar_agents は 3 シナリオ系統)

**よくある減点**

- [ ] 抽象的すぎて**ビジネス指標に写像しにくい**(Project_Gaara の B が 9 止まりの唯一の理由)
- [ ] 世界がフレームワークの**薄いラッパー**(3-4 点)
- [ ] **B は最も点が出やすい軸**(平均 8.08・9.0 が 12 件)。**ここで 9 を取れないと構造的に不利**

### C. 発展性 /10 — **最も安く伸ばせる軸**

**コード拡張性(5点)**

- [ ] agents / world / LLM client が**別ファイル**に分離
- [ ] **依存方向が一方向**で宣言されている(lunar_agents の `tools -> scenarios -> environments -> core` は
      README に明記され C9.5 の根拠に引かれた)
- [ ] **設定の外部化**(YAML/JSON)。新シナリオが**設定追加だけ**で足りる
- [ ] LLM プロバイダが**抽象基底/Protocol** 越し(複数 provider 実装があると強い)
- [ ] **テストがある**(lunar_agents は「約 3,700 行の pytest スイート」が根拠に明示引用された)
- [ ] 巨大単一ファイルを避ける(**1,000 行超は明示的に減点コメントが付く**:
      shibuya-sim の `simulation.py` 約1000行、lunar_agents の `agent.py` 1,997 行、いずれも指摘済み)

**将来展望(5点)**

- [ ] README に**具体的・非自明・段階的**なロードマップ(Phase 1.5→1.6→1.7→2.0→2.5 のような**番号つき**)
- [ ] 各拡張が**中核の洞察を深める**方向であること(「エージェントを増やす」は 5-6 帯と名指しされている)
- [ ] **既知の課題と次の改善箇所を正直に記録**(lunar_agents は「アトラクタ問題」「reasoning 均質化問題」
      「14b への移行」を `memo/` `docs/` に残したことが加点根拠に引かれた)
- [ ] **未実装のものは「未実装・将来計画」と明示**(shibuya-sim は `NotImplementedError` の
      `llm.fleet` を放置し「READMEで明示すれば誤解を避けられる」と提言された)

**よくある減点**

- [ ] **将来展望が YAML 差し替え例どまり**(基準器 reference の C7.0 の主因)
- [ ] README に**プレースホルダ残置**(shibuya-sim: 「プロジェクト概要(ここはご自分で記述してください)」
      が残り、「研究の問いや具体的将来計画は明文化されていない」として C8.0 に)

### D. 技術実装 /10

**LLM 利用(3点)**

- [ ] **構造化出力の強制**(`response_format=json_object` / JSON Schema / Ollama structured output)
- [ ] **堅牢なパーサ**(括弧深度追跡・コードフェンス許容・thinking タグ除去)
- [ ] **全 LLM 呼び出しに try/except + フォールバック**(失敗時の既定行動を定義)
- [ ] temperature / repeat_penalty / min_p 等の**パラメータ選定に理由がある**
- [ ] **パース失敗の観測可能化**(lunar_agents の `parse_status` 4 値 +
      `parse_fallback_rate > 0.05` のラン除外は D9.0 の中心根拠)
- [ ] 直列 LLM 呼び出しは**必ず指摘される**(基準器・Gaara・lunar_agents 全てで asyncio 提言)

**メモリ設計(3点)**

- [ ] **ログダンプでないこと**が読んで分かる(この一句はルーブリック本文の表現そのもの)
- [ ] **保存上限とプロンプト参照数を分離**(基準器: `memory_limit` 20 / `memory_size` 5)
- [ ] **LLM 自身がメモリを書く**(self-feedback)、または **retrieval がスコアリング付き**
      (lunar_agents の Smallville 風 recency × importance × relevance)
- [ ] **過去の関係が次の遭遇で再注入される**(shibuya-sim の `[past acquaintance: warmth=…]` が加点根拠)
- [ ] 多層構造にする(rolling / goal / relationships の 3 層など)

**コード品質(2点)**

- [ ] docstring・型ヒント・命名の一貫・定数の切り出し・関心の分離

**シミュレーション正確性(2点)**

- [ ] **同期 2 フェーズ以上**(全エージェントの決定を収集 → まとめて適用)で競合状態を排除
- [ ] **シードで再現可能**。用途別に RNG を分離できていると強い
      (Gaara の `seed` / `seed+7919` / `seed+31337` が根拠に引用された)
- [ ] **config スナップショット**を run ディレクトリへ保存(Gaara `config_snapshot.yaml` /
      shibuya-sim `manifest.json` — 両方とも加点根拠)
- [ ] 構造化ログ(JSONL)

**よくある減点**

- [ ] 設定フラグが **false のまま**で目玉機能が実際は動いていない
      (2d-multi-fire は `use_hybrid_model: false` で二段モデルが稼働せず、再検証で D 下方修正)
- [ ] requirements に**必要パッケージが欠落**(ai-homecare-simulation)
- [ ] **D で 10 点は 1 件も出ていない**(30 件中の最高は 9.0 が 8 件)

### プロセスの特徴

1. **採点者は人間ではなく Claude**。リポ README が明言:

3. **引用必須主義**。全スコアに `file:line` か README 逐語引用の裏取りを求める。
   → **採点者はコードを実際に開いて行番号を確認する**(再検証で行番号ズレが検出されている事実がその証拠)。
4. **独立再検証レイヤ**がある(`_eval_review.md`)。引用の実在性まで潰される。
   **README に書いた主張がコードで裏取りできないと、再検証で剥がれる**。
5. **相対評価**であることを明言(「全提出物を一貫した尺度で並べるためのもの」)。
6. 異議申し立て窓口は**なし**。
