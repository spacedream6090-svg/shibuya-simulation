## 1. C 軸(発展性)— 唯一の全面敗北。しかも原因はコードではない

### 1.1 shibuya-sim が 8.0 になった理由(講評原文)

> 「README のトップに**「プロジェクト概要（ここはご自分で記述してください）」というプレースホルダが残されており**、
> 研究の問いや具体的将来計画は明文化されていない。」
> 「**明文化された将来展望文書がない分、ロードマップ提示としては減点要因。**」
> 「`config.llm.fleet`（gpt-4o-mini 60%/gemini-flash 30%/claude-haiku 10%の混在艦隊）は `NotImplementedError` で未実装」

検証レポート(`shibuya-sim_eval_review.md`)の C 節はこれを裏づけたうえで、
**加点側は満額に近い**と書いている:

> 「加点要因: モジュール分離（src/ 7ファイル、単一責任）、設定の8YAML外部化、スクリプト群の充実、
> `llm.fleet` スキャフォールドの先取り、データクラス `Agent` のフィールド設計の余裕度……」
> 「減点要因: **READMEの「プロジェクト概要」プレースホルダ未記入**、`llm.fleet` 未実装、
> `scripts/aggregate_runs.py` などのスクリプトが揃っているが、**ロードマップ文書がない**。」

**コード拡張性そのものは減点されていない。減点は 3 つとも文書/未実装宣言の問題である。**

### 1.2 上位3チームが C で 9.0 以上を取った内訳

**lunar_agents(9.5)** — 講評:
> 「README と CLAUDE.md に Phase 1.6（LUPEX/VIPER 型）、Phase 1.7（Artemis 初期運用、複数 PSR・インフラ共有）、
> Phase 2.0（Artemis vs ILRS 制度差）、Phase 2.5（ISRU）、3D Lunarcraft 環境への移行が**具体的に提示**されており、
> 研究的・産業的価値の深化が明確。」
> 「**「アトラクタ問題」「reasoning 均質化問題」「14b モデルへの移行」など、既知の課題と次の改善箇所が
> memo/ と docs/ に詳細に記録されている。**」

→ 「**次に何をやるか**」と「**何がまだ解けていないか**」を、フェーズ表と日付つき memo で示している。
実装済みかどうかは問われていない。

**Project_Gaara(9.0)** — 講評:
> 「REPORT.md と README.md の両方に、現研究を起点として4本（subject substitution、frontier-model relational language、
> BMI as relationship interface、information-life ontology）の**具体的かつ非自明な拡張方向**が示されている。」

→ たった 4 本。ただし「非自明」であることが評価されている。

**near-future-ai-society(9.0)** — 講評:
> 「README に A/B比較実験（内省層あり/なし）が**手順込みで明記**され、`--seed` で初期配置を揃える比較プロトコルが整備されている。」
> 「DESIGN.md には**「含意探索実験 vs 仮説検証実験」という研究方法論上の自覚的な位置付け**もあり、学術的拡張性が高い。」

そして検証レポートが決定的なことを書いている:
> 「事後分析の 6 種ファイル（analysis_report.md 等）は『事後に手動 / Claude 併用で生成』する想定であり、
> **自動生成パイプラインまではコード化されていない**。『構想』としては優れているが『実装済み』ではない点に留意。
> ……厳格に評価すれば 8.5 も合理的範囲だが、**構想の具体性で 9.0 を支える根拠は十分**。」

### 1.3 結論: C 軸は「実装量」ではなく「読み手が未来を辿れるか」で採点されている

| | 実装済み分析パイプライン | ロードマップ文書 | C |
|---|---|---|---|
| nfais | **無し**(手動想定) | 有り(A/B手順 + 6種出力計画 + 次実験6本) | 9.0 |
| Gaara | 有り(analyze_run / score_diversity / summarize_batch) | 有り(future direction 4本) | 9.0 |
| lunar | 有り(cli / batch / aggregate / report / review) | 有り(Phase 1.6→2.5 表 + memo 18本) | 9.5 |
| **shibuya-sim** | **有り**(detect_emergence / aggregate_runs 等 12本) | **無し(README プレースホルダ)** | **8.0** |

**shibuya-sim は実装で勝ちながら文書で負けている。**
本選ではこの1点だけで +1.0 が確定的に取れる。

## 2. B 軸(世界設定)— 10.0 は「実在ミッション/実在制度からの逆算」で出る

shibuya-sim の B=9.0 は**満点でこそないが、講評は極めて肯定的**:

> 「デモ的な抽象都市ではなく、社会科学研究としてのオリジナリティと実問題への接続が極めて明瞭。」
> 「`data/pois.geojson` — 40KBの実OSM POIキャッシュが同梱され実地性が担保される」

一方 lunar_agents が 10.0 を取った理由は:

> 「現実の LUPEX・Artemis・ILRS・Chang'e 7 等の**ミッションから逆算した**極めて独自性の高いシナリオ。」
> 「`CLAUDE.md` — 『シミュレーションは国際月探査ロードマップ（LUPEX・Artemis・Chang'e 7等）から
> **逆算した5類型のミッション**に対応する。』」
> 「複数シナリオ（water_exploration / sample_return_micro / south_pole_survival_survey）で**フェーズ別の検証が可能**。」
> 「**商業・宇宙開発・社会科学（情報の非対称性、ICT インフラ共有、制度差）への発展余地が明確**で、極めて高い分析価値を持つ。」

ただし検証レポートは 10.0 に留保を付けている:
> 「やや誇張気味: 『商業・宇宙開発・社会科学への発展余地』は CLAUDE.md の Phase 2.0/2.5 ロードマップに
> 記載されているとはいえ、**現状実装は Phase 1.5 までであり、満点根拠としては将来計画にやや依存**している。
> 9.0-9.5 でも整合する。」

**→ B=10.0 は「世界の作り込み」だけでなく、「その世界が現実のどの制度・どのミッション・どの学問領域に
接続するかを名指しで書く」ことで取られている。** そして採点者はその接続文が**将来計画でも加点している**。

nfais の B=9.0 も同型で、
> 「AI規制法・再認証義務・新世代置換・市民の死を巡る責任議論など、
> **現実の AI ガバナンス論点をそのまま圧力源に落とし込んでいる**」
と、現実論点との対応を評価されている(検証レポートは 9.5 への上方修正余地ありと記載)。

### shibuya-sim への含意

現行 shibuya-simulation は第1回の shibuya-sim から大きく進化しており、
屋内 SFM 人流・組織/経済・関係内生化・ラベル伝播・選挙・SNS を持つ。
これらを「渋谷が舞台の面白いシム」ではなく、
**「どの実在制度・実在統計・実在研究領域から逆算したのか」を名指しで書く**だけで B は 9.5〜10.0 帯に届きうる。
既に `docs/research/` に shibuya-population / shibuya-government / shibuya-organizations /
odpt-integration / lexicon-ipf-shibuya 等の実地調査が積まれており、素材は揃っている。
**足りないのはトップレベル文書での「逆算の宣言」である。**

## 3. A 軸(創発設計)— shibuya は既に高い。10.0 に必要なのは「診断器」

shibuya-sim の A=9.0 は lunar_agents(8.5)を上回る。減点箇所は一点だけ:

> 「`src/simulation.py:329-336` — 「Choose stay when … prefer to move」というやや方向付けのある一文が含まれる
> （**減点要因の軽微なヒント**）」

検証レポートはこれをさらに厳しく見ている:
> 「むしろ『prefer to move』は単なるヒントではなく、`"most people don't stand still without reason"` という
> **明確な行動誘導文**で、創発設計の純度を若干損なう側面はある。減点幅は小（-0.5以下）。」

lunar_agents の A=8.5 も同種の減点(persona description のテキスト性、Navigation Guidance、
boundary WARNING 文)であり、**「行動を方向づける自然文が1つでもあれば A は 10 にならない」**というのが採点の実態。

### では Project_Gaara はなぜ 10.0 だったか

Gaara は「方向づけ文を消した」だけではない。**方向づけが起きていないことを測る装置を作った**:

> 「**さらに「ドローン化／解釈化」を区別する診断器（`score_diversity.py`）まで備え、
> 創発の有無自体を反証可能な形で測定する設計になっている。**」

`OPERATING_PRINCIPLES.md` に**閾値を事前宣言**している:
- ドローン署名: 1〜2カテゴリが粒子の **≥80%** を占める
- 解釈署名: **≥4 カテゴリ存在し、かつ最大カテゴリ <40%**

そして「見かけの多様性」を明示的に失敗モードとして定義している:
> **Failure mode 1 — Surface diversity, drone underneath.** ... **Drone with synonyms is still drone.**
> **Failure mode 2 — Random divergence, no coherence.** *Noise is not interpretation.*

### shibuya-sim への含意(A で 10 を狙う道)

1. **プロンプト内の残存誘導文をゼロにする**。`"most people don't stand still without reason"` 型の文は、
   環境側のコスト(移動コスト・滞留コスト)に置き換える。lunar の言い方を借りれば
   **「言葉ではなく世界の構造が LLM の行動を変える」**。
2. **「創発している/していない」の閾値をデータを見る前に宣言する**。
   shibuya には既に `detect_emergence.py`(架空POI / 集合注目 / 規範発話)があるが、
   講評は「stdlib-only の正規表現＋類似度ベースで**保守的**」と減点方向に評価している。
   **閾値と失敗モード(=「これは創発ではない」の定義)を文書化する**ことが、指標を増やすより効く。
3. 加えて Gaara の失敗モード定義は shibuya の **no-fingerprint 原則の検算装置**になる。
   「行動指示を書いていない」を主張するのではなく、
   「**指示が漏れていたらこの指標がこう振れるはずで、実際そうならなかった**」という形にできる。

## 4. D 軸(技術実装)— 4チーム全員 9.0。差は付いていない

全員が同じ理由で 9.0 に留まっている:

| チーム | 減点理由 |
|---|---|
| shibuya-sim | `src/simulation.py` 約1000行が肥大化(prompt構築/IO/apply phase が同一ファイル) |
| lunar_agents | `environments/lunar_2d/agent.py` **1,997行** |
| Project_Gaara | LLM 呼び出しが同期直列 / structured output 未使用 / 分類器が正規表現で脆い |
| nfais | 旧 `main.py` 残存 / dead code / ORIGIN 不変のコードレベル防御が無い |

**→ D で 10 を取ったチームは1つもない(全提出物中でも本調査範囲では確認できず)。
D は「取りに行く軸」ではなく「落とさない軸」。**
巨大ファイルの分割は D の減点を消すが、それ以上の伸びしろは薄い。
本選で 1 点使うなら A か B か C に投じるべき。

なお、D で共通して**加点**されているのは以下:
- 構造化 JSON 強制 + 頑健なパーサ + フォールバック(4チーム全員)
- 多層メモリ(4チーム全員。shibuya は rolling / current_goal / relationships の3層)
- 同期2フェーズ(収集→適用)によるレース排除(4チーム全員)
- seed 決定性 + config_snapshot / manifest 出力(4チーム全員)

**これらは既に「上位帯の前提条件」であり、差別化要因ではない。**
差が付くとすれば lunar の `parse_status` 4値 + `parse_fallback_rate>0.05` によるラン除外方針のような、
**「観測の信頼性をラン採否の機械判定に落とし込む」レベルの工夫**である
(講評は総評で「LLM 出力解析の徹底した observability」を優れている点の筆頭級に挙げた)。

## 5. 上位3チームに共通する4つの型

軸別の分析とは別に、3チームの提出物を横断して見える共通の作法。

### 型1: 自分の主張を弱める事実を、自分で先に書く

- lunar: 「C7 の介入は厳密には 2 変数（コミットメント進捗の常時表示 + micro 化）で、**両者の寄与は分離されていない**」
- Gaara: `CORRECTION — interception score was 1st-attacker-biased` — 指標が主張に有利すぎたことを暴き、
  **前回の結論を明示的に撤回**して指標を差し替えた。
- nfais: 「**提示文が効果を示唆していた（suggestive）**……行動変化は指示追従（要求特性）と分離できない」
  「これは**構成上そうなるよう作った決定論モデル＝発見でなく face validity**」

→ 講評はこれを「物語性」「研究方法論として誠実」「反証可能」と表現して**加点している**。

### 型2: 「うまくいかなかった仮説」を成功例と同格で並べる

- lunar: アトラクタ問題の表(C1=base を延々 verify / C4=過去行動の繰り返し / C8=移動だけし続ける)
- Gaara: **Hypotheses that didn't deliver** 節(`V_AXES` が多様性最低 / `M_PULSE` が intercept 最悪 /
  sensory 語彙は**西へ 19 単位**動かした = 「Sensory ≠ directional」)
- nfais: `move` 採択 **99.4%** / 方向 `up` **48.4%** の解剖 → 「これは欠陥か、観察対象か」→「**両方です**」

### 型3: 「何を主張しないか」を明示する

- Gaara: `OPERATING_PRINCIPLES.md` の **What this is NOT**
  (最良の swarm-intercept アルゴリズムを作る試みではない / LLM が有意識だという主張ではない /
  特定の結果が解釈を*証明*するという主張ではない)
- nfais: `docs/findings.md` の **主張しないこと**表(現実の責任配分 / MHC 閾値の普遍性 / 制度の現実的必要性)
- lunar: `info_propagation_rate` の docstring 「**Conservative: doesn't prove causation**」

### 型4: 提出物の形式は「論文構造」であって「スライド」ではない

- lunar の提出 PDF(35ページ)は **research-report-hackathon-v2.md を HTML 経由で印刷したもの**
  (ヘッダに `file:///.../research-report-hackathon-v2-designed.html` が焼き込まれている)。
  それで 1 位。
- nfais の提出 PDF(43ページ)は「SIMULATION REPORT」という**デザインされた報告書**で、
  各章に「この章でわかること」「ひとことで言うと」が必ずある。3 位。
- Project_Gaara は**スライドがレビューリポに存在しない**(`slides/` に `02-*` が無い)。
  それでも 1 位。README + REPORT.md + FINDINGS.md + saved_simulations/ の実データだけで 37.0。

→ **スライドの見栄えは順位に効いていない。効いているのは
「Abstract → 問い → 設計原則 → 実験 → 結果 → 限界 → 今後」という論文構造が揃っているか。**

## 6. 結論 — 「35.0 → 37.0 に足りなかったもの」

### 足りなかったもの(確定的に特定できるもの)

| 順位 | 足りなかったもの | 根拠 | 期待増分 |
|---|---|---|---|
| 1 | **README/トップ文書に研究の問いと将来ロードマップが無い** | 講評 C: 「明文化された将来展望文書がない分、ロードマップ提示としては減点要因」 | **+1.0(C)** |
| 2 | **世界設定が「どの実在制度・実在ミッションからの逆算か」を名指ししていない** | 講評 B(lunar 10.0): 「LUPEX・Artemis・ILRS・Chang'e 7 から逆算した5類型」 | +0.5〜1.0(B) |
| 3 | **創発の有無を「事前宣言した閾値」で機械判定する装置が無い** | 講評 A(Gaara 10.0): 「創発の有無自体を反証可能な形で測定する設計」 | +0.5〜1.0(A) |
| 4 | プロンプト内に残る行動誘導文 | 講評 A: 「Choose stay when … prefer to move」/ 検証: 「明確な行動誘導文」 | +0〜0.5(A) |
| 5 | `NotImplementedError` を残したまま未実装宣言をしていない | 講評 C: 「実装するか、READMEで『未実装・将来計画』と明示すると誤解を避けられる」 | C に含む |

### 足りていたもの(=既に上位帯)

- **A 軸の設計思想**: 生データのみ・行動指示なしは lunar_agents(8.5)より高く評価された。
- **B 軸の実地性**: OSM 実 POI + citation 付き人口分布 + 12 アーキタイプ + A/B 対照群は
  Gaara(9.0)・nfais(9.0)と同点。
- **D 軸の実装水準**: 4チーム全員 9.0。構造化 JSON・多層メモリ・2フェーズ同期・seed 決定性は全員が持っている。
- **モジュール分離とツール群**: 検証レポートは C の加点要因として満額に近く評価している。

## 7. 本選提出物への含意

### 7.1 必ず足すもの(コストが低く、効果が確実)

1. **README トップに「研究の問い / 対照群設計 / 創発指標 / 何を主張しないか」の4節を書く。**
   第1回のプレースホルダ放置が -1.0 の直接原因。これは書くだけで消える。
2. **ロードマップ文書を1本置き、README から導線を張る。**
   lunar は Phase 1→1.5→1.6→1.7→2.0→2.5 の表 1 枚で C=9.5。
   shibuya は既に `docs/plans/` と devlog を持っているので、**トップから辿れるようにするだけ**でよい。
   「実装済み / 実装中 / 構想」を列で分けること(nfais は構想だけで 9.0 を取っている)。
3. **未実装機能に「未実装・将来計画」と明記する。**
   `NotImplementedError` を残すなら README で宣言。これも書くだけ。
4. **「主張しないこと」表を作る。**
   3チーム全員がやっており、講評は全員でこれを加点している。
   shibuya の場合: 「実在の渋谷の人流予測ではない」「k* が現実社会の閾値だと主張しない」
   「LLM に意識があるとは主張しない」等。

### 7.2 強調するもの(既にあるが、書かれていないので伝わっていない)

5. **「どの実在制度・実在統計から逆算したか」を B 軸向けに名指しする。**
   国勢調査・ODPT・OSM・渋谷区基本計画・法制度…。
   既に `docs/research/` に 80 本近い実地調査があるので、**その一覧を提出物側に見せる**。
   さらに「この世界設定はメディア社会学 / 組織論 / 政治学 / 都市工学のどの問いに接続するか」を書く。
6. **認知層と物理層の分離を一文で宣言する。**
   Gaara の `cluster.py` docstring(「LLM は速度・粘性・色に触れない」)に相当する宣言を、
   shibuya の SFM 人流と LLM 判断の関係について書く。実装上そうなっていても、書かれていなければ採点されない。
7. **失敗と修正の履歴を提出物の導線に載せる。**
   lunar は `memo/` 18 本の日付つき失敗ログを「物語性」として加点された。
   shibuya には devlog(64バッチ)がある。**これは強力な資産だが、現状は提出物から見えていない可能性が高い。**

### 7.3 新しく作るもの(A で 10 を狙う場合)

8. **創発判定の閾値を事前宣言し、失敗モードを定義する。**
   Gaara 型: 「これは創発ではない」を先に定義する(見かけの多様性 / ランダムノイズ)。
   shibuya の R²(k) 相転移判定についても、**データを見る前に「相転移とみなす条件」を文章化**する。
   これは no-fingerprint 原則の検算装置にもなる。
9. **観測の信頼性をラン採否の機械判定に落とす。**
   lunar 型: `parse_fallback_rate > 0.05` のランは分析に使わない。
   shibuya の k* 掃引は「LLM が本当に決めた行動」だけで計算されるべきで、
   パーサ fallback が混ざると相転移点そのものが人工物になりうる。
10. **残存する行動誘導文を環境コストへ置き換える。**
    lunar の実証: 「言葉ではなく世界の構造が LLM の行動を変える」
    (C3 で環境側にサンプル腐敗・スコアボード・carry 状態を追加したら PSR 探索タイル数が 2 倍)。

### 7.4 やらなくてよいこと

- **スライドのデザイン投資**。Gaara はスライド無しで 1 位、lunar は md の印刷 PDF で 1 位。
  投資するなら「論文構造が揃っているか」に投資する。
- **D 軸の追い込み**。4チーム全員 9.0 で頭打ち。巨大ファイルの分割は減点を消すだけで、伸びない。
- **指標を増やすこと自体**。shibuya は既に 3 指標(架空POI / 集合注目 / 規範発話)を持っており、
  講評は「保守的」と評したが**減点はしていない**。効くのは指標の数ではなく**閾値と失敗モードの宣言**。
