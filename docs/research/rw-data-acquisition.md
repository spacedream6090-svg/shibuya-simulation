## 0. 三行要約

1. **最大の発見: 渋谷区の人流データ（KDDI Location Analyzer 由来）は、Power BI 目視転記ではなく CSV/GeoJSON で機械取得でき、ライセンスは CC BY 4.0 だった。** 既存 `real-world-feedback.md` ②表 #4 の「CSV/API なし・ライセンス未明示」は**本調査で覆る**（§2-5-A）。街路3地点＋エリア5区画 × 属性3（居住者/勤務者/来街者）× 2018年1月〜2024年12月の84か月。`real-world-feedback.md` §3-3 が挙げた要約統計量5つのうち**3つがこれ1本で埋まる**。
2. **有料人流データは不要と判定。** 無料で足りる（§2-6）。加えて Agoop アカデミック版は **2021-09-30 で新規契約終了**、モバイル空間統計は価格非公開かつ学術価格は学校法人前提 — 本チームでは調達経路自体が無い。
3. **自律実装できるのは5ソース**（アメダス・WBGT・渋谷区人流・ODPT・気象庁防災XML）。**ユーザーの手動作業は実質ゼロ〜30分**（新規登録が必要なソースが1つも無い。ODPT は既存キーで足りる）。唯一のハードデッドラインは **アメダスの保持期間10日**（実測確認）＝本選期間中に取り逃すと二度と取れない。

## ② ソース別詳細

各項目 = (1)取得方法 (2)登録手順 (3)費用 (4)ライセンス (5)レート制限・更新 (6)粒度・渋谷カバレッジ (7)自動化難易度

### 2-1. A1: 気象庁アメダス（bosai JSON）

**(1) 取得方法** — 登録不要の HTTP GET。**2026-08-07 に実接続して全て 200 応答を確認済み**。

| 用途 | URL | 実測 |
|---|---|---|
| 最新観測時刻 | `https://www.jma.go.jp/bosai/amedas/data/latest_time.txt` | `2026-08-07T20:30:00+09:00` |
| 観測点マスタ | `https://www.jma.go.jp/bosai/amedas/const/amedastable.json` | 1,286地点 |
| 全国スナップショット | `https://www.jma.go.jp/bosai/amedas/data/map/{yyyymmddhhmmss}.json` | 約350KB / 1,286地点 |
| **地点別3時間ブロック（推奨）** | `https://www.jma.go.jp/bosai/amedas/data/point/{id}/{yyyymmdd}_{HH}.json` | 約9KB / 16タイムスタンプ |

`point/` 形式が推奨。1リクエストで3時間分（10分値×18）が取れ、全国版の1/38のサイズで済む。`{HH}` は `00,03,06,09,12,15,18,21` のいずれか。

取得フィールド実測（44132・2026-08-07 18:00 台）:
`pressure, normalPressure, temp, humidity, snow*, sun10m, sun1h, precipitation10m/1h/3h/24h, windDirection, wind, maxTemp(+Time), minTemp(+Time), gust(+Time)`。
各値は `[値, 品質フラグ]` の2要素配列（フラグ0＝正常）。

**(2) 登録手順** — **不要**。ユーザー作業ゼロ。

**(3) 費用** — 無料。

**(4) ライセンス** — 気象庁ホームページ利用規約＝**公共データ利用規約（第1.0版）**（CC BY 4.0 互換・商用可・**出典明示必須**・加工したらその旨も明記）。https://www.jma.go.jp/jma/kishou/info/coment.html
→ 論文・提出物への掲載可。表記例:「気象庁ホームページ（アメダス）のデータを加工して作成」。
なお本 JSON は「公式 API」として仕様公開されたものではない（気象庁サイトの内部エンドポイント）ため、**予告なく形式が変わり得る**。これは §5 のリスクに計上。

**(5) レート制限・更新頻度** — 明示的な数値制限の記載は見当たらない（`https://www.jma.go.jp/robots.txt` は **404＝クロール制限の宣言なし**を実測）。ただし防災情報XML 側には「1日10GB以上で IP 遮断」の明示があり、同じ気象庁インフラである以上、常識的な間隔を守る。**10分値なので10分間隔以上を空ければ十分**。

**★(5-補) 保持期間 = 約10日（実測・最重要）**
2026-08-07 時点で `point/44132/{date}_12.json` を日付を変えて叩いた結果:

| 日付 | 応答 |
|---|---|
| 2026-08-07 / 08-06 / 08-01 / **07-28** | **200** |
| 2026-07-25 / 07-20 / 07-07 / 06-07 | **404** |

→ 境界は 7/25〜7/28 の間、すなわち **保持は10日**。
**帰結: 本選期間 8/15〜30 のアメダス10分値は、期間中（遅くとも各日から10日以内）に取得しないと永久に失われる。** 過去日を後から埋めたい場合は別系統（`https://www.data.jma.go.jp/stats/etrn/` の日別値・既存 `fetch_weather_history.py` が使用中、または `https://www.data.jma.go.jp/risk/obsdl/` のフォーム経由ダウンロード）に頼ることになり、10分粒度は戻らない。

**(6) 粒度・渋谷カバレッジ** — 10分値。**渋谷区内に気象庁の観測点は無い。** `amedastable.json` 全1,286地点から渋谷駅（35.6580, 139.7016）への距離を計算した実測上位:

| 順 | 距離 | ID | 地点 | 種別 | 観測要素（実測） |
|---|---|---|---|---|---|
| 1 | **5.76 km** | **44132** | **東京**（北の丸公園・千代田区） | A=官署 | 気温・湿度・気圧・風・日照・降水 **全要素** |
| 2 | 8.16 km | 44126 | 世田谷 | C | **降水のみ**（気温なし） |
| 3 | 12.72 km | 46061 | 日吉 | C | 降水のみ |
| 4 | 13.37 km | 44071 | 練馬 | C | 気温・湿度・風・日照・降水 |
| 5 | 13.64 km | 44166 | 羽田 | C | 気温・風・降水（湿度なし） |

→ **気温を持つ最寄は 44132「東京」の5.76km一択**。世田谷は8kmと近いが降水しか観測していないため代替にならない。
**注意（既存 `fetch_weather_history.py` の CAVEATS と同じ）**: 44132 は 2014-12-02 に大手町から北の丸公園へ移転しており、移転前後で気温系列に不連続がある。また北の丸公園は緑地内のため、**渋谷スクランブル交差点の実効気温より系統的に低い**（都市キャニオン・アスファルト輻射なし）。**補正はしない**（生の観測値を凍結し、バイアスは下流の設計判断とする）。

**(7) 自動化難易度** — **易**。認証なし・JSON・スキーマ安定。既存 `fetch_weather_history.py` の凍結流儀をそのまま踏襲できる。

→ 論文・提出物への掲載可。表記例:「出典: 環境省熱中症予防情報サイト」。

**(5) レート制限・更新頻度** — 明示的な数値制限の記載なし（`robots.txt` は404を実測）。実況は毎正時更新、予測は1日複数回更新（実測ファイルの生成時刻 `2026/08/07 20:25`）。**1時間間隔のポーリングで十分**。

**(6) 粒度・渋谷カバレッジ** — 東京都の提供地点は実測で11点: `44046, 44056, 44071, 44112, 44116, 44132, 44136, 44172, 44226, 44263, 44301`。**渋谷区内の地点は無い。最寄は A1 と同じ 44132「東京」。**


**守る掟（既存の流儀をそのまま継承）**

1. **APIキーは環境変数のみ。** コード・文書・ログ・`_meta`・成果物に値を書かない。マスク表示（`fetch_odpt.py` と同型）。
2. **オフライン取得 → 静的凍結 → シミュはキャッシュのみ読む。** `src/` は `data/realworld/` を**一切参照しない**。シミュ実行中のネットワークI/Oは禁止（`odpt-integration.md` §(c)-1）。
3. **`_meta` に出典・ライセンス・取得時刻・件数・欠測数を必ず埋める**（`fetch_weather_history.py` と同型）。
4. **取れなかったら捏造しない。** §5 参照。
5. **生データと派生データを分離。** `data/realworld/`（生）と、較正用に整形した派生物は別ディレクトリ・別スクリプト。

### 4-2. 取得スケジュールと頻度

| ソース | 頻度 | 後追い可否 | 根拠 |
|---|---|---|---|
| A1 アメダス | **1日1回**（`point/{id}/{date}_{HH}.json` を8ブロック＝計8リクエスト/日） | **不可（10日で消える）** | 実測（§2-1） |
| A2 WBGT 実況 | 1日1回（月次累積ファイルを1本） | **可**（月末に1回でも全部入る） | 実測（§2-2） |
| A2 WBGT 予測 | 1日1回（3時間値×18コマ） | 不可（上書きされる） | 実測 |
| A3 渋谷区人流 | **期間中に1回**（月次データ） | 可 | 実測（§2-3） |
| A4 ODPT 静的（時刻表・乗降人員） | **期間中に1回** | 可 | `odpt-integration.md` |
| A4 ODPT リアルタイム（在線・運行情報） | **60〜120秒**（取得する日だけ） | **不可** | `dct:valid`=5分（実測） |
| A5 防災XML | 1時間（長期フィード `_l`） | 数日は可 | 「数日間の全入電を掲載」 |

**リクエスト総量の見積（1日あたり）**: アメダス8 + WBGT 2 + 防災XML 24 ≒ **34リクエスト/日**。
ODPT リアルタイムを終日回す場合のみ 720〜1,440リクエスト/日が加わる。**在線は「較正に使う数日だけ」に限定する**のが妥当（`real-world-feedback.md` §1-5 条件5「取得期間を必要最小限に」と同じ思想）。

**実行方式** — 次のいずれか。ユーザーの好みで選ぶ。
- **(a) 手動日次実行**（推奨・最も安全）: `python scripts/rw_fetch/fetch_all.py` を1日1回叩く。所要数秒。失敗が即座に見える。
- **(b) Windows タスクスケジューラ**: 毎日固定時刻に (a) を起動。取り逃し防止に強いが、失敗が静かに積み上がるので **§5 の取得台帳が必須**。
- ODPT リアルタイムだけは別コマンド（`--realtime --minutes 120` 等）で必要な時間帯だけ回す。

### 4-3. 8/12 フリーズとの関係

**取得スクリプトはフリーズ対象外**と整理する。根拠:

| | 対象 | 理由 |
|---|---|---|
| フリーズ対象 | `src/` `conf/` `data/`（シミュが読む既存ファイル） | シミュの挙動・決定論・ゴールデンに影響する |
| **フリーズ対象外** | **`scripts/rw_fetch/` と `data/realworld/`** | **シミュ本体が一切読まない。**`src/` からの参照ゼロ・`conf/` へのキー追加ゼロ。ゴールデン（`golden_baseline_l1.json`）・状態ハッシュチェーンに触れない |

**この整理が成り立つ条件（実装時に機械検査で固定すべき）**:
1. `src/` 配下に `data/realworld` および `rw_fetch` への参照が存在しないことを AST/grep で固定（既存の `traces.py` で `city`/`graph` 不参照を AST 固定したのと同型）
2. `conf/config.yaml` に本件のキーを**追加しない**（ゼロタッチ。IF-E の `src`/`conf`/`registry` 読み取り専用と同型）
3. 較正で得たパラメータを本ランに入れる場合は、**フリーズ前に `conf` へ値として確定**させる（＝L1較正の成果物は「数値」であって「取得スクリプト」ではない）。フリーズ後に取得したデータは **L2事後検証（何も動かさない）にのみ使う**

→ **8/15〜30 の取得作業はフリーズを侵さない。** 事後検証は `real-world-feedback.md` §3-4 のとおり「論文で最も安全に主張できる層」であり、フリーズ後に走らせるのが正しい。

### 4-4. 規模見積

| モジュール | 概算行数 | テスト | 難所 |
|---|---|---|---|
| `common.py` | 120 | 8 | リトライ・欠測記録・出典文 |
| `amedas.py` | 150 | 10 | 3時間ブロックの繰り上げ、品質フラグの扱い、10日境界の警告 |
| `wbgt.py` | 130 | 8 | 実況℃ / 予測0.1℃ の**単位差**、空欄セル、月跨ぎ |
| `shibuya_flow.py` | 110 | 6 | DCATフィードから itemId 解決、UTF-8 BOM |
| `odpt_rt.py` | 160 | 10 | `dct:valid` 超過データの破棄、`includeAlighting` の保持、チャレンジ枠/オープン枠の振り分け |
| `jma_xml.py` | 120 | 6 | Atom パース、東京地方の抽出 |
| `fetch_all.py` | 130 | 6 | 取得台帳、部分失敗時の継続 |
| **合計** | **約920行** | **約54テスト** | — |

ネットワークに触れないテスト設計（既存流儀）: 実HTTPは叩かず、**凍結したサンプル応答をフィクスチャとして持つ**（本調査で実データを取得済みなので、そのまま流用できる）。加えて `--verify` サブコマンド（取得済みファイルのスキーマ+SHA-256検証・ネット不使用）を `fetch_weather_history.py` と同型で付ける。

**工数感**: 1〜2バッチ相当。A1+A2+A3（登録不要・スキーマ確定済み・実データ取得済み）を先行させれば、**半バッチで「気象＋人流」の骨格が立つ**。A4リアルタイムは既存 `fetch_odpt.py` の拡張なので相対的に軽い。
