## 0. 3行サマリ

- 外部の一次ソースは**「呼数・モデル・エージェント数」は出すが「1呼あたりの入力/出力トークン」を明示するものはほぼ皆無**(Park 2023=「数千ドル」止まり、AgentSociety/Project Sid=トークン非開示)。唯一 **AGA(Affordable Generative Agents 2024)がトークンを丸ごと開示し、"believability はプロンプト長でなく行動の有限性で決まる/トークンを 30〜43% に削っても人間らしさは落ちない"** という本件に直結する結論を出している。
- 自プロジェクト実測: **入力プロンプト**は既定 ~900字(≈530tok)/本番リッチ ~1,770字(≈1,040tok)、**出力**(キャッシュ実測)は発話系 ~50〜100tok・plan ~160〜260tok・内省(思考除外の最終JSON)~140〜250tok。**現行 320 は発話には十分だが plan がしばしば天井に当たる**;**1200 は思考モードには妥当だが 4b で最終JSONが空になる(全体の 11〜13%)**。
- 推奨: 発話 **256〜384**(SNS投稿はもっと短く 160〜200 でよい)、plan は**専用に 384〜512**、内省 **思考ONの 4b は 1500〜2048 に増やして最終JSONの飢餓を防ぐ**/大型モデルは 1000〜1500 で足りうる。「増やすほど良い」は文献上否定されているので、**量より配分(少数リッチ vs 多数チープ)を実験で切り分けるのが本筋**。

### 外部調査から読み取れる相場観

1. **入力 >> 出力**。開示のある唯一の実測(AGA ベースライン)で **出力トークン ≈ 入力の 7%**。会話/内省の生成物は短く、コストと文脈窓は**入力(ペルソナ+記憶想起+状況)側で決まる**。→ 自プロジェクトの実測(出力/入力 ≈ 0.1〜0.3)と整合。
2. **「呼の種類」が品質に効く。「トークン量」は早く飽和する。** Park は reflection という**呼種**の有無が品質を左右すると示し、AGA は**トークン量を大幅に削っても believability は落ちない**と定量で示した。ユーザーの懸念「多すぎる冗長は無益」は文献側で支持される。
3. **大規模系(10k体級)はトークンを開示しない。** スケールは分散配線(Ray/asyncio/接続再利用)で解き、1呼トークンは論文の関心外。→ 相場は「小さく保ち、呼数×並列で回す」。

## 2. 自プロジェクト実測(読み取りのみ)

### 2.1 方法

- `src/society/cognition/deliberate.py::build_prompt` と `reflection.py::_DEEP_REFLECT_TASK` を読み、**mock backend で `Simulation` を実際に走らせ**、`sim.llm.generate` をラップして**実プロンプト文字数**を purpose(`rng_key` 先頭 = deliberate / plan / reflect / recall)別に採取。
  - 既定 config: seed=42, 10体, 288step。
  - 本番リッチ config: `conf/production.yaml`(calendar/weather/relations/inner_life/recursion/tools.equip_all/variety_hint 等 ON), seed=42, 30体, 288step。
- 出力側は `runs/*/llm_cache.jsonl`(実 ollama 応答が保存されている run)を集計。**保存されるのは `data["response"]`(=最終JSON)のみ**で、`think=True` の**思考トレースはキャッシュに残らない**(`ollama.py` L41)。→ 内省の"真の生成量"は下表より大きい(思考が別途 1200 予算を食う)。
- トークン換算はユーザー指定の **~1.7 文字/トークン**(=tok≈chars/1.7)。ただし qwen3 の日本語は実際にはもっと密(かな/漢字は ~1.0〜1.5 字/tok)で、逆に JSON 雛形・英字は疎(~4 字/tok)。**文字数が実測値・トークンは概算(±30% 程度)**と理解のこと。

読み取り:

- **発話系の出力は短い**(典型 50〜130 tok、p90 でも ~240 tok)。現行 `max_tokens=320`(≈540字)は**発話・投稿・DM には十分な余裕**で、天井に当たることはまれ。むしろ SNS 投稿は短文が望ましく、320 は**やや過大**。
- **plan が 320 の天井に近い**。plan 出力は最大 466〜531 字(≈275〜310 tok)で、**320 token 予算(≈540字)にしばしば接近→時に途中切れ**。plan は `model.max_tokens` を共用(`planning.py` L92)しているのが原因。**plan に専用の大きめ予算が要る**。

- 8b は空がほぼ無く(1/117)最終JSONも安定 → **モデルが大きいほど固定予算でも破綻しにくい**。

## 3. 推奨値

### 3.1 現行 320 / 1200 の妥当性評価

| 項目 | 評価 | 根拠 |
|---|---|---|
| deliberate `max_tokens=320` | **妥当〜やや過大** | 出力典型 50〜130tok、p90 ~240tok。天井当たりまれ。SNS 投稿はもっと短くてよい |
| plan(320 共用) | **不足気味** | 出力が 275〜310tok まで伸び 320 天井に接近=途中切れの温床。専用予算が要る |
| reflect `reflect_max_tokens=1200`(think=True) | **4b では不足しうる / 大型では妥当〜過大** | 最終JSONは 140〜250tok だが思考が同予算を消費。4b で空応答 11〜18% |
| recall `max_tokens=100` | **妥当** | 一言想起=極小出力。過不足なし |

### 3.2 推奨レンジ(purpose 別)

| purpose | 推奨 `max_tokens` | 根拠・狙い |
|---|---|---|
| speak / dm(会話) | **256〜320** | 現状で十分。下げても品質不変(AGA)。冗長抑制なら 256 |
| **post(SNS投稿)** | **160〜200**(purpose分離を推奨) | SNS は短文が自然。短予算は"らしさ"を上げつつ throughput も上げる |
| coin_label / propose 等(制度・造語) | **320〜384** | やや長い理由文が要ることがある |
| **plan(専用化を推奨)** | **384〜512** | 2〜5項目の構造化出力。320 では途中切れ。専用予算で確実に閉じる |
| **reflect(think=True)** | **4b: 1500〜2048 / 8b以上: 1000〜1500** | 思考予算の飢餓で最終JSONが空になるのを防ぐ。大型は密なので削れる |
| recall | **100(据置)** | 変更不要 |

補足: これらは**別々の `max_tokens` を purpose 別に持てる seam があると効く**(現状 deliberate/plan は `model.max_tokens` を共用)。導入可否は**実装前にユーザー合意が必要**(本ドキュメントは提案のみ)。

### 3.3 現地 qwen3:4b と 本選大型モデルの違い(注意点)

- **思考の冗長さが違う**。4b は思考モードで冗長化・ループしやすく固定予算で最終JSONが飢える → **4b は reflect 予算を厚め(≥1500)に**。大型は思考が密・構造化が安定 → **同品質をより小さい予算で**(reflect 1000〜1500、発話 256 でも可)。
- **入力側は大型で余裕が増す**。本番リッチ入力 ~1,400tok は大型の文脈窓に対し軽微。入力を削る動機は薄い(削るなら記憶想起の件数調整が筋で、トークン上限ではない)。
- **vLLM の throughput は出力トークン数が支配**(prefill は安く、decode は1トークンずつ)。本選で 7GPU 群を回すなら、**出力キャップ(特に reflect)の右サイズ化がスループットの主レバー**。入力を削るより出力を締める方が効く。
- **キャッシュ整合**: `max_tokens`/`think` は cache key に含まれる(`cache.py` L32)ので、予算を変えると別キー=再生成。予算変更を伴う比較ランは**キャッシュを共有しない**(=決定論は保たれるが実LLM再走が要る)。

### 3.4 文献に基づく設計原則(ユーザーの問題意識への回答)

- 「トークンを増やせば情報量=行動品質が上がる」は **AGA が定量に否定**(30〜43% に削っても Likert 不変)。**限界効用は早く飽和**する。→ 予算は"足りる最小"に置き、余ったGPUは**呼数×並列(=より多くのエージェント/step)**に振るのが相場に合う。
- 品質を上げたいなら**トークン量でなく (i) 呼種(reflection/planning の有無・質) (ii) プロンプト内容(記憶想起の的確さ・多様性ヒント) (iii) 行動の有限性を破る機構**(既に variety_hint/inner_life 等で着手済)に投資するのが文献の教え。
- 「トークン制限で思考の LOD(リッチ思考/簡単思考)を作る」構想は妥当かつ**低コストで実験可能**(§4)。ただし**効果は実LLM でしか出ない**(mock は予算に関係なく固定長を返すため、LOD 掃引は ollama/vLLM で回す必要がある)。

## 4. 実験設計(リサーチのみ・実装禁止)

> 共通前提: mock では出力長が予算に反応しない → **本群は実LLM(ollama/vLLM)必須**。`max_tokens` は cache key に入る(§3.3)ので各水準は独立キャッシュ=決定論は各 seed で保たれる。トークン上限は**呼を増減しない**=**R1(呼数は k 非依存)を壊さない**(上限は出力長のみ変える)。新 stream の追加は不要=**決定論の「新 stream 1 draw・既定 OFF」性に抵触しない**。

### 4.1 エージェント別ランダムトークン制限による最適量探索

- **割り当て**: 各エージェントに初期化時 1 回、発話系キャップを付与し**run 全体で固定**(=個体レベルの思考LOD)。値は covariate としてログ。
- **分布の候補**:
  - **離散水準(第一推奨)**: 例 `{96, 160, 256, 384, 512}` tok。用量反応(dose-response)が解釈しやすく、水準あたりの反復数を確保でき ANOVA/回帰がクリーン。まずこれで曲線の形を掴む。
  - **対数一様(補助)**: `LogUniform(64, 1024)`。品質が飽和する(=低予算側に興味が集中する)ため対数間隔が情報効率的。連続曲線の微細形状を見る第2アームとして。
  - 実務: **離散を主・対数一様を従**の二段。
- **従属変数(行動品質)**:
  - 既存の **Y_external 成分**(transmission / label_adopt / new_relations / sns_reach / 世界改変アクション)= k* パイプラインをそのまま流用。
  - **JSON パース成功率 / fallback 率**(=途中切れの直接プロキシ。§2.3 の空応答率)。
  - **発話多様性**(distinct n-gram、自己反復率。sim は既に反復注意を出す)・語彙richness。
  - **行動の有限性曲線**(累積 distinct アクション種の時間推移。AGA Fig.7 型)= "リッチ思考が行動レパートリーを本当に広げるか"の検証。
  - LLM 審判 believability(AGA 型 5件法)は**オフライン評価に限定**(プロジェクト方針: 審判を因果ループに入れない)。
- **必要シード数**: 5水準×(10〜100体)で、エージェントを分析単位にすれば 100体×5=20/セルで足りるが、**seed でクラスタ相関補正**が要る。ラン seed は既存慣行(s1..s5 / s7/s13/s42)に倣い **≥5 seed**。
- **k との関係**: トークンキャップは **k(writeback)とは直交な別因子**。掃引中は **k を固定(または均衡)**して交絡を避ける。キャップは呼数を変えない=R1 は各セルで維持。

### 4.2 「思考の質(トークン)× 量(発火頻度)」直交設計 — どちらが行動に効くか

- **2因子**:
  - **Q_quality = 1呼の出力予算(思考LOD)**: 例 `{低=128, 高=512}`。
  - **Q_quantity = 発火頻度**: `drive.threshold`(または `drive.weights`)で `{低頻度, 高頻度}`。
- **2×2(または連続直交)**: 2因子を**個体ごとに独立割り当て**して相関を~0 に設計(ユーザー要望の「相関を低くしてどちらが効くか」)。
  - **主効果** = 「リッチ思考」と「多く考えること」のどちらが Y_external/世界改変に効くか。
  - **交互作用** = 両者が補完(相乗)か代替(頭打ち)か。
  - 連続版: (予算, 閾値) を相関≈0 の同時分布からサンプル→ Y を両者で標準化回帰(標準化βで相対寄与)。
- **交絡対策(重要)**: 発火頻度↑は単純に「出力総量↑」を意味しうる(§外部調査の"呼種が効く"と同型の compute 交絡)。**総トークン(予算×頻度)をセル間でマッチした compute-matched アーム**を1本置くと、"**固定予算を少数リッチに配るか多数チープに配るか**"という**配分の純粋比較**になり、「世界改変を生むのはどちらの配分か」を最もクリーンに検定できる。あるいは総呼数を covariate としてログ。
- **必要シード数**: 2×2×5 seed = 20 ラン(個体割り当てなら少なめ+seed クラスタ補正)。
- **R1/決定論への適合**: 発火頻度は**設計因子として意図的に変える**(k に紐づかない)。**k は固定**して内部結合チャネルの交絡を排除。予算・閾値は"パラメータ"であって"追加の乱数 draw"ではない=各セルは seed で決定論。**新 stream 不要=決定論の既定挙動に非干渉**。
