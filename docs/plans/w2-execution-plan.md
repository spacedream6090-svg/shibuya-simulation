## §0 一行のまとめ

**ルールベースでしか動かないエージェントをゼロにする**。在場25万の全員が「朝に計画し(LLM)・
自分の計画を生きて・出来事に応じて考え直し(LLM)・夜に振り返る(LLM)」。SoA配列は状態の持ち方の
最適化にすぎず、認知には関与しない。予算は A5000×7 で **LLM 12-15h/シミュ日 → 10シミュ日 ≈ 5.5-6.5壁日**
(エンジンとの重畳前提)。可否ラインは従来どおり**背景状態のSoA化でエンジン単価 0.0002s/agent-step 級**。

## §1 設計の核: 「全員思考」モデル

### 1.1 何を捨てるか
million-scale §2 の旧3tier設計では、背景13-15万人は「統計スケジュール駆動・LLMなし」= ルールベース
専用層だった。ユーザー差し戻し(2026-07-19)「個々人の思考は全体に大きく関係する。ルールベースで
しか動かないエージェントはなくしたい」を受け、**この層を廃止**する。

### 1.2 何に置き換えるか — 思考の「階層」ではなく「頻度の連続体」
在場する全員に以下を保証する:

1. **朝の計画(LLM・全員)**: 各自がその日の予定を短いLLM呼び出しで立てる(~600in/200out)。
   出力は機械実行可能な日課スケジュールにコンパイルされる。
2. **日中 = 自己計画駆動の実行**: エンジンが実行するのは固定ルールではなく**本人が朝に立てた計画**。
   移動・勤務・買い物・休憩は全て「自分のLLM思考の産物」の実行。
3. **顕著性駆動の追加熟慮(LLM・全員に開かれる)**: 既存 drive ゲート(発話量・関係変化・造語接触・
   地位変化などの観測可能量)を全員に適用。「何かが起きている人」に思考予算が自然に厚く配分される。
   組織形成の渦中の人・ファウンダー前駆は自動的に高頻度になる。予算総量は N 比例。
4. **夜の内省(LLM・全員)**: 一日を振り返り記憶(day_summary・beliefs)へ書き戻す。

**一日の流れの例**(観光客・特に何も起きない日): 朝「センター街と宮下パークを回って夕方に帰る」と
計画(LLM 1回)→ 日中はその計画どおり移動・滞在(エンジン実行・顕著性イベントなし)→ 夜「渋谷は
人が多かった。また来たい」と内省(LLM 1回)。**この人の一日はLLM 2回だが、全てが本人の思考に発する**。
同じ日に路上ライブに遭遇していれば顕著性ゲートが開き、立ち止まるか・SNSに書くかの熟慮が挟まる。

### 1.3 SoAとの関係 — hydrate機構
- SoA(numpy構造体配列)は**状態の置き場**であり認知の等級ではない。全員の位置・スケジュール・
  所持金はSoA行に置かれ、move・在圏判定・混雑寄与は全員一括のベクトル演算(これがエンジン単価
  0.0002 の源泉)。
- LLM発火時(朝・夜・顕著性熟慮)は、SoA行+記憶サイドテーブルから **フル状態を復元(hydrate)**
  してプロンプトを構築し、結果(計画・記憶・信念)を書き戻して**脱水(dehydrate)**する。
- 旧設計の「動的昇格」に相当する処理はこの hydrate であり、**履歴の後付け問題は発生しない**
  (全員が毎日、朝計画と夜内省による連続した認知履歴を持つため。§3.1 参照)。

### 1.4 予算検算(A5000×7・prefix cache 実効 ~38req/s・在場25万)
| 項目 | 呼数/シミュ日 | 時間 |
|---|---:|---:|
| 朝計画(全員・短プロンプト) | 250,000 | ~1.5-1.8h |
| 夜内省(全員・短プロンプト) | 250,000 | ~1.5-1.8h |
| 日中の顕著性熟慮(平均~6回/人日) | ~1,500,000 | ~9-11h |
| **LLM合計** | **~2,000,000** | **~12-15h/シミュ日** |

- エンジン(背景SoA 0.0002達成時)~12h/シミュ日は**LLMと重畳実行**(非同期発行)で壁時間に
  ほぼ隠れる → **wall ≈ 14-15h/シミュ日 → 10シミュ日 ≈ 5.5-6.5壁日**。
- 重畳が取れない場合(直列)は ~26h/シミュ日 → ~11壁日。重畳実行は P2 の設計要件に含める(§6リスク)。
- 参考: 旧3tier設計のLLMは~2h/日だった。全員思考は**LLM負荷を約7倍**にするが、それでも
  フル密度天井(5.4M呼=30h超)の37%であり、A5000×7の24hに収まる。

### 1.5 正直なトレードオフ — 思考密度
日中熟慮の平均 ~6回/人日は、較正済み200体ラン(21.6呼/人日)の **~28%**。会話の応答性・きめ細かさは
200体ランより粗くなる。ただし配分は一様ではなく顕著性駆動なので、**観測対象(組織形成核・ファウンダー
前駆・その近傍)は自然に200体密度へ近づき、静かな一日の人が薄くなる** — 現実の注意配分と同型。

**密度の増幅策(採否は実測後・どちらも合格条件つき)**:
- (a) 顕著性中位帯の熟慮を小型モデル(qwen3-1.7b級・~10倍スループット)へ。**ブラインドA/Bで
  判別不能が採用条件**(過去の「<2B不採用」決定の再訪であることを明記。不合格なら不採用のまま)。
- (b) 類似状況のバッチ推論(同一プロンプト骨格の同時発行でprefix cache効率↑)。

## §2 現行システムとの差分(何がどう変わるか)

| 領域 | 現行 | 全員思考後 |
|---|---|---|
| LLM発火上限 | `lod.max_llm_per_step=300`(固定・Nが増えると密度が薄まる) | 朝・夜=全員保証+日中=N比例予算の顕著性配分 |
| 日中の行動決定 | 全員が毎stepエンジンのルーチン+LLM層のみ熟慮 | 全員が自分の朝計画を実行+顕著性で熟慮 |
| 状態の持ち方 | 全員フルAgentオブジェクト(~103KB/体) | SoA行+記憶サイドテーブル・発火時hydrate |
| 在場の決め方 | 起動時 `n_agents` 固定 | presence純関数で日次ローテーション(実測曲線追従) |
| ペルソナ | 300名簿 | 100万プール(95%決定論生成・LLMは2-5%) |
| 組織台帳 | 52組織 | ~1.1万(経済センサス分布駆動) |
| 観測解析 | 全件RAM読み(10⁸件で破綻) | row-group逐次ストリーミング |

**変わらないもの**: R1ドクトリン(新機能=新streamのみ・既定OFF=ゴールデンL1バイト一致・
呼数k-blind・no-fingerprint)/ 決定論(seed・stream純関数)/ 議員名簿制(from_roster)/
検証プロトコル(mock ≤24stepスモーク・実LLMフルランはしない)。

## §3 影響分析(本書の主目的)

### 3.1 研究への影響
- **✅ 「動的昇格のk\*交絡」(million-scale §7-5 で"未解決の核"・要ユーザー決定とした問題)が構造的に
  解消**: 旧設計では背景→前景昇格時に「過去の履歴が薄い個体」が生まれ、無名からのファウンダー
  立ち上がり経路を実験デザインが殺す懸念があった。全員思考では全員が毎日の計画・内省・記憶を
  連続的に持つため、**誰がファウンダーになっても認知履歴が繋がっている**。ユーザーの直観
  (「個々人の思考は全体に効く」)と研究の妥当性がここで一致する。
- **✅ 組織形成・ファウンダー観察**: 顕著性駆動の予算配分は「渦中の人ほど思考が厚い」= 観測解像度が
  対象を自動追尾する。組織形成イベントの前後の思考ログが全員分残る。
- **⚠️ 本番ランの位置づけ**: 本番10日ランは**k掃引なしの単一条件・観察ラン**として扱う(k\*・R²(k)の
  データは従来どおり較正済み小規模掃引で取得)。全員思考の思考密度不均一(顕著性依存)は観察ランでは
  現実の注意配分の再現だが、k掃引に混ぜると交絡になるため**掃引系の実験には持ち込まない**。→ §7 確認事項1。
- **⚠️ 思考密度28%の解釈**: 日中熟慮が200体較正比で薄い分、「会話の質・偶発的な深い対話」は本番ランで
  過小になり得る。集団現象(語彙普及・混雑・組織化)は在場数が支配するため影響は小さい見込みだが、
  個人史の細部は前景近傍以外で粗くなる。

### 3.2 性能・ハードへの影響
- **LLM**: ~2.0M呼/シミュ日(旧3tier比 ~7倍・フル密度天井比 37%)。A5000×7 prefix cache実効
  ~38req/s で 12-15h/シミュ日。**短プロンプト(朝・夜)はスループットがさらに出る**ため上振れ余地あり。
- **エンジン**: 可否ラインは不変=**背景状態SoA化で 0.0002s/agent-step**(未達なら25万同時は不成立・
  §6縮退)。全員思考はエンジン側には「計画スケジュールの実行器」を足すだけで単価への影響は軽微。
- **重畳実行が新たな必須要件**: LLM 12-15h+エンジン12hを直列にすると26h超/日。step内の発火を
  非同期バッチ発行し、エンジンの物理演算と重ねる(P2)。
- **本選機での実測が前提**: 38req/s は推定(±50%)。Day-0ベンチ(P7)で置換するまで壁日数は確定しない。

### 3.3 メモリ・状態への影響(旧試算からの変更点)
- **全員が記憶を持つため、million-scale §4.2-C(2.3GB)は成り立たなくなる**。在場25万が episodes を
  育てると最悪 ~26GB級(§4.2-B'相当)。対策: 夜内省で day_summary へ圧縮+非前景の episodes 上限を
  小さく(例: 30件)取り、**~10-15GB を目標**。単ノードRAMで可(本選機の実RAM確認は P7 宿題に追加)。
- checkpoint/resume: SoA=numpy直dump・記憶サイドテーブル=pickle・presence/tier=純関数で保存不要。
  `config_hash` を `pool.size`+`present_cap` ベースへ置換(resume不変性)。
- 観測テキスト量: 朝計画+夜内省 50万件/日 ×10日 = 500万テキスト(~10億トークン級・zstdで数GB)。
  **保存ポリシー(全文は前景+無作為サンプル、他は要約+ハッシュ)を P4 で決める** → §7 確認事項3。

### 3.4 既存コード・テストへの影響
| ファイル | 変更内容 | ゴールデンへの影響 |
|---|---|---|
| `engine/scheduler.py`・`simulation.py` | 朝計画/夜内省フェーズ・N比例予算・hydrate境界・非同期発行 | 全て `pool.enabled`/`thinking.everyone` 既定OFFの新分岐=OFF時バイト一致 |
| `world/background.py`(新規) | SoA配列・一括move/在圏/混雑 | 新規ファイル=影響なし |
| `agents/agent.py`・`memory.py` | スリム状態・hydrate/dehydrate・記憶上限 | 省略可能引数+既定値=現行挙動 |
| cognition(計画コンパイラ新規) | 朝計画テキスト→実行可能スケジュール(構造化出力+失敗時再試行) | 新規 |
| `conf/production.yaml` | pool/thinking ブロック追加(**既存ブロックにin-place統合**=重複キー事故防止) | production はゴールデン対象外 |
| `observer/schema.py` | 新kind(day_plan・plan_step・hydrate等)事前登録 | 追加のみ |
| tests | R1呼数予算式テスト・hydrate往復の状態保存性・resume L1一致・presence曲線追従 | 既存51+α本は全green維持が検収条件 |

- **ローテーション(P3)と全員思考(P2)は agent-core 変更**であり、既定OFFでも配線の通り道が
  既存パスに触れる。ここが回帰リスクの最大点 → 検収は毎回フルpytest+ゴールデン比較(§5)。

### 3.5 データ整備への影響
- ペルソナ100万(P5): 95%以上は決定論生成(IPF・組織台帳需要駆動・匿名合成)。LLM生成は2-5万体のみ
  (一括バッチ・本ラン外・A100級なら0.1-0.2h/A5000でも1h未満)。**議員ペルソナ名簿もここで投入**
  (現状は from_roster が警告フォールバック中)。
- 組織台帳(P6): 52→~1.1万。従業者ペルソナの需要源+就業先POI割付。**P5はP6の出力に依存**。
- 在場実測曲線(納品済み `data/jinryu/shibuya_concurrent_144step_curve.csv`)がローテーションの
  目標曲線(平日昼ピーク37.2万・深夜8.5万)。

## §6 リスクと縮退線

| リスク | 影響 | 対処 |
|---|---|---|
| **c_bg が 0.0002 に届かない**(最大の未知数・leanは300体mockの下限値) | 25万同時が不成立 | present_cap を 25万→10万→5万と段階縮小(**プールは100万維持**・presenceが純関数なのでcap変更は他に波及しない)。10万なら全員思考LLMも~0.8M呼=~6hに軽くなる |
