# Claude Code 指示書：観察ランと検証ランの二重化

以下をそのまま Claude Code に渡してください。段階ごとに分けてあります。**一度に全部渡さず、Phase 0 から順に渡してください。**

---

## 共通の前置き（毎回の冒頭に付ける）

このリポジトリは渋谷を舞台にした LLM マルチエージェント社会シミュレーションです。既に R1 ドクトリンという設計規約が存在します。すなわち、新機能は既定 OFF であること、既定 OFF 時にゴールデンランと L1 バイト一致すること、LLM 呼び出し回数 k に世界状態が依存しないこと、no-fingerprint（実験条件がエージェントから観測可能な痕跡を残さないこと）、乱数は用途ごとに専用 stream を使うこと。これから依頼する作業は、この規約を破壊せずその上位互換として拡張するものです。**既存のゴールデンテストが通らなくなる変更は、いかなる理由があっても採用しないでください。**

作業前に必ず既存のテストスイートを実行し、green であることを確認してから着手してください。各 Phase の完了時にも再実行し、既存テストが 1 本も落ちていないことを確認してください。落ちた場合は原因を報告し、勝手にテスト側を修正しないでください。

実装方針として、**テストを先に書いてください**。各 Phase に受け入れ基準（T1〜T8）を示しているので、それを満たす失敗するテストを先に追加し、その後で実装してください。

## Phase 0：記録と再生（最優先・8/8 までに必須）

### 背景と狙い

本選期間は観察ランに集中したいので、実行速度を落とす完全決定論化は後回しにします。その代わり、**再現できないランでも、後から必ず再生できる**状態にします。非決定性の発生源は LLM 推論のみであり、その入出力を漏れなく記録すれば、記録済み応答を差し込むことで世界の側は決定論的に再生できる、という考え方です。

### 実装してほしいもの

**(1) 実行層の抽象化**

`Clock` / `RandomSource` / `LLMClient` / `Journal` の 4 つを注入可能なインターフェースとして切り出し、シミュレーションコアがこれ以外の経路で時刻・乱数・ネットワークに触れないようにしてください。既存コードで `datetime.now()` やモジュールレベルの `random` を直接呼んでいる箇所があれば列挙して報告し、置換案を出してから置換してください。挙動が変わる可能性がある箇所は独断で変えず、必ず報告してください。

**(2) LLM キャッシュ層**

すべての LLM 呼び出しを content-addressed なキャッシュ経由にしてください。キーは、messages の canonical JSON（キー順を固定し、浮動小数は固定桁の十進表記に正規化）、モデル ID、サンプリングパラメータ、プロンプトテンプレートのハッシュ、これらを連結したハッシュとします。

実行モードを 3 つ設けてください。`FREE` はキャッシュミス時に推論を実行して書き込む（速度優先）。`STRICT` も同様だが、二度目以降のランでは全ヒットする。`REPLAY` は**キャッシュミス時に例外を投げて即座に停止**します。

ここが最重要です。**REPLAY モードでキャッシュミスした際に新規推論へフォールバックする実装は、絶対に書かないでください。** 静かに非再現性が混入し、検証装置としての価値がゼロになります。フォールバックが「親切」に見える場面があっても実装せず、エラーメッセージにミスしたキーと該当 step・agent_id を出して停止してください。

**(3) ジャーナル層**

append-only の記録層を実装してください。step 単位で index を張り、圧縮して保存します。記録内容は、全 LLM 呼び出しの入出力全文とメタデータ、各エージェントの各 step の意思決定（選択行動・移動先 POI・発話 ID・対話相手）、世界状態の差分、step ごとの状態ハッシュ、実行時の全スイッチ状態です。

容量設計として、世界状態の full snapshot 間隔は設定可能にしてください。ただし **LLM の入出力全文の記録だけは、いかなる設定でも省略できないようにしてください**。容量が逼迫した場合に削るのは snapshot 側です。

本選は 10 日連続ランを想定しているので、想定容量を概算して報告してください。エージェント数と step 数から見積もり、圧縮率の実測値を添えてください。

**(4) 状態ハッシュチェーン**

各 step の終了時に、世界状態の canonical シリアライズに対するハッシュを計算し、前 step のハッシュを混ぜてチェーンにしてください。シリアライズでは、dict と set はキーでソートしてから直列化し、浮動小数は固定桁の十進表記に正規化し、集約計算の順序を固定してください。

**(5) run manifest**

各ランの開始時に、コードの git SHA、設定ハッシュ、run_seed、モデル ID とウェイトのハッシュ、プロンプトテンプレートのハッシュ、指標定義のハッシュ、全スイッチ状態、環境差分 ID、実行モード、開始時刻を JSON で出力してください。

**(6) 指標定義の凍結**

指標の定義を設定ファイルではなくコードとして `metrics/` 配下に集約し、そのディレクトリの正規化ハッシュを `metrics_spec_hash` として算出して manifest に埋め込んでください。指標コードが 1 文字でも変われば hash が変わるようにします。

現時点で凍結すべき指標は次の 3 つです。判定基準（閾値）は私が後で埋めるので、**閾値を空欄のまま必須項目として定義し、未設定ならラン開始時にエラーで停止する**設計にしてください。

- 語彙の専門化スコア（対照条件との差分で判定する形にすること）
- 信念・噂の分岐：シミュレータが保持する真偽の地上真実に対する各エージェントの信念距離、および検証行動を取った個体の分離
- 円環の閉じ（下方因果）：規範成立後に新規 presence したエージェント（その規範の形成に不参加）の行動が、成立前の新規参入者と比べてどれだけ変化したか

### 受け入れ基準（テストとして書くこと）

- T2：FREE ランを短く実行し、そのジャーナルで REPLAY したとき、全 step の意思決定が完全一致すること
- T3：全スイッチ OFF で既存ゴールデンと L1 バイト一致すること
- T5：ジャーナルから 1 レコードを意図的に削除したとき、REPLAY が即座に fail すること
- T7：指標コードを 1 文字変更したとき `metrics_spec_hash` が変わること
- T8：コアコード内に `datetime.now()`、グローバル RNG、未ソートの dict 反復が存在しないことを静的検査で確認すること（lint ルールとして追加し、CI に組み込むこと）

## Phase 1：対照条件（本選前半に並行）

以下のアブレーションスイッチを実装してください。**すべて既定 OFF、全 OFF 時に既存ゴールデンと L1 バイト一致**を維持してください。これは R1 ドクトリンの要求です。

- `ablate.llm_off`：LLM を使わず、ルールベースの行動選択にフォールバックする。ルールは既存のニーズ充足ロジックと POI 選好から構成し、新規の凝ったヒューリスティックは足さないこと（比較のベースラインなので、素朴であることに価値がある）
- `ablate.propagation_off`：発話は通常どおり生成するが、他エージェントの文脈には一切入らない。**LLM 呼び出し回数を変えないこと**（k 非依存を保つため、発話生成そのものは実行する）
- `ablate.cognitive_tier`：llm.fleet の割当を強制的に下位ティアへ落とす。段階を指定できるようにすること
- `ablate.shuffle_partners`：対話相手を関係グラフではなくランダムに選ぶ

各スイッチについて、ON にしたときにエージェント側から条件が観測可能な痕跡が生まれていないか（no-fingerprint 違反）を自己点検し、報告してください。特に `propagation_off` は、発話が返ってこないことでエージェントが状況の異常を推論できてしまう可能性があるので、実装方針を先に提案してから着手してください。

### 受け入れ基準
- T3・T4 が引き続き通ること（全 OFF でゴールデン一致、k 非依存）

## Phase 2：完全決定論化（余力があれば）

`STRICT` モードで、seed のみから世界状態がバイト一致で再現される状態にしてください。

- 乱数は `derive(run_seed, purpose, agent_id, step)` による決定論的な派生のみを使い、グローバル RNG を完全に排除する
- エージェントの並列評価は許すが、結果の world state への適用は必ずバリア後に `agent_id` 昇順で行う
- 環境差分 `env.variant_id` を実装する。**ラン開始時に固定され、途中で変更できない設計にすること**。時系列途中の介入は指紋になるため実装しないでください

### 受け入れ基準
- T1：同一 seed で STRICT を 2 回実行し、状態ハッシュチェーンが完全一致
- T6：Scheduler の並列度を 1 と N で変えても状態ハッシュが一致
