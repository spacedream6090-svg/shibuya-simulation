# Claude Code 指示書：機能フラグ体系と検証装置の実装

そのまま Claude Code に渡せる形で書いています。**Part A から順に、一度に一つずつ渡してください。**

---

## 共通の前置き（毎回の冒頭に付ける）

このリポジトリは渋谷を舞台にした LLM マルチエージェント社会シミュレーションです。既に R1 ドクトリンという設計規約があります。新機能は既定 OFF であること、既定 OFF 時にゴールデンランと L1 バイト一致すること、LLM 呼び出し回数 k に世界状態が依存しないこと、no-fingerprint（実験条件がエージェント側から観測可能な痕跡を残さないこと）、乱数は用途ごとに専用 stream を使うこと。今回の作業はこれを破壊せず拡張するものです。既存のゴールデンテストが落ちる変更は採用しないでください。落ちた場合はテスト側を修正せず、原因を報告してください。

各 Part の着手前に、変更予定のファイル一覧と設計方針を先に提示してください。私の確認後に実装に入ってください。スコープ外のリファクタリングはしないでください。

## Part A：機能フラグと再現性等級

### 狙い

実験再現性を担保できない実装も**積極的に入れます**。観察ランでは面白いものを全部載せたい。ただし、載せたものを対照実験のときに確実に外せる必要があります。そこで「再現性を担保するかどうか」を実装の是非の判断基準にせず、**機能ごとの属性として宣言させ、ランのモードで自動的に取捨する**構造にします。

### 実装してほしいもの

**(1) 機能レジストリ**

すべての切り替え可能な機能を一箇所のレジストリに登録し、各機能に次のメタデータを持たせてください。

- `id`：機能識別子
- `repro_tier`：再現性等級。次の三段階
  - `strict`：seed のみから決定論的に再現できる
  - `journal`：単体では非決定だが、入出力を記録すれば事後に再生できる（LLM 応答など）
  - `none`：記録しても再生できない（実時間依存、外部 API、GPU のバッチ非決定性に直接依存する処理、非決定的な並列マージなど）
- `default`：既定値。**必ず OFF**
- `affects_k`：LLM 呼び出し回数を変えるか
- `fingerprint_risk`：エージェント側から観測されうるか（`none` / `possible` / `known`）
- `description`：何をする機能か

**(2) ランモードによる自動取捨**

ランのモードを三つ設けてください。

- `observe`：`none` まで全等級を許可。本選の観察ラン用。全部盛りにできる
- `journal`：`journal` まで許可。事後再生可能な範囲での観察
- `verify`：`strict` のみ許可。対照実験・アブレーション用

起動時に、モードが許す等級を超える機能を**自動的に OFF にし、OFF にした機能の一覧をログと run manifest の両方に出力**してください。ユーザーが明示的に ON にした機能がモードによって落とされた場合は、警告として目立つ形で出してください。黙って落とさないこと。

**(3) 機能の設計上の制約（重要）**

`journal` および `none` 等級の機能は、**OFF にしても世界の因果が壊れない層として実装してください**。つまり、コアの行動選択・移動・関係更新がこれらの機能の存在を前提にしてはいけません。ON で豊かになり、OFF で素朴になる、という関係にしてください。

この制約が守られているかを検証するテストを書いてください。`verify` モードで全 `none`/`journal` 機能が落ちた状態でも、シミュレーションが最後まで完走し、世界状態が妥当な範囲に収まることを確認します。

**(4) ラン間比較のガード**

解析ツール側で、`repro_tier` の異なるラン同士を直接比較しようとした場合に**警告を出すか、明示的なフラグなしには比較を拒否**してください。observe ランと verify ランを無自覚に並べて論じるのが一番危険なので、構造的に防ぎます。

**(5) run manifest**

コード git SHA、設定ハッシュ、run_seed、モデル ID、プロンプトテンプレートハッシュ、指標定義ハッシュ、ランモード、有効な機能の一覧と各等級、自動 OFF にされた機能の一覧、環境差分 ID、開始時刻。

### 受け入れ基準

- 全機能 OFF で既存ゴールデンと L1 バイト一致（R1 ドクトリンの維持）
- `affects_k` が false の機能を ON/OFF しても世界状態が不変
- `verify` モードで `none` 等級の機能が必ず OFF になる
- `verify` モードで完走し、世界状態が妥当な範囲に収まる
- 機能を新規登録するとき、`repro_tier` の宣言を忘れると CI が落ちる

## Part B：真偽台帳と信念の測定（最優先）

### 狙い

このシミュレーションで最も強い「人工オラクル」は、噂と信念の分岐です。シミュレータ自身が「実際に何が起きたか」を知っているため、正解が世界の内部に存在します。エージェントの信念が正解からどれだけ離れたか、誰が確かめに行き、誰が受動的に受け入れたかを、観察ではなく距離として測れます。

**これは観察ラン中に記録されていなければ事後に作れないので、本選前に入れる必要があります。**

### 実装してほしいもの

**(1) 真偽台帳（Ground Truth Ledger）**

世界で実際に起きた事実をイベントとして台帳に記録してください。各 fact は、ID、発生 step、発生場所、真の値、直接目撃可能な条件（どの POI にどの時間帯にいれば目撃できたか）を持ちます。

**この台帳は絶対にエージェントから読めないようにしてください。** プロンプト構築経路に台帳への参照が一切入らないことを、静的検査と実行時アサーションの両方で担保してください。ここは実装ミスが最も起きやすく、かつ起きると実験全体が無価値になる箇所です。プロンプト文字列に台帳由来の値が混入していないことを検査するテストを必ず書いてください。

**(2) 信念状態**

各エージェントは fact ごとに信念を持ちます。値、確信度、情報源（エージェント ID / 直接目撃 / インターネットチャネル）、取得 step、検証済みフラグ、伝播経路の親ノード。

これにより情報の伝播木が構成できるようにしてください。誰から誰へ、何 step で、どう変形して伝わったかを事後に辿れることが要件です。

**(3) 検証行動**

エージェントの行動空間に「確かめる」を追加してください。現場の POI へ移動して直接確認する、当事者に直接聞く、インターネットチャネルで裏を取る、の三種類です。実行された場合は検証済みフラグと根拠を記録します。

この行動を取るかどうかはエージェントの判断に委ねてください。**検証しやすくするための誘導をペルソナやプロンプトに入れないこと**。誰が確かめに行くかが観測対象そのものです。

**(4) 指標**

- 信念距離：真値と各エージェントの信念の乖離。時系列とエージェント別
- 検証率：fact ごと、エージェント別
- 訂正の伝播効率：検証済みエージェントと接触した後、相手の信念がどれだけ真値へ動いたか
- 意味ドリフト：伝播木の深さに対する、発話内容の意味的な変形量

## Part C：語彙の専門化と帰無モデル

### 狙い

語彙の専門化は、真偽台帳と違ってオラクルが存在しません。「専門的に見える」は観察結果でしかない。したがって帰無モデルを自前で作り、**差分でしか主張しない**という形にします。

### 実装してほしいもの

**(1) 専門化スコア**

トピッククラスタ内での語彙の狭まり、役割による語彙の分化、時間を通じた特定語彙の持続、この三つを指標化してください。定義は `metrics/` にコードとして置き、後述の凍結対象に含めます。

**(2) 帰無モデルとしての対照スイッチ**

- `ablate.propagation_off`：発話は通常どおり生成するが、他エージェントの文脈には一切入らない。**LLM 呼び出し回数を変えないこと**（発話生成そのものは実行する）。この条件で専門化スコアが落ちなければ、その専門化は相互作用ではなくペルソナのプロンプト由来だったと結論します
- `ablate.shuffle_partners`：対話相手を関係グラフではなくランダムに選ぶ。関係構造が効いているのか、単に会話量が効いているのかを分離します

`propagation_off` は、発話が返ってこないことでエージェントが状況の異常を推論できてしまう可能性があります（fingerprint 違反）。実装方針を先に提案してから着手してください。

## Part D：最小知能水準の測定（認知階層アブレーション）

### 狙い

「その振る舞いは本当に LLM 由来か」を切り分ける実用的な手段はアブレーションしかありません。llm.fleet の認知階層をそのままダイヤルとして使い、**現象ごとに、それが消える知能の下限を測ります**。ルール層まで落としても再現される現象は LLM の手柄ではない、と正直に言えるようにするのが目的です。

### 実装してほしいもの

**(1) `ablate.cognitive_tier`**

llm.fleet の割当を強制的に下位ティアへ上書きするスイッチ。段階は `rule`（LLM を使わずルールベース）/ `small` / `mid` / `full` の四つ。`rule` のルールは既存のニーズ充足ロジックと POI 選好だけで構成し、凝ったヒューリスティックを足さないでください。比較のベースラインなので、素朴であることに価値があります。

**(2) 実時間の漏れ防止**

ティアを変えるとトークン数とレイテンシが変わります。世界時間は必ず sim clock 基準で進め、**実時間の差が世界の挙動に漏れないこと**をテストで担保してください。

**(3) 解析出力**

各現象について、ティアを下げながら現象が消える点を記録し、`minimum_cognitive_tier(phenomenon)` の形で出力する解析スクリプトを用意してください。

## Part E：円環の閉じ（下方因果）の観測

### 狙い

創発を「何かが立ち上がった」で判定すると水掛け論になります。**規範が個体を拘束し返すか**で判定します。この設計には日次 presence 選抜があるので、毎日、その規範の形成に一切参加していないエージェントが新規に流入します。彼らの行動が規範成立の前後で変わるなら、円環は閉じています。

**これも観察ラン中のメタデータが無いと事後に作れないので、本選前に入れてください。**

### 実装してほしいもの

**(1) コホートのタグ付け**

各エージェントについて、初めて presence した step、その時点での規範状態のスナップショット、接触履歴を記録してください。これにより「規範成立前に初参入したコホート」と「成立後に初参入したコホート」を事後に切り分けられるようにします。

**(2) 規範候補の検出**

特定の行動パターン、あるいは特定の表現が、一定閾値以上の頻度で共有された状態を規範候補として検出し、成立 step を記録してください。L3（規範発生）の検出をここに落とし込みます。閾値は後述の凍結対象です。

**(3) 下方因果の測定**

規範成立の前後で初参入したコホートについて、**参入初日の行動分布**を比較してください。成立後コホートの行動が有意に規範側へ寄っていれば、円環が閉じたと判定します。

## Part F：環境差分による介入（余力があれば）

### 狙い

環境は、エージェントから見て外生変数のまま動かないので、**指紋を作らずに介入を撃てる唯一のハンドル**です。時系列途中でショックを入れると指紋になるため実装しません。条件間の差分は並行ランで表現します。

### 実装してほしいもの

`env.variant_id` として、建物・歩道・階段・改札・サイネージ位置・照明・営業時間の差分パッチを定義できるようにしてください。**ラン開始時に固定され、途中で変更できない設計にすること。** 比較は同一 seed・同一ペルソナ選抜の並行ランで行います。

エージェントのプロンプトに variant ID や実験を示唆する語が混入していないことを検査するテストを書いてください。

## Part G：指標の凍結（事前登録）

指標定義を設定ファイルではなくコードとして `metrics/` に集約し、そのディレクトリの正規化ハッシュを `metrics_spec_hash` として算出し、run manifest に埋め込んでください。指標コードが変われば hash が変わり、事後の指標いじりが露見します。

凍結対象は Part B・C・E の指標です。**判定閾値は私が後で埋めるので、空欄のまま必須項目として定義し、未設定ならラン開始時にエラーで停止する設計**にしてください。

レポート出力では、**実装健全性の検証**（ゴールデン一致、k 非依存、fingerprint 検査）と、**現象の由来の検証**（アブレーション差分）を別セクションに分けてください。この二つは種類の違う検証なので、同じ表に混ぜないでください。

## 優先順位（8/8 まで残り 8 日を前提）

観察ラン中に**記録されていないものは事後に作れません**。したがって、この期間に入れるべきは「装置」より先に「観測点」です。

1. **Part B（真偽台帳・信念・伝播木・検証行動）** — 後から絶対に作れない。最優先
2. **Part E(1) のコホートタグ付け** — これも後から作れない。実装量は小さい
3. **Part A（機能フラグと再現性等級）** — 対照ランを回すための土台
4. **Part C(1) と Part G** — 指標定義の凍結
5. **Part C(2)・Part D** — 対照スイッチ。本選前半に並行でよい。対照ランは小規模（人数・日数を絞る）で構わない
6. **Part F** — 余力があれば

この順序を入れ替えないでください。1 と 2 を欠いたまま 10 日回すと、どれだけ良い現象が出ても事後解析の入口がありません。
