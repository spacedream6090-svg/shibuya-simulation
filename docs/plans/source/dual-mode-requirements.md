# 実装要件：観察ランと検証ランの二重化

対象：渋谷 LLM マルチエージェントシミュレーション（AUTOMATA 本選 8/8–8/23 想定）
前提：既存の R1 ドクトリン（新機能は既定 OFF／ゴールデン L1 バイト一致／LLM 呼数 k 非依存／no-fingerprint／専用乱数 stream）を破棄せず、その上位互換として拡張する。

---

## 0. この文書の主張

再現性を担保できないのは実装全体ではなく、**LLM 推論という一点**である。GPU 上のバッチ推論は、同一プロンプト・同一 seed でもバッチ構成や KV キャッシュの状態によって出力が揺れうる。したがって「再現できる実装／できない実装」を二本立てで書くのではなく、**非決定性を LLM 呼び出しの内側に封じ込め、その境界に content-addressed なキャッシュ層を置く**。境界の外側（世界状態・行動選択・指標計算）は完全に決定論にする。

この設計により、同じコアコードのまま次の三つの実行モードが成立する。

| モード | 目的 | 決定性 | 速度 |
|---|---|---|---|
| **FREE** | 本選の観察ラン。現象を見つける | なし（LLM 応答は毎回新規生成） | 最速 |
| **REPLAY** | FREE ランの事後再生・検証 | ジャーナル由来でバイト一致 | 速い |
| **STRICT** | 対照条件・アブレーション | seed のみからバイト一致 | 遅い |

FREE ランは再現できないが、**完全に記録されているので REPLAY で再生できる**。これが「再現性を担保できない実装も、検証可能な形で残す」ということの中身である。

---

## 1. 目的と非目的

### 目的
1. 本選期間中は FREE モードで観察ランを回し、現象の発見に集中できること。
2. 発見した現象について、後から「それは本当に起きたのか／どこから来たのか」を追跡できること。
3. 対照条件（決定論ベースライン、伝播オフ、認知階層ダウン）を同一シードで実行し、比較できること。
4. 指標の定義を実行前に凍結し、事後の指標いじりを不可能にすること。

### 非目的
- LLM 推論そのもののビット単位再現。これは追わない。キャッシュで固定する。
- 本選期間中の k 掃引の完遂。掃引は余力次第の副次のままでよい。
- 3D 可視化・PLATEAU 連携。post-MVP のまま。

## 2. アーキテクチャ要件

### 2.1 実行層の分離

エージェントのロジック・世界のロジックは**モードに一切依存してはならない**。モード差は下記の実行層コンポーネントの実装差替えのみで表現する。

- `Clock`：シミュレーション時刻の唯一の供給源。`datetime.now()` 等の実時刻取得はコアコード内で全面禁止（lint で機械的に検出する）。
- `RandomSource`：用途別 stream を発行する。seed は `derive(run_seed, purpose, agent_id, step)` で決定論的に派生させる。グローバル RNG（`random.random()` 等）はコアコード内で禁止。
- `Scheduler`：エージェントの評価順序を決める。並列実行は許すが、**結果の world state への適用は必ずバリア後に `agent_id` 昇順で行う**。並列度を変えても結果が変わらないこと。
- `LLMClient`：後述のキャッシュ層を必ず経由する。
- `Journal`：後述の記録層。

コアコードが上記以外の経路で外界（時刻・乱数・ネットワーク・ファイル・環境変数）に触れることを禁止する。

### 2.2 LLM キャッシュ層（設計の心臓部）

すべての LLM 呼び出しは、次のキーで content-addressed にキャッシュされる。

```
cache_key = hash(
    canonical_json(messages),   # キー順固定・浮動小数の書式固定
    model_id,
    sampling_params,            # temperature, top_p, max_tokens, seed
    prompt_template_hash
)
```

- **FREE**：キャッシュミス時は推論を実行し、結果を書き込む。ヒットしても再推論してよい（速度優先の設定を許す）。
- **REPLAY**：キャッシュミスは**即座に fail** させる。決して新規推論にフォールバックしてはならない。silent fallback は非再現性を静かに混入させる最悪の失敗モードであり、これを禁止することがこの層の存在理由である。
- **STRICT**：キャッシュミス時は推論を実行し書き込む。二回目以降のランは全ヒットになるので、seed のみからバイト一致で再現される。

キャッシュは run をまたいで共有可能とし、対照条件間で「同じプロンプトには同じ応答」が保証されるようにする。これにより、アブレーションの差分が LLM 応答の揺らぎではなく設計差から来ていることを主張できる。

### 2.3 ジャーナル（記録層）

両モード共通で、以下を append-only に記録する。step 単位で index を張り、圧縮して保存する。

1. 全 LLM 呼び出しの `cache_key` / 入力メッセージ / 出力全文 / モデル ID / サンプリングパラメータ / 所要時間
2. 各エージェントの各 step における意思決定（選択された行動、移動先 POI、発話 ID、対話相手）
3. 世界状態の差分（full snapshot は N step ごと、それ以外は差分）
4. 各 step 終了時の `state_hash`（後述）
5. 対照スイッチの状態、環境差分 ID

ジャーナルの容量が本選 10 日ランで問題になる可能性があるため、**LLM 出力全文の保存は必須、世界状態の full snapshot 間隔は設定可能**とする。容量が逼迫した場合に削るのは snapshot 側であり、LLM 入出力を削ってはならない。

### 2.4 状態ハッシュチェーン

各 step 終了時に、world state の canonical シリアライズに対するハッシュを計算し、前 step のハッシュを混ぜてチェーンにする。

```
state_hash[t] = hash(state_hash[t-1], canonical_serialize(world_state[t]))
```

- dict / set の反復順に依存しないこと（キーでソートしてからシリアライズ）
- 浮動小数は固定桁の十進表記に正規化してからハッシュすること
- 集約計算（合計・平均）の順序を固定すること

このチェーンが、二つのランが「本当に同じだったか」を一行で判定する装置になる。

## 3. 対照条件（アブレーションスイッチ）

以下をすべて実装し、**既定は全 OFF、全 OFF 時は既存ゴールデンと L1 バイト一致**であることを CI で守る。

| スイッチ | 内容 | 検証したいこと |
|---|---|---|
| `ablate.llm_off` | LLM を使わず、ルールベースの行動選択にフォールバック | その現象は LLM 由来か、それとも移動・POI・ニーズの力学だけで出るか |
| `ablate.propagation_off` | 発話は通常どおり生成するが、他エージェントの文脈に一切入らない | 語彙の専門化は相互作用由来か、ペルソナのプロンプト由来か |
| `ablate.cognitive_tier` | llm.fleet の割当を強制的に下位ティアへ落とす（段階指定） | その現象が消える知能の下限はどこか |
| `ablate.shuffle_partners` | 対話相手を関係グラフではなくランダムに選ぶ | 関係構造が効いているのか、単に会話量が効いているのか |
| `env.variant_id` | 建物・歩道・階段・改札・サイネージ位置・照明・営業時間の環境差分セットを指定 | 環境の因果効果 |

`env.variant_id` は**ラン開始時に固定**され、途中で変更できない設計にする。時系列途中の介入は指紋になるため実装しない。条件間の差分は並行ランで表現する。

## 4. 指標の凍結（preregistration）

- 指標の定義は設定ファイルではなく**コードとして** `metrics/` 配下に置き、そのディレクトリの正規化ハッシュを `metrics_spec_hash` として算出する。
- 各ランの manifest に `metrics_spec_hash` を埋め込む。指標コードを後から変えれば hash が変わり、事後の指標いじりが自動的に露見する。
- 少なくとも次の三つを、ラン開始前に判定基準込みで定義しておくこと。
  1. **語彙の専門化**：スコアの定義と、`propagation_off` 条件に対して何点差をもって「相互作用由来」と判定するか
  2. **信念・噂の分岐**：シミュレータが保持する真偽の地上真実に対する、各エージェントの信念距離。検証行動を取った個体とそうでない個体の分離基準
  3. **円環の閉じ（下方因果）**：規範成立後に新規 presence したエージェント（その規範の形成に不参加）の行動が、成立前の新規参入者と比べてどれだけ変化したか。有意と判定する閾値

### run manifest に必ず含める項目

コード git SHA / 設定ハッシュ / run_seed / モデル ID とウェイトハッシュ / プロンプトテンプレートハッシュ / `metrics_spec_hash` / 全アブレーションスイッチ状態 / `env.variant_id` / 実行モード / 開始時刻

## 5. 受け入れ基準

以下はすべて自動テストとして書けること。

- **T1**：同一 seed で STRICT を 2 回実行 → `state_hash` チェーンが完全一致
- **T2**：FREE ランを実施 → 同じジャーナルで REPLAY → 全 step の意思決定（行動・移動先・発話 ID・対話相手）が完全一致
- **T3**：全アブレーションスイッチ OFF → 既存ゴールデンと L1 バイト一致（R1 ドクトリンの維持）
- **T4**：LLM 呼び出し回数 k を変えても、スイッチ OFF 時の世界状態が不変（k 非依存の維持）
- **T5**：ジャーナルから 1 レコードを意図的に削除 → REPLAY が即座に fail する（silent fallback の不在）
- **T6**：`Scheduler` の並列度を 1 と N で変えても `state_hash` が一致
- **T7**：指標コードを 1 文字変更 → `metrics_spec_hash` が変わる
- **T8**：コアコード内に `datetime.now()` / グローバル RNG / 未ソートの dict 反復が存在しないことを静的検査で確認

## 6. 段階と優先順位（8/8 まで残り 8 日を前提）

時間切れになった場合に何を捨てるかを、あらかじめ決めておく。

**Phase 0（8/8 までに必須。これが無いと本選ランの価値が半減する）**
- ジャーナル層（LLM 入出力の完全記録）
- LLM キャッシュ層と REPLAY モード（fail-fast 込み）
- `state_hash` チェーン
- 指標三つの定義凍結と `metrics_spec_hash`
- run manifest

**Phase 1（本選前半、8/8–8/12 に並行して）**
- `ablate.llm_off` と `ablate.propagation_off` の 2 スイッチ
- 各対照条件を、観察ランより小規模（人数・日数を絞る）で最低 1 本ずつ

**Phase 2（余力があれば）**
- STRICT モードの完全決定論化（T1・T6 の達成）
- `ablate.cognitive_tier` / `ablate.shuffle_partners`
- `env.variant_id` による環境差分ラン

Phase 0 さえ通っていれば、本選が観察ラン中心で終わっても、**得られた現象は事後にいくらでも検証できる状態で残る**。逆に Phase 0 を欠いたまま 10 日回すと、どれだけ綺麗な結果が出ても後から検証する手段が無くなる。優先順位を逆にしないこと。
