**本書が新しく出した最重要の 3 つ**:

1. **総量は合っているが mix が壊れている**(来街者 2.6 万人/日 問題)。これは「人数を増やす」ではなく「L2 に出勤率を掛け、L4 の来訪頻度に裾を作る」で総量を保ったまま直る。
2. **姓名が 5,760 通りしかない**(姓 60 × 名 96)。100 万人で**同姓同名が平均 174 人・最大 229 人**(実測)。さらに**名前が出生コホートに条件づいていない**ため「57 歳の花音」「22 歳の幸子」が生じる。日本語話者には一目で分かる破綻で、無料の一次ソース(明治安田生命 生まれ年別名前ベスト10・**1912 年以降**)で直せる。
3. **`occupation` 文字列が事実上の外部 API になっている**。src/ の 15+ テーブルと conf の 11 箇所以上が文字列で名指ししており、**v2 の最大のリスクは分布ではなく語彙の破壊**。§3-2 の「派生欄として残す」設計はこのリスクを回避するために選んだ。

### 2-8. `--fraction` と段階導入の土台

`occupation` 文字列を読んでいるテーブルの実測(§6 に全リスト):

**語彙を作り直すと、これらが全部「静かに」外れる**(例外は出ず、賃金 0 円・職場なし・担い手 0 人になる)。第109/第111 で「conf が名指ししていたのに名簿に 0 人だった警備員 1,397 人・設備保守員 1,033 人」が実在化した件は、まさにこの静かな破綻が実際に起きていた証拠。

⇒ **v2 の規律: `occupation` の語彙は現行 186 語の上位集合に留め、削除しない。** 新しい表現力は全部新欄が担う。移行後に src/ 側を新欄へ寄せるのは**別レーン**(PPv2-G・任意)。

★**`rank`(役職)の作り方**: 役職は**個人属性ではなく組織のピラミッド**なので、**org 単位で配る**のが正しい。台帳は既に `size.employees` と `size.band`(経済センサス 8 区分)を持っているので、
`rank` は「その社の規模帯 → 部長級/課長級/係長級/職長級/その他役職/非役職 の人数」を割り、`i` 番目のスロットに決定論で振る(**乱数ゼロ**・現行のスロット展開 `role = roles[i % len(roles)]` と同じ作法)。
**規模別の正解表は §1-2(d) にそのまま入っている**(1,000人以上 / 100〜999人 / 10〜99人 の 3 区分)。**従業者 2 人の会社に部長は置かない**という整合がこれで自動的に付く(現行台帳は `1-4` 帯が最多)。

★★**設計を誤らせる罠が 2 つあるので §1-2(d) を必ず読むこと**:
- **係長級 / 課長級 = 0.90** — 厳密なピラミッド木ではない(日本企業は係長を置かず課長が直接統括する形が多い)。**素朴な木構造を仮定してはいけない。**
- **国勢調査の「管理的職業従事者」2.1% を役職に使ってはいけない** — その **79.7% は役員**で、被雇用の管理職は全就業者の 0.311% しかない。**賃構の役職区分を使う。**
- **`rank` は年齢に条件づける** — 役員は 30代前半 587 人 → 50代後半 1,736 人と単調増加(§1-2(e))。

★**ついでに見つかった現行の隠れた歪み**: `_build_L2_slots:686` の `role = roles[i % len(roles)]` は**業種内の職種を均等ラウンドロビン**にしている。
たとえば `IT` の roles は 5 種なので各 20%。しかし実データ(§1-2(c))は **専門技術 57.8% / 事務 27.2% / 販売 7.6% / 管理 5.3%**。
⇒ **v2 は `roles` に重みを持たせる。** 重みの正解は第10-3表の `産業 × 職業大分類` 行%から逆算できる。**推測不要。**

### 3-5. ★来街者の水準較正 — 「総量保存で mix を直す」

§1-6 の三点測量の結論:**総量は合っているのに、渋谷に買物・観光で来る人が 1 日 2.6 万人**(実在は ≈13 万人)。
これが「来街者の正確な人数を設定して」への直接の答え。

**原因は 2 つあり、どちらも総量を動かさずに直せる**:

1. **L2 に出勤率が無い。** 経済センサスの `従業者数` は**名簿上の在籍者**で、パート・短時間・シフト・休暇・テレワークを含む。シムは平日に **224,240 人全員**を資格者にしている。
   ★**較正値は今回の bbox 計算から直接出る**: 台帳の従業者 222,849 に対し、bbox の通勤通学流入は ≈163,900。学生ぶん(L3 25,238)を引くと通勤 ≈138,700。
   ⇒ **出勤率 ≒ 138,700 / 222,849 ≈ 0.62**。**これは推測ではなく、経済センサスの「従業者数」と国勢調査の「従業地人口」を同じ bbox で突き合わせた比。**
   (この 0.62 にはパート・シフト非番・休暇・テレワーク・複数事業所計上が全部畳み込まれている。分解するには別の一次データが要る = §7 の残穴。)
2. **L4 の `visit_rate` の裾が薄い。** 現行は log-uniform **[0.003, 0.06]** = 年 1 回〜年 22 回。**「週 2 回来る常連」(0.3/日)が 1 人もいない**。L3 常連(`weekly_2..4`)が 20,000 人だけ担っているが、これはハードコードの固定値。
   ⇒ v2 は **来訪頻度分布そのものを一次データ(人流の再訪頻度分布)に当てる**。

**総量保存の式**(v2 の較正目標):
```
到着(平日) = L2 従業者 222,849 × 出勤率 + L3 + L4 + L5
           ≈ 293,263(改札外流動 FY2024 換算の到着側)+ 徒歩/バス/自転車の流入
```

| | 現行 | v2 目標(bbox 一次統計から) | 倍率 |
|---|---:|---:|---:|
| L2 日次通勤者 | 224,240 | **≈138,700**(出勤率 0.62) | ×0.62 |
| L3(学生+常連) | 25,238 | ≈25,000(据置) | ×1.0 |
| **L4 非定期来街** | **25,946** | **6 万〜13 万**(中心 ≈10 万) | **×3〜5** |
| L5 | 1,258 | 1,258 | — |
| **合計到着** | **276,682** | **≈23 万〜30 万** | — |

★**レンジで置く理由**: 経路 A(bbox 昼間人口 + 鉄道到着の差)= 約 13 万、経路 B(渋谷区 PT 実測 18,000 同時 × 滞在時間換算)= 6〜10 万。**2 経路が一致するのは「桁」であって「値」ではない**ので、単一の点推定を装わない。**中心 10 万・許容 6〜13 万** を較正目標にし、実測レポートには両経路を併記する。

★**L4 を ×5 にする方法は「プールを 5 倍にする」ではない。** 現行は 707,778 人 × 平均 `visit_rate` 0.0190 = 13,461 + revisit ≈12,500。
**平均 `visit_rate` を 0.019 → 0.16 相当まで上げる**(= 頻度分布に「週 1〜2 回来る層」の裾を作る)。プール規模は据え置ける。
**★これはユーザー原理と整合する**: 世界が「今日は 13 万人来い」と決めるのではなく、**個々人の来訪習慣(頻度)が現実的になった結果として 13 万人になる**。

★**二重計上の罠を必ず踏まないこと**(既存資産 [boundary-calibration-data.md](../research/boundary-calibration-data.md) が実測で潰してある):
JR は**乗車人員**・他社は**乗降人員**で数え方が違う / 乗降人員は乗換の通過客を含む / 路線別乗車を同一駅で足すと改札内乗換が二重に入る(JR 内だけで **+5.15%** 過大)。
**渋谷の駅内流動の 65.6% は改札内の乗換で、街には一歩も出ていない。** ⇒ **使うべきは「初乗り・最終降車駅間移動人員」だけ**。

### 3-7. 世帯を先に作る(合成人口の正道)

現行は「個人を作ってから並び順で束ねる」。v2 は逆にする — **MATSim / ActivitySim / Pseudo-PFLOW が採る標準**([presence-endogenization.md](../research/presence-endogenization.md) が既に引いている系譜):

1. 世帯類型の周辺分布(単独 / 夫婦のみ / 夫婦と子 / ひとり親 / その他)と世帯人員分布を統計から取る(§1-1)
2. **世帯を先に生成**し、世帯類型に応じて構成員の年齢・続柄を**同時に**引く(夫婦の年齢差・母の年齢別出生数を制約に)
3. 個人属性(業種・職種・役職)は**世帯内の役割と年齢に条件づけて**引く

これで G1(子どもゼロ)・G2(世帯の年齢整合なし)が同時に解ける。**現行の `_pool_partition`(名簿の連続 n 人を束ねる)はそのまま「世帯 id が名簿に埋まっている」形に置き換わるだけ**で、ランタイム側の変更は小さい。

### 5-3. 推奨順序と最小構成

**推奨順序**: **A(骨格)→ D+D2(受け皿)→ C(世帯)→ B(職業軸)→ F(姓名)→ E+E2(水準)→ G → H**

理由:
- **A を飛ばすと他が空振りする。** 存在しない子ども・存在しない高齢者に機構を足しても実測が動かない(既に `voter_age_min: 18` が 1 人も落とせていない実例がある)。
- **D は A の前提。** 子どもを L1 に入れる前に行き先(保育所・小学校)が要る。
- **C は A+D の後。** 世帯に子どもを入れるには子どもが居て学校がある必要がある。
- **B は独立に進められるが、A と同時に打つとテストの切り分けが困難**になるので後。
- **E は最後。** 在場者数が動く唯一のレーンなので、他が固まってから実測する。

**本選前に 1 セットだけ選ぶなら**: **A + D(+D2) + F**。
- **A** = 「全年齢を実装」への直答。子ども 23,011 人相当と 85+ 8,845 人相当が世界に現れる
- **D** = 「教職員は多すぎ」への直答(教員:職員 1:1 → 4.8:1)+ **A の前提**(子どもの行き先)。D2(保育所)は 0-5 歳を入れるなら必須
- **F** = 最小コストで最大の「見た目の実在感」(同姓同名 174 人と「57 歳の花音」が消える)
- **この 3 つは `scripts/` + `data/` のみ。src/ 不触・conf 不触・呼数ゼロ・golden 不変**(§6-0 で実証)。

★**ただし A を入れた瞬間、§6-4 の年齢依存テーブルが「初めて発火する」**(子ども 0.26%→10%・高齢 1.8%→18.8%)。**A の後は必ず fraction 0.1 で縦煙を焚いて呼数とメモリを実測すること。** これが本計画で唯一「既定 OFF で逃げられない」変更点。

## 8. ユーザー判断待ち

1. **レーンの採否と順序**。最小構成 **A + D(+D2) + F**(本選前・src/conf 不触)/ フル 10 レーン(本選後)のどちらを取るか。

3. **昼間人口をどちらで採るか**: 国勢調査集計 **633,452** と 東京都推計系列 **551,344**(現 `shibuya_population.json` が使用)が方法論違いで食い違う。
4. **出勤率(§3-5)を新パラメタとして入れてよいか**。入れると L2 の日次資格者が減り、在場者数が動く(= 呼数が動く)。

6. **`occupation` 語彙を「削除しない」規律を受け入れるか**。受け入れない場合、src/ 15+ テーブルと conf 11+ 箇所の同時改修が必要になる(= 本選前には不可)。
7. **域外通勤(PPv2-G)の修正を本選前に入れるか**。現状は「**就業者の 55% が出るべきところが 17.5%**・しかも人選が逆」。直すと日中の在場住民が最大 5,000 人減る(呼数・観測に影響)。**あわせて「在宅就業 16.8%」という第 3 の状態を作るか**も判断が要る(現行は out/in の 2 値しかない)。
8. **公務(`PA`)を台帳に新設するか**。渋谷区の常住就業者の 2.65% が公務(2,474 人)だが**台帳に 1 社も無い**。プールの「公務員」21,669 人は L4 の職業タグで、実際に区役所で働いていない。「台帳に無い業種の職業は発明しない」規律に従うなら、**先に区役所・警察署・消防署を org として台帳に入れる**必要がある(§3-6 と同じ順序制約)。
9. **`roles` の均等ラウンドロビンを重み付きに変えるか**(§3-2 末尾)。第10-3表の産業×職業行%から重みが逆算できるので推測は不要だが、**L2 の職種構成が全社で変わる**(= 職業名の分布が動く = §6-3 のテーブル群が影響を受ける)。
10. **`is_foreign` を engine に繋ぐか**(現状は読み手ゼロの死に項目で、`agent.language` と矛盾)。繋ぐなら来街者の外国人比率を 25〜35% に上げる判断も同時に要る(§1-6-d)。
