# LLM呼数予算の再設計(llm-budget-respec)— リサーチ結果と選択肢

> 起案 2026-08-25(本番24c走行中)。ユーザー指示:「呼数capはあくまで**安全上限**であって充足目標ではない。
> 人口(present_cap)と同じく、実使用は需要駆動で決まる仕様にしたい。まずリサーチして案を見せて欲しい」。
> 決定待ち=**本書は提案であり、どの案も未適用**。実測はリサーチ3レーン(コード機構/24c実データ/文献)による。

## 2. 実測で確定した現状(24c・step 0-70)

| 事実 | 実測値 | 出典 |
|---|---|---|
| capは飽和(=配分器化) | 昼帯300/300・plan枠240が46step連続で厳密に240 | journal 21,128件 |
| **自発発火(general)が昼帯ゼロ** | step25以降 n_fires=0。需要は18.7万件/stepまで積み上がり全拒否 | L2 n_drive_requests/n_fires |
| 計画のLLM被覆が崩壊 | plan実行の**79%がLLM無し骨格フォールバック**(step52-65区間)・drop累積901 | L2 plan_fallback_total |
| LLMはstep時間の**9.7%** | step69=2,830sのうちLLM 250-280s。劣化(350→2,830s/9h)は全て非LLM側(土曜流入×物理) | vLLMログburst復元 |
| **艦隊は93-98%遊休** | Waiting=0が全走行で不破・KV≤23%・GPU util 0%。律速=engine.batch_llm.workers:16 | vLLMメトリクス |
| 1呼の実コスト | plan(14B)=1.06s/呼・deliberate/reply(8B)=0.35s/呼(壁時間・w16時) | トークン/秒の二重導出一致 |
| 認知被覆 | **0.11回/人/日**(300×144/400k)= 第118時点(0.173@250k)よりさらに薄い | 算術 |

**機構面**(コード監査): cap内はreply 20%/life(plan+内省)30%/general(自発)50%の三レーン。
**lifeはgeneralの余りを借りられるがgeneralは借りられない**(lod.py:191-207)+フェーズ順でplanが先に走る
→ plan需要(在場全員が毎朝1計画=数千/step)がgeneral枠を毎step食い尽くす=**創発の本体である自発発火が構造的に最初に死ぬ**。
また `lod.max_llm_per_step` は checkpoint の config_hash 照合対象(_VOLATILE_KEYS外)のため、**現行コードでは途中変更をガードが意図的に拒否**する(壊れる状態は無い=ガードのみ)。

  =**今の24c昼帯(自発0)はこの予言の実現形**。
- **需要フロア≈5,222呼/step@400k**(plan+reflect需要47万/日@250kの換算)→ capを「常に非飽和の純粋上限」にするには
  この水準超が必要=7GPU艦隊では非現実的。**現実的な位置づけ=「被覆率ダイヤル+夜間は自然非飽和」**(§4の3で担保)。
- 計画被覆率(life枠×144/400k): cap300=**3.2%**→1,500=**16.2%**→2,500=**27%**→9,259で100%。
- Shadow高認知ラン(代表5k・全決定LLMとの行動一致率=capの忠実度コスト自前実測)は**定義済み未実行**=本選後の宿題。

## 4. 原則の設計への写像(どの案でも共通)

ユーザー原則「cap=安全上限・実使用は需要駆動」を3点で実装する:

1. **capの導出根拠をスループット予算に一本化**: cap値=「LLMに許すstep壁時間」÷「実測1呼コスト」から導く(§5の表)。
2. **需要<capの時間帯は自然に非飽和**(深夜step24-50で実証済みの既存挙動=変更不要)。
   需要>capの時間帯の配給は「reply保証→plan FIFO(18step超で骨格)→自発はdrive降順」の必要度順で続行。
3. **自発枠の保護(新規・本丸)**: 新キー `lod.budget.tiers.life_borrow`(既定true=現行1バイト同一/finals=**false**)で
   planによるgeneral枠の全量借用を止める。plan溢れは既存の骨格フォールバック梯子が受ける(=需要の正直な配給)。

コード変更は2点のみ: ①life_borrowキー(lod.py _take+registry+テスト) ②checkpoint._VOLATILE_KEYSへ
運用キー4つ追加(lod.max_llm_per_step / engine.batch_llm.workers / tiers.reply_share / tiers.life_borrow)
=「観察ランの運用レバー」宣言(決定論ガードの意図的緩和・観察ランのDT定義=厳密再現不要に整合)+宣言テスト。
→ 適用は**直近checkpoint(step72=シミュ内土曜12:00以降、半日毎)からのresume**で進行ロスほぼゼロ。

併せて `engine.batch_llm.workers` **16→32→48の段階引き上げ**を推奨(艦隊遊休93-98%・Waiting=0・KV≤23%の実測余地。
14B系で2-2.5xの短縮見込み=**推定**なので32で一度実測してから48へ)。

## 5. 選択肢(数字は実測1呼コストからの算術・w16=worst case/w48=見込み)

| | **案B 推奨** | 案C | 案D 攻め |
|---|---|---|---|
| cap | **1,500** | 2,500 | 4,000 |
| レーン(reply/life/general) | **300/450/750** | 500/750/1,250 | 800/1,200/2,000 |
| plan被覆率(現3.2%) | **16.2%** | 27% | 43% |
| 自発発火/step(現・昼=0) | **最大750** | 最大1,250 | 最大2,000 |
| 返答保証(現60) | **300** | 500 | 800 |
| 呼/人/日 | **0.54** | 0.90 | 1.44(=DP-U4上端の400k換算) |
| LLM加算/step(w16) | +570s(9.5分)=**不可** | +22分=不可 | +33分=不可 |
| LLM加算/step(w48見込) | **+90-150s** | +300-420s | +630-730s |
| +B2(_apply speak O(N)/LLM発話) | **+40-110s** | +90-250s | +150-400s |
| ETA影響(w48・日あたり) | **+13-17%** | +25-35% | +40-55% |

- **workersの引き上げ(16→32→48)はどの案でも前提**(w16のままでは全案不成立)。2-2.5x短縮は推定のため
  **32で一度実測→48**の段階適用とし、実測が届かなければcapを800-1,000へ縮めて着地(dotlist再変更可が本変更の利点)。
- **案B推奨の理由**: 「昼の自発発火ゼロ」の解消(=本ランの研究主題「自発的な社会行動からの創発」の生命線)+
  計画被覆3.2→16.2%を、ETA+13-17%(2.5-3.3日→2.2-2.9日分)で買う。深夜はLLM律速のため夜step+50-100%が
  コストの主因(帯実測に織り込み済み)。
- 案C/Dは案B適用後2-3hの実測(step時間・RSS・B2実コスト)を見てからdotlistで増額するのが安全
  =「段階点として案B」が本provisionの推奨運用。
- 現状維持(cap300)も選択肢として残る: ETAは最良だが、昼帯の自発発火ゼロ+計画被覆3.2%のまま
  =「朝LLM計画+ルール実行の世界」(proposal-dp-u3が警告した形)を受け入れる判断になる。

## 6. 適用手順(GO後)

1. 実装レーン(Opus・~1-2h): life_borrowキー+_VOLATILE_KEYS 4键+宣言/同値/境界テスト(既定=現行1バイト同一をピン)。
2. フルゲート→スキャン→コミット→サーバーpull(24cは走行継続のまま)。
3. 直近checkpoint確認→24c停止(TERM)→`--resume`+dotlist(新cap/workers/life_borrow=false)→巡航確認(reject/RSS/step時間)。
4. devlogへ「途中変更の事実」を明記(凍結sha256は起動時値・変更時刻とキーを併記=来歴の正直な記録)。
5. 適用後2-3hでpurpose別呼数・n_fires・plan_fallback・step時間を再実測→上振れ余地(案C側)を再判断。

## 7. リスクと正直な限界

- workers 2-2.5xは**推定**(GPU余裕の実測はWaiting=0/KV≤23%まで。並列度を振った制御実験は未実施)→段階適用で吸収。
- B2(_apply speakのO(N)全走査)は自発発話数に線形。案Bの~1-2分/stepは許容圏だが、実測が上振れたら
  generalを段階的に絞る(capはdotlistで再変更可能になるのが本変更の利点)。根治(索引化)は本選後。
- 途中変更は軌道を変える(resume≠straight)=観察ランの定義内だが、24c前半(cap300)と後半で
  呼数レジームが変わることは解析時に区間注記が必要(starvationカウンタのcap混合も同様)。
- recall(agentic_pull)は予算外のまま(内省1件=実呼2)=既存仕様・本変更では触らない。
