# 本番ラン運用ゴール(開始前に固定・2026-08-17)

> 位置づけ: 科学ゴール=U-10事前登録・提出ゴール=submission-goals.md が既に持つ。
> 本書は第3の柱=「ランそのものの運用基準」を開始前に固定する(走行中の後知恵変更を禁じる)。

## 1. ランの成功定義(3条・これ以外をラン中に追加しない)

1. **技術完走**: 10シミュ日を完走する(または§4の打ち切り線内で最長到達)。
2. **観測健全**: L1/サイドカーの欠損なし・保存則PASS・resume発生時も整合(resume==straight検証済みの経路のみ使用)。
3. **中身の評価はラン後に既存文書で行う**: U-10の閾値表+submission-goalsの観測目標バンド。
   ★ランの中身の「良し悪し」をラン中に再定義しない(結果を見てからゴールを動かさない)。

## 2. 不介入原則(観察ランの掟)

世界には手を入れない。**許される介入は技術障害への対処のみ**:
- ①プロセス死→watchdog/手動resume(E4手順) ②資源枯渇(ディスク/RAM)→backup_run経由の退避+再開
- ③vLLMサーバー障害→当該サーバーの再起動(モデル・rev・フラグは凍結値のまま)
- ④Discord報告系の障害→報告側のみ修理(L1不読の設計どおり・シムに触れない)

**禁止**: freeze_config後のconf変更・世界パラメタの調整・「面白くするため」のイベント注入・
特定個体への操作。**全介入をログに残す**(時刻・理由・操作・影響範囲)→RESULTSに全件開示。

## 4. 打ち切り・縮退線(既存決定の参照集約)

- RAM: 実測ピークがRAM線の想定を超え **220GiB接触が視野に入ったら** checkpoint→退避→
  (決定済みなら)mem.relations削減版で再開。250GiB到達を待たない。
- 壁時計: T10外挿が実効枠(W/1.15=167h)を超えるペースならcap縮退(2,500→1,500等・
  ★freeze前に決めた縮退表の範囲でのみ。freeze後のcap変更は「介入」であり§5のラン0扱い)。
- 14Bタイア滞留>1step相当が常態化→(freeze前に宣言した縮退線どおり)6+1へ。ラン中は不可=ラン0扱い。

## 5. 「ラン0」条項(やり直しを許す唯一の窓)

- **開始後24時間(実時間)以内**に致命欠陥(観測の構造的破損・保存則の破れ・parse崩壊
  ・配線事故)が発覚した場合に限り、当該ランを「ラン0=最終リハーサル」と再宣言して
  修正→本番をやり直せる。
- **24時間を過ぎたら完走優先**。以後の欠陥は記録して走り切り、RESULTSに正直に開示する。
- ラン0宣言は理由と発見経緯をdevlogに記録(「結果が気に入らない」は理由として認めない)。
