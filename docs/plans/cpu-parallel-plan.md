## 0. なぜ今1-2コアしか使わないのか(事実)

- エンジンは単一プロセスのPython。支配コスト(v9火炎図・250k夕方)= 物理積分51.3%(SFM/ORCA・
  numpyベクトル化済みだがゾーン逐次)+知覚/カウント27%(純Python+numpy混在)+その他。
- 純Python部はGIL(全スレッドで1本のロック)により**スレッドを増やしても並列にならない**。
  第155監査でC4(ゾーン並列)を「却下寄り」とした根拠がこれ。
- numpy部分はGILを解放するため理論上スレッド並列余地があるが、**解放割合は未実測**。

## 2. エンジン並列化計画(本選後・測定駆動)

R1制約=並列化後もビット同一(または宣言付き変更)。並列reduceは**id順の固定順序**で畳む。

### Phase 0: 計測(0.5日)
- py-spy --native + 簡易実験(numpy演算中のスレッド並列度)で**物理カーネルのGIL解放割合**を実測。
- ここの数字がPhase 1の期待値を決める(解放率高→スレッドで安価に取れる/低→プロセス+共有メモリ必須)。

### Phase 1: ゾーン間スレッド並列(2-4日+物理ベンチ再検証)
- 物理ゾーン(scramble/hachiko/center_gai)は空間的に独立→step内で3ゾーンを
  ThreadPoolExecutorへ(join順固定・書き戻しはゾーンid順)。
- 期待: GIL解放率が高ければ物理51.3%×(1-1/3)≈**step時間-30%前後**。低ければ効果減=Phase 2へ。
- 検証: 基本図±20%・破綻統計・軌跡ビット比較(スレッド化はfloat演算順を変えないため
  ビット同一が狙える=ゾーン内は逐次のまま)。

### Phase 2: 知覚/カウントのfork並列(3-5日)
- C2聴衆列挙・カウント系は話者ごとに独立読み取り→Linuxのfork(copy-on-write)で
  空間索引を共有した読み取り専用ワーカーへ。結果はid順マージ=決定論保存。
- 期待: 27%×(1-1/6)≈**-20%前後**。リスク: プロセス起動/結果回収のオーバーヘッド(バッチ化で回避)。

### Phase 3: SoA+共有メモリ+numba prange(1-2週・GPU移行計画と合流)
- 第133のSoA基盤を物理へ本格適用→shared_memory上の配列をプロセス並列/numba prangeで。
- PENDING既載のGPU移行(CuPy)と同一の前処理=どちらへも進める中間形。
- ここまでやればstep時間は理論上1/3〜1/5圏。ただし数値検証の作法(ビット差の宣言・ベンチ全再測)が本体。

### 本選窓で不可の理由(再掲・正直に)
Phase 1ですら物理ベンチ全再測が必須で、失敗時の切り戻しも含め最短2-4日。走行中のRun Bに
載せる手段もない(リスタート級)。残り~4日の本選窓では割に合わない。
