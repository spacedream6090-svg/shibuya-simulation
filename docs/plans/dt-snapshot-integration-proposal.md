## 1. ユーザー定義への回答

「ある時点の現実の切り取りを舞台にする。同期不要。現実は解像度を高めるデータ収集ツール」——この定義で見ると:

1. **切り取り機構はリポに既にある**。build_map.py の `--osm-date`(Overpass attic query)が道路・建物・POI を
   基準日つきで凍結済み(現行 osm_date=2025-04-01)。「外界をロード時に1回解決して凍結する」作法も
   start_date:auto / seed:auto で既出。**再提案は発明ではなく横展開**。
2. **用語問題(旧 DT-U3)は解消**: Kritzinger の分類は「自動データフローの向き」だけで決まるので、
   事前凍結=Digital Model・日次自動取り込み=Digital Shadow と**正確に自己記述**できる。
   「频度(いつの現実か)×忠実度(どれだけ実データか)」の2軸で数字で言う。
3. **観察ランの再現性緩和(journal 等級)で復活するのは「一方向強制」だけ**。実天候を全員共通の
   環境変数として与える型は、読んだ値を全記録すれば事後再生できる=journal。
   EnKF 等の**状態同化は引き続き不採用**(シム状態を書き換えると内生性の研究が壊れるため。決定論の都合ではない)。

## 2. 推奨設計(調査ノート §4)

- **案A(strict)**: 事前 materialization = `data/snapshot/*.json` に凍結して読む(過去期間・対照実験用)。
- **案B(journal)**: 本選ラン用。日次で snapshot を追記 materialization し resume で取り込む。取り込んだ
  ファイルと SHA-256 を manifest に記録=事後再生可能。**core のネットワーク出口は LLM の1本のまま**。
- 案C(ラン中に core が直接 fetch)は**案Bへ縮退させる**(採らない)。
- 先行文献: Fowler Event Sourcing「External Queries」・Temporal SideEffect・フライトシム天候ファイル駆動
  (MSFS .WPR / X-Plane Historic Weather)・ODD Element 6「Input data」(調査ノート §4.6)。

## 3. S 系列(スナップショット忠実度)と投入提案

詳細表は調査ノート §6.2。**確定済みの第70–78(13.5–15日 vs 暦14日)に余裕は無い**ため、絞って提案:

| レーン | 項目 | 工数 |
|---|---|---:|
| **本選前(承認求む)** | **S0** 入力来歴(inputs[]=SHA-256/出所/ライセンス/取得日時)を run_manifest へ=**第71に相乗り**・**S1** observe.yaml の忠実度是正(広域地図+実ダイヤ明示)・**S2** バス静的表の生成(読み手実装済み)・**S5** 本選期間の実イベント表(world.events_file=機構既存)・**S9** ODD Element 6「Input data」節(文書のみ・査読対策の費用対効果最大) | 計≈1.8日 |

### DT-S1(天候)の判断材料
- 現行 weather.py の8月は合成 `(32,25,雨30%)±3℃` で、**35℃出現率 14.5%・36℃以上は出現不可能・「連続する猛暑」が構造的に出せない**。
  本選10日ラン(8/16–8/26)は 2025 年に東京都心が **10日連続猛暑日**となった 8/18–8/27 とほぼ重なる。
  「8月中旬の渋谷の忠実再現」を名乗るなら天候が支配的要因(realism-first 方針に直結)。
- ただし 3.5-4.5日は **第75(ダンバー)・第78(ablate)と正面競合**。選択肢:
  - **(a) 入れる+第75ダンバーを本選後へ**(推奨: 観察ランにとって環境忠実度>機構実験の順。ただし ID-U1 の
    「ダンバーまで本選前」決定を覆すためユーザー承認必須)
  - (b) 入れる+第78の ablate 4種を本選前半へスリップ(計画済みの許容範囲。装置系が薄くなるリスク)
  - (c) 今回は見送り=本選は合成天候(S4 の取得だけ本選中に実施し、本選後 S3 でリプレイ実験)

## 4. PUB-U1(公開ミラー)への影響 — ライセンスの地雷2件
1. 商業施設6館・渋谷区サイトの情報は「私的利用を超える複製は事前許諾要」=**成果物・公開ミラーへ転載不可**
   (取り込むならデータは非公開ディレクトリ+gitignore)。
2. OSM 由来の店舗テーブルは ODbL の Derivative Database=**配布した瞬間 share-alike 発動**。公開ミラーに
   data/ を含めない現行方針の維持が前提条件になる。
