## 0. デバッグは要るか(答え)

**「デバッグ期間」としては不要**。理由: ①静止木6,656テスト+golden+resume==straightが
毎コミットの型 ②ram計測→SNS完全グラフ根治のように「本番を殺すバグ」はリハーサルの型が
先回りで捕まえる構造が既に回っている ③開始後の「デバッグ」はrun-operations-goals.mdの
不介入原則が禁止し、ラン0条項(24時間窓)だけが唯一のやり直し口。
残っているのはデバッグではなく**計画済みのゲート消化**(下の§1-2)だけ。

## 2. 時間削減(TRIM)— 方法論: 実測してから切る

**原則**: ①二台帳(再現・創発)と提出物に寄与しない機能だけをOFF候補にする ②闇雲に切らず
**step時間の内訳を実測**して大物から(前例: prof10k6で物理74%→A+B+Cで95倍化=最大レバーは
既に消化済み) ③OFFは本選confの1行=R1的に安全・ただし台帳1(再現)を毀損する向きのOFFは
台帳への影響を明記して判断。

### 時間の構造(現在の見積)
- T10 = エンジン27.6-52.2h + LLM 23-42h(cap1,500・5+2)。**LLM側の最大レバーはcap選択**
  (1,500 vs 2,500=±27h)で、これは明朝の判断ラウンドの議題。
- エンジン側はSNS根治で「3.8億エッジのset演算+全走査」が消えた分の高速化が今夜のランで
  実測される(前夜比のstep時間で判定)。

### OFF候補の初期リスト(明朝、実測の数字を付けて判断ラウンドに同梱)
| 候補 | 何を失うか(台帳への影響) | 期待削減 |
|---|---|---|
| indoor_tracks(屋内軌跡サイドカー) | 屋内ミクロ軌跡の再生(提出のビューアは建物内散布で代替可)。台帳影響=小 | ディスク+19GB・I/O |
| memory.parquet(G4)の頻度減(日次→隔日) | メタバース射影の記憶密度。台帳影響=小(本文はL1にもある) | I/O中 |
| l3_snapshots頻度減 | 全量スナップショットの時間解像度 | I/O中 |
| physics zonesのゾーン数絞り | 群集表現の適用範囲(主要交差点は維持)。台帳1の物理再現に影響=**要慎重** | エンジン中 |
| roster.parquet(A13) | 中間日入場者名簿(解析はpoolから再構成可) | I/O小 |
| 犯罪V1/V2の実LLM検証(未消化の診断項目) | 本番では不要=**やらないことにする**(時間削減はランでなく準備側) | 準備半日 |
- **切らないもの(明記)**: llm_journal(day_trace・宣言率監査・再現性の生命線)・llm_cache
  (resume)・G観測サイドカー(創発台帳の主役)・J1 copresence 24(U13)・GTロガーG1-G7の
  骨格(G2剪定禁止)・starvation/causality(健全性観測)。

### 手順
1. **今夜のram再計測ランからstep時間系列を抽出**(SNS根治後の実測ベースライン)。
2. 明朝: 大物順に「OFF候補×期待削減×台帳影響」の表を数字つきで判断ラウンドへ。
3. 承認されたOFFはfinals conf 1行ずつ(freeze前)。golden不変・OFFの理由をconfコメントに。
