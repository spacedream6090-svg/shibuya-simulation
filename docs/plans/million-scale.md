## §1 数値骨格(最初に固定する数字)

### 1.0 前提定数(出典つき)
| 記号 | 値 | 由来 |
|---|---:|---|
| N_concurrent(同時present) | **250,000**(±精密化中。範囲 20-40万) | shibuya-population.md ③平均25万/④ピーク35万 |
| pool(プール総数) | **1,000,000** | shibuya-population.md §8(固定キャスト~28万+来街回転~70万) |
| 発火密度 d | **0.15 呼/agent-step** | 較正 200体 day1=4,293呼 ÷144step÷200 = 0.149。ユーザー「200体密度維持」 |
| steps/シミュ日 | 144(10分刻み) | 全較正ラン共通 |
| 非LLM単価 c(現行レンジ) | **lean 0.00183 / full 0.060**(33倍) | scale-feasibility §4(mock下限 / 本番プロファイル実測) |
| LLM実効レート R_eff | 下表(推定・要本選実測) | estimate_runtime.py FLEET_PRESETS + overhead15% |

**★N比例発火は現行モデルと非連続**: 現行は `lod.max_llm_per_step=300`(固定cap)で **N が増えると
per-capita 密度が落ちる**(25万なら deliberate 密度 ~0.003=ユーザー目標の 1/50)。ユーザーの「0.15密度維持」は
**cap を `0.15×N` に比例拡大**すること。結果、**25万での LLM 呼数は capped モデルの ~12.7倍**になる。
→ scale-feasibility の LLM 試算表(cap前提)は本方針では過小。以下は N比例(cap非飽和)で引き直す。

### 1.1 LLM 呼数/シミュ日(密度 0.15)
```
calls/シミュ日 = N_present × 0.15 × 144 × λ_LOD      λ_LOD = 実効発火倍率(tier割引)
```
| ケース | λ | 呼数/シミュ日 |
|---|---:|---:|
| **全present フル密度(上限=天井)** | 1.000 | **5,400,000** |
| 前景10% + 残90%を1/10 | 0.190 | 1,026,000 |
| 前景4% + 残96%を1/10 | 0.136 | 734,400 |
| **tier実配分(前景1万フル+中景9万を1/10+背景0)** | — | **410,400**(§2で確定) |

### 1.2 LLM 実効レートと時間/シミュ日(7GPU)
R_eff = 7×(req/s/GPU)×spec×apc ÷ 1.15(overhead)。**全て推定**(4B×1300/320 の measured 公開値なし。
本選で `vllm bench serve --random-input-len 1300 --random-output-len 320` 実測必須)。

| フリート | base 呼/s | +spec×1.15 | +spec+apc×2.2 |
|---|---:|---:|---:|
| A100×7 | 48.7 | 56.0 | 123.2 |
| H100×7 | 85.2 | 98.0 | 215.6 |
| A5000×7(本選想定?) | 18.3 | 21.0 | 46.2 |

**LLM 時間/シミュ日(N=25万)**:
| 発火配分 | 呼数/日 | A100×7 base | A100×7 spec+apc | H100×7 spec | H100×7 spec+apc |
|---|---:|---:|---:|---:|---:|
| **全フル密度(天井)** | 5.40M | **30.8h(24h超)** | 12.2h | 15.3h | **7.0h** |
| 前景10% | 1.03M | 5.9h | 2.3h | 2.9h | 1.3h |
| **tier実配分** | 0.41M | 2.3h | 0.9h | **1.2h(A100 spec=2.0h)** | 0.5h |

**読み**: **全present をフル密度で撃つと A100×7 は LLM だけで 24h 超**(prefix cache が効けば 12h に半減)。
H100×7 なら天井でも 7h(spec+apc)。だが LOD tier で中景/背景を割り引けば(§2)**呼数は 0.41M/日 = どのフリートでも 2h 前後**。
= **LLM 側は tier さえ効けば律速にならない。フル密度天井を全数に課さないことが条件**。

### 1.3 非LLM エンジン時間/シミュ日 ← ここが本当の壁(N=25万)
```
engine 秒/シミュ日 = c × N_present × 144      (LOD でも spec でも減らない=全present の物理step)
```
| 単価 c(s/agent-step) | 時間/シミュ日 | 10シミュ日 |
|---:|---:|---:|
| **0.060(現行 full)** | **600h(=25日)** | **250日**(完全に不成立) |
| **0.00183(現行 lean)** | **18.3h** | 7.6日 |
| 0.0012 | 12.0h | 5.0日 |
| 0.0006 | 6.0h | 2.5日 |
| **0.0002(SoA背景目標)** | **1.0h** | 0.4日 |

### 1.4 ★目標エンジン単価の逆算(item1 の核)
- **一様単価で 24h/シミュ日に収める**: `c ≤ 86,400/(250,000×144) = 0.0024 s/agent-step`。
  → lean(0.00183)は**辛うじて通る**(18.3h)。ただし lean は **300体 mock の下限**で、25万で成り立つ保証はない(§7)。
- **serial(engine+LLM)を ~15h/シミュ日=10日で6日 wall に収める**: engine ≤ ~12h → `c ≤ 0.0012`(**lean 未満が必要**)。
- **一様単価は誤誘導**: present の内訳は tier で単価が桁違い。**支配は数の多い背景(25万中15万)**。
  → 操作すべき目標は **背景単価 ≤ 0.0002〜0.0003 s/agent-step**(lean比 ~6-9倍・full比 ~200-300倍の改善)。
  前景(1-2万)は数が少ないので 0.010 のままでよい。**背景をSoA配列化で桁下げできるかが唯一の可否ライン**(§3-b)。

### 1.5 合計と 10シミュ日 wall(tier実配分・H100×7 前提)
| 構成 | engine/日 | LLM/日 | serial 合計/日 | **10シミュ日 wall** |
|---|---:|---:|---:|---:|
| **目標(背景0.0002達成・§2 tier)** | 12.4h | 1.2h | 13.6h | **~5.7日** |
| engine と LLM をオーバーラップ | 12.4h | (隠れる) | 12.4h | ~5.2日 |
| 背景 0.0006 止まり(SoA部分達成) | 22.4h | 1.2h | 23.6h | ~9.8日(綱渡り) |
| 背景 lean 0.00183 のまま(SoA未達) | 65.9h | 1.2h | 67h | **~28日(不成立)** |

→ **10シミュ日を現実的 wall(1週間級)に収める必要条件 = 背景tierのSoA化で c を 0.0002 級へ**。
これが達成できない限り、25万同時は **同時数を段階縮小(§7)**しない限り成立しない。

## §2 認知LOD設計(3tier)

**前提の分離**(agent-lod-deepdive §2-6・§4 の結論を採用): LOD は「**個体を潰す**」のではなく「**個体は保持し
環境/背景の解像度だけ落とす**」方向のみ k\* に無害。以下はその制約下の tier 設計。

### 2.1 三層の定義
| tier | 計算様式 | LLM | 非LLM単価目標 | 想定人数(25万present中) | 対応する現実 |
|---|---|---|---:|---:|---|
| **前景(FG)** | フルLLM・フル物理step・全チャネル・observer記録 | 0.15呼/step(**200体密度**) | ~0.010 | **1〜2万** | 観測対象=組織形成核・ファウンダー前駆+その近傍 |
| **中景(MID)** | routine(非LLM日課)駆動・稀にLLM | ~0.015呼/step(前景の1/10) | ~0.002 | 8〜9万 | 街に居るが観測の主対象でない従業者・来街者 |
| **背景(BG)** | **統計的行動=スケジュール駆動・SoA配列・LLMなし** | 0 | **~0.0002** | 13〜15万 | 群衆の賑わい・混雑密度・語彙普及率の"場"を作る存在 |

**LLM 呼数**(§1.1 の実配分): 前景1万×0.15 + 中景9万×0.015 = 1,500+1,350 = 2,850呼/step ×144 = **410,400呼/シミュ日**。
→ どのフリートでも 2h 前後(§1.2)。**背景は一切撃たない**(=呼数天井 5.4M の 7.6%)。

### 2.2 tier 割当の決め方(R1・k\* 非交絡が絶対条件)
agent-lod-deepdive §4 Q3(Entry 8 の trait裏口)と compute-optimization「前景/背景割当は k非依存・決定論固定」を厳守。

- **既定割当は k非依存・trait非依存の決定論**: `stream("tier", persona_id, day)` 一本で層を引く(traits と無相関)。
  presence(§5)と同型の純関数。→ **k掃引の全条件で同じ人が同じ tier**(共通乱数)= tier が k\* を交絡しない。
- **観測目標の前景固定**: 組織形成・ファウンダー前駆の**近傍**を前景に置く。ただし割当基準は
  **観測可能イベントのみ**(発話量・関係次数・造語採用・地位カウント=drive.py が既に使う no-fingerprint 観測量)で、
  **信念・k・内部状態を読まない**(R1)。→ 「誰が世界を変えるか」の内部条件に触れずに近傍を厚くする。
- **動的昇格の扱い(未解決の核)**: 背景→前景の昇格は「昇格個体の過去が薄い=履歴の後付け」問題を必ず生む
  (agent-lod-deepdive §2-5・Q4)。**ファウンダーが背景から出る経路を殺さない**ためには、
  (i) 候補近傍を**最初から前景/中景に固定**(背景から founder を出さないと割り切る)か、
  (ii) 昇格条件を記録済み状態の決定論関数にし llm_cache を固定して**二段目に高精細リプレイ**(本ランは軽く・
  注目個体を後で再走)か。**どちらを採るかは実装前にユーザー決定**(§7・OPEN)。既定は (i)=静的固定(安全)。

### 2.3 N比例上限との整合
ユーザーの「0.15密度維持」は **前景+中景(=思考する層)に対して**適用する:
```
cap_per_step = 0.15 × N_thinking      N_thinking = FG_count + MID_count（背景は含めない）
```
= 現行 `lod.max_llm_per_step=300`(固定)を **`0.15×N_thinking` の比例式**に置換する seam。
前景は 200体密度をフルに享受し、中景は 1/10、背景は 0。**「200体相当の思考密度」は観測対象(前景)で厳密に保たれ、
背景は思考しない**——これが density維持と計算予算の両立点。cap を N_present(25万)に掛けると LLM が 24h 超(§1.2 天井)なので、
**掛ける対象は N_thinking(=10万級)であることが要**。

### 2.4 R1(k掃引はどの層で成立させるか)
- **k\* は前景tier内でのみ測る**(compute-efficiency Tier 3・agent-lod-deepdive §4 Q1 の採用条件)。
  R²(k) の母集団 = 前景コホート(1-2万)。**統計検出力は現行300体より遥かに大きい**(母集団拡大の利)。
- **前景コホートは k掃引の全条件で同一集合**(`stream("tier")` が k非依存)。→ 「前景だけで測った k\*」の主張範囲は
  「前景と同じ観測解像度で生きた個体について」。背景を母集団から除くことの解釈上の限界は agent-lod-deepdive §4 Q1 の
  未決事項として残る(本書は解消しない)。
- **中景の稀LLM**は k\* の被説明変数(内省=beliefs 書き戻し)に触れないよう、**中景の稀発火は deliberate のみ・reflect は前景限定**
  にするのが安全(reflect のゲートは R1 に直接触れる=scale-audit B9 の警告)。要実装時合意。

## §4 状態・メモリ予算

### 4.1 現行 Agent オブジェクトの概算(agent.py + memory.py 実測構造)
- Agent = `@dataclass`(**__slots__なし・~90フィールド**)+ `MemoryStore`(episodes≤120・buffer≤30・day_summaries=7・relations dict)。
- Episode ~350B(text=日本語30-80字)。150 episode で ~52KB。

| 個体種別 | 概算サイズ | 支配項 |
|---|---:|---|
| フル典型(記憶満載・relations有界60) | **~103 KB** | episodes 52KB + relations 18KB |
| 社交ハブ(relations 無上限2000件) | ~672 KB | relations が支配(B6 LRUで有界化可) |
| **スリム背景/ドーマント** | **~1.5 KB** | id+位置+数フィールドのみ(episodesなし) |

### 4.2 100万プールの RAM 試算
| 設計 | RAM | 判定 |
|---|---:|---|
| A) 全員フルオブジェクト @103KB | **~98 GB** | 単ノードで危険(大ノードでのみ可) |
| B) 思考層10万をフル+残90万スリム | **~11 GB** | 可 |
| B') 思考層25万をフル+残75万スリム | ~26 GB | 可 |
| **C) 前景2万オブジェクト + 背景SoA(numpy行~400B)** | **~2.3 GB** | **推奨**(§3-b と同一設計) |

→ **背景の状態設計 = 必要フィールドだけ**(位置・node・schedule_id・present・所属org・簡易所持金)。
episodes/beliefs/relations は**前景/中景に昇格した個体だけが育てる**。**「リッチ記憶を持つ母集団」に上限**を課す
(10日で"一度でも前景になった"集合が単調増加するため、上限cap+LRUで有界化)。

### 4.3 イベント量と checkpoint
- **イベント量**: 25万present × 1.3 events/agent-step × 144 × 10シミュ日 = **~4.68億件**。
  ディスク(parquet+zstd 100-150B)= **44-65 GB**(保存可)。**未flushなら RAM ~305GB=即破綻** → B2 flush 必須(実施済)。
  背景tierは**イベント記録を間引く**(move_segment・arrive を統計化)必要。
- **checkpoint 戦略**: (i) 前景/中景=個体の記憶・関係・所持金を pickle(有界化 B6/B7 前提)。(ii) 背景SoA=numpy配列を直接dump(軽い)。
  (iii) **presence/tier は `(seed, id, day)` の純関数=保存不要**(persona-pool §5.4・RngHubステートレス)。
  (iv) `config_hash` を `n_agents` 依存から **`pool.size`+`present_cap`** に置換(resumeで不変)。
  (v) **既定OFF後方互換**: `pool.enabled=false` でゴールデンとバイト一致(civil-share=0 と同じ掟)。

## §5 ローテーション/プール(persona-pool.md を100万へ適用)

### 5.1 present とプールの分離(persona-pool §9 の核)
- **present(LLM/計算コスト源)= 25万** と **pool(記憶・アイデンティティ保持源)= 100万** を分離。
  日次プレゼンス `stream("presence", persona_id, day)` の純関数で**当日 present/absent** を層別決定(persona-pool §5)。
- absent = ドーマント(tick/LLMから外れる=**コストゼロ**)。再登場は**同一実体の再活性化**(前回の記憶・関係を保持)。
- **現行の欠落**: 「同時数の数倍プールから日次で誰が入域するか」を選ぶ機構は**未実装**(simulation.py L438 が
  `n_agents` に固定・余剰名簿は具現化されない)。= W2 の新規実装の中心(要 agent-core 合意)。

### 5.2 プール生成コスト(層×方法・persona-pool §3)
100万を**全部LLMで作らない**(manifold collapse・コスト)。層で分担:
| 層 | 主方法 | LLM呼 |
|---|---|---:|
| L1 住民(~3万) | (a) IPF | 0 |
| L2 従業者(需要駆動) | (b) 組織台帳 employees 逆算 + (a) | 0 |
| L3 定期来街(学生=capacity) | (b)+(a)+(d) | 0 |
| L4 非定期来街(回転主層・数十万) | (d) 匿名合成セグメント + (a) | 0 |
| L5 役割・少数の深いL1/L3常連 | (c) LLM一括+人手確認 | **~LLM対象2-5%のみ** |

- **LLM生成はプールの 2-5%(2-5万体)に限定** → 一括バッチ(VS=`build_personas.py::llm_persona`)で **~2-5万呼 = A100×7 spec で 0.1-0.2h**(一回きり・本ラン外)。
  残り95%以上は決定論(IPF/需要駆動/匿名合成)= **LLM負荷ゼロ**。生成は既存 `gen_personas.py`(pool→抽出の2段構造が既存)/`build_personas.py`(IPF+VS)を拡張。

### 5.3 組織台帳 1.1万への拡充(item5)
- 現状 **52組織**(会社42+学校10)vs 実bbox **~11,000-12,000事業所**(現実の1/230)。台帳 `employees` が**従業者ペルソナの需要源**。
- 拡充方法: (i) 経済センサス町丁目別(§shibuya-population 出典)の**産業大分類×従業者規模帯の分布**から
  組織を手続き生成(`build_orgs.py` を分布駆動へ拡張)。(ii) 各組織に `employees`/`roles`/`workplace_poi`/`shift_pattern`。
  (iii) **就業先POI(地図ノード)がボトルネック**(shibuya-population §6)——地図の建物×階に組織を束ねる割付が要る。
- 役割ペルソナ数は台帳+インフラの集計式(persona-pool §4)で確定(店員=Σemployees・駅員/運転士/タクシー/警察=インフラ数×持ち場×shift)。
  **議員=名簿制**(選挙なし・事前決定)は W1-P4 で `assembly.from_roster` 実装済(Entry 20)。

## §7 リスクと未知数(正直な明記・断定しない)

1. **α外挿と密度前提**: 発火密度 0.15 は 200体単一ランの day1 値。25万での per-capita 密度が同一に保てるかは未検証
   (混雑で発話機会が変わる=scale-feasibility §4.3)。deliberate/plan/reflect 比(92.9/7.1)も単一ラン由来。
2. **25万同時×フル機能は未踏**: 先行の最大は OASIS 10万(小モデル・3h/A100×5)・AgentSociety 1万。
   **LLMエージェント社会シミュで25万同時の公開例は無い**。本書の可否は試算——実測で覆り得る。
3. **エンジン目標単価 0.0002 の不確実性**: lean 0.00183 は **300体 mock の下限**で、25万で成り立つ保証はない。
   背景SoA が 0.0002 に届くかは **W2-A の実測でしか分からない**(33倍レンジの真値=最大の未知数)。
4. **LLM req/s は全て推定**(±50%)。本選機スペック未定(A5000級なら LLM時間は A100 の ~2.7倍・§1.2)。
   prefix-cache は接頭辞共有が前提(共有無しで −37%)。spec は飽和運転で 1.0割れもある。
5. **動的昇格の k\* 交絡(未解決の核)**: ファウンダーが背景から出る経路と、昇格個体の履歴の連続性は両立が難しい
   (agent-lod-deepdive §4 Q4)。既定は静的固定(安全)だが「創発の主経路(無名からの立ち上がり)を実験デザインで消す」
   懸念が残る。**要ユーザー決定**。
6. **観測B3未実装**: 4.68億イベントを現行 measure は解析不能。W2-F を欠くと「回せたが測れない」。
7. **checkpoint/resume の長時間耐性**: ~6日 wall のランが途中で落ちる前提の resume 決定論(W2-G)が要る。

### 7.1 エンジン目標未達の場合の縮退(同時滞在を段階縮小する優先順)
c が 0.0002 に届かない場合の**縮退レバー(優先順)**。**プールは100万のまま**(ドーマントは安いので削らない)、
**present_cap(同時数)を落とす**のが第一手:

| 優先 | レバー | 効果 | 失うもの |
|---|---|---|---|
| 1 | **present_cap 25万→10万**(1/2.5) | engine/LLM ともに 2.5x 軽く。10万なら lean で ~7.3h/シミュ日 | ピーク密度の現実感(局所混雑は薄まる) |
| 2 | **前景比率を下げる**(1万→5千) | LLM のみ削減(engine不変)。k\*母集団は縮む | k\* 検出力(母集団半減) |
| 3 | **シミュ日 10→5** | wall 半減 | 長期創発(組織形成・語彙普及の後半) |
| 4 | present_cap 10万→5万→2.5万 | 更に線形に軽く | 「現実の渋谷」からの乖離(街区スケールへ後退) |
| 5 | 背景の記録を更に間引く/観測を粗く | engine 追加削減 | 観測の解像度 |

**着地の目安**(scale-feasibility §6 と整合): **背景SoA達成なら 25万×10日が射程**、部分達成なら **10万×10日**、
SoA未達なら **1万×10日(lean で ~22シミュ日/24h の既知安全圏)**。**「同時数を段階縮小」は present_cap 一つで
決定論的に効く**(pool と presence が純関数なので、cap を変えても他は不変=検証が容易)。

## §8 まとめ(素材としての示唆)

- **25万同時×10日の可否は、背景tier SoA化で非LLM単価を 0.0002s/agent-step 級へ落とせるか一点**(§1.4・W2-A)。
  達成で H100×7 ~6日wall が射程、未達で 25日以上=不成立。**投資は 9割エンジン**。
- **ユーザーの N比例発火(0.15密度)は LLM を再び co-binding に戻す**: フル密度天井は A100×7=24h超。
  ただし **cap を N_thinking(前景+中景)に掛け背景を撃たなければ** LLM は 2h 前後に収まる(§2.3)。
- **記憶とプールの分離**(present=コスト源 / pool=記憶源)で 100万プールの RAM は背景SoA設計で ~2.3GB に収まる(§4.2-C)。
- **観測B3(ストリーミング解析)が未実装の最大の隠れリスク**——回せても測れない事態を W2-F で潰す。
- **W2 は A(背景SoA)を起点に E→D / G→C / B / F の順**。**ハッカソン前にローカルで c を実測**して可否を確定し、
  未達なら present_cap を段階縮小(§7.1)——これが「人数>時間」方針下での安全な着地戦略。
- 実装着手は §2.2 の動的昇格方式・§7-5 の k\*交絡・cap対象(N_thinking)を**ユーザーと詰めてから**(`pre-coding-alignment`)。
