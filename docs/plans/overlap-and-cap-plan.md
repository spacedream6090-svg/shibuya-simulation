# OVL: エンジン×LLM並列化+cap増量計画(2026-08-19深夜・ユーザー指示)

> 指示: 「②(並列化)のリサーチと計画」「cap1,200では0.7回/人/日=推論を増やしたい」「VRAMは使い果たすのか
> 実データを」「エンジン+推論で10分/step以内なら許容」。

## 1. VRAMの実データ(vLLMログ+nvidia-smi実測)

- **capはVRAMを消費しない**。VRAMは起動時に予約済み(gpu-memory-utilization 0.90):
  8Bサーバー=重み5.96GB+**KVキャッシュ15.06GB=計21.2GB/GPU を負荷ゼロでも確保**。
- KV容量実測: 8B=**109,632トークン/サーバー**(8,192トークン満杯リクエストで13.4並列・実プロンプト
  2-3kトークンなら**35-50並列**)・14B=73,696トークン(9.0並列@8,192)。
- 現行スループット(A8実測・chat): 8B×5=20呼/秒・14B×2=4.66呼/秒——**これはVRAM律速ではなく
  演算律速**。つまりcap増の制約は「艦隊スループット×step内のLLM壁時計予算」だけ。

|---|---|---|---|
| 60-75秒(現行cap1,500相当) | ~1,500 | 0.86 | 現行線 |
| 4分 | ~5,900 | 3.4 | |
| **6分** | **~8,900** | **5.1** | 推奨帯の下限 |
| 8分 | ~11,900 | 6.8 | |
| 10分(全部LLMに使う場合) | ~14,800 | 8.5 | OVL完成時の理論上限 |

上乗せ余地: ①プロンプトのプレフィックス整列(lane4 #3-11・enable-prefix-cachingは既にON=字面順を
「不変部→準不変部→可変部」に揃えるだけでKV再利用率が跳ねる) ②client並列度(workers 16→48-64)の
スループット検証(30分プローブ)——合わせて実効×1.5-2倍の見込み=同じ壁時計で7.5-10回/人/日圏。

## 3. 壁時計の正直な算術(10分/stepの意味)

- 全step一律10分だと T10=240h=実時間10日=**8/30提出に間に合わない**。
- ただし夜間(00-06時・36step)は軽い(実測1-2分)。**「昼はLLM上限10分・夜は成り行き」**の形なら:
  平均≈(36×1.5+108×10)/144≈**7.9分/step → T10≈190h≈8日** — 8/20夜開始で8/28夜完走・分析2日。
  成立はするが余白ゼロ。**平均6分設計(昼8分上限)なら T10≈144h**=GO線内+分析3日=推奨。
- capはfreeze後に変えられない(ラン0条項)ので、**最終capはリハーサル実測(B完走+エンジン修正後)で
  T10式に代入して決める**。縮退表(cap段階)をfreeze前に宣言しておく。

## 4. OVL: エンジン×LLM並列化の設計(リサーチ結論)

**成立根拠2つ(調査済み)**:
1. **GIL問題なし**: LLM待ちはHTTP I/O=GIL解放。バッチを非同期発行→メインスレッドで独立フェーズを
   計算→join→行動適用、が素直に書ける(プロセス分割不要)。
2. **乱数の順序安全**: sim.hub.streamはキー導出(purpose, ids, step)のハッシュ独立生成=フェーズの
   実行順を入れ替えても**draw列が1ビットも変わらない**(設計段階からのR1資産)。順序リスクは
   データ依存だけに集約される。

**構造**: step内を「LLM依存部」と「独立部」に二分し、
`発行(async) → [独立フェーズ実行] → join → 行動適用 → 依存フェーズ` に再配列。
T_step = max(T_engine独立部, T_LLM) + T_依存部 へ。

**作業列**:
- **OVL-0 依存監査(半日)**: 全フェーズについて「当stepのLLM結果(行動・hear・関係更新)を読むか」を
  表にする。候補独立部=物理・経済/org日次・観測フラッシュ(前step確定分)・GTサイドカー・l2集計・
  checkpoint準備。候補依存部=hear配布・SNC・C2(発話後の状態を読むか要確認)・drive更新。
- **OVL-1 実装(1日)**: conf `engine.overlap.enabled: false` 既定。ON時のみ再配列。
- **OVL-2 検証(半日)**: ★決定的テスト=**人工遅延mockバックエンド**(応答にsleepを注入)で
  ON/OFF 2ランの**L1完全バイト一致**を機械検証=「並列化は壁時計だけを変え、世界には1ビットも
  触れない」ことの証明。+実測リハで短縮率を記録。
- **効果試算**: エンジン昼帯修正後(2-4分)+LLM 6-8分 → 直列8-12分 → **max()=6-8分(30-40%短縮)**。
  エンジン未修正のままだと効果は5-10%(隠れるのが小さい方=LLMのため)→ **実施順序は
  ①エンジン熱点修正(C2列挙)→②OVL** が正しい投資順序。

**リスクと縮退**: 隠れた依存の見落とし=OVL-2のバイト一致が落ちる→当該フェーズを依存部へ戻すだけ
(機能は失わない・短縮率が下がるのみ)。本選に間に合わなければOFFのまま=現行直列(安全)。

## 4.5 OVL-0監査結果(2026-08-19深夜・完了)

**LLM発行点は3系統**: ①朝計画(scheduler.py:1101・同期ブロック)②日中熟慮(:3288・whileラウンド)
③夜内省(:1156/1177)。いずれも発行→即ブロック待ちが同一呼び出し内=待ち中エンジンは1行も走らない。

**主要判定**(詳細表は監査ログ・実装時に参照):
- 物理SFM(:6356)・move(:6357)は熟慮より**前**かつLLM行動は翌step実行=当stepのLLM結果を読まない。
  ただし位置はプロンプト入力なので熟慮とは重ねられない(PRE)——**朝計画バッチとなら重なる**。
- C2会話(:6416)はプロンプトの関係行を書く=熟慮の前必須(PRE)。
- 行動適用(:6455-)以降のフェーズ群(indoor/jitter/crowd/gossip/観測末尾/L2/L3)は依存部(B)。
- _reply_toは翌step消費(2段構造)=stepを跨ぐ先読み不可の確認。

**実装推薦(優先順)**:
1. **朝計画LLM×物理/移動ブロックの重ね**(最大の獲物): 発行だけasync→devices/SFM/move/取締り/索引/
   drive/c2を実行→_phase_drive前にjoin。この区間はday_planを読まない(例外=既定OFFのP4/DPH-B tiered)。
   朝は計画呼数最大帯×moveが昼帯エンジン最重量=max()化の利得最大。L1 day_planは記録位置スプライス
   (_reorder_decide_log :3202と同手法)。framework同期リトライ(planning.py:235)はjoin後1ラウンド。
2. **checkpoint/flushのIO背景化**(simulation.py:2412-2443): pickle化のみ同期・gzip圧縮+書き出しは
   背景スレッド(次stepと完全独立)。COMPLETEマーカーは背景完了時=A6規約維持。GB級checkpointの
   スパイクを丸ごと隠す。
3. **熟慮窓への小フェーズ移動**(traffic :6379・pov :6418・joint/household observe :6377-78):
   LLM結果もプロンプトも読まない・書くのはL1+自前状態のみ。実装が最も安全=OVL-2バイト一致検証の
   練習台。次段候補: envfb.update(:6571)・transit_staff(:6586)=入力が発行前確定の機械検証後。

## 4.6 OVL-2準備設計(2026-08-20早朝・コード調査済み・実装は保留=ユーザー指示)

**注入点の確定**: 全LLM呼び出しは `CachedLLM.generate/generate_many`(llm/cache.py)を通り、
未命中分のみ `backend.generate` がフェーズ2のThreadPool(workers>1)で並行発行される。
→ **MockBackend.generate(llm/mock.py)冒頭に固定sleepを入れれば、実LLMのHTTP待ちと同じ
並行性プロファイル(スレッドで待つ・GIL解放)を決定論のまま再現できる**。

**設計(実装待ち・半日未満)**:
1. conf `model.mock_latency_ms: 0`(既定0=現行バイト一致)。MockBackend構築点は
   simulation.py 2箇所(:986 基底 / :1563 mindサブモデル)。
2. sleepは乱数不使用の固定値・応答内容は1バイトも変えない。実行回数カウンタ
   `n_latency_sleeps` を持たせ、壁時計でなく**カウンタで遅延経路の通過を機械検証**
   (CIの時間アサート不安定を回避)。
3. テスト3本: A=latency 0 vs 50msの同seed 2ランで出力バイト一致(既存の2ラン一致ヘルパー再利用)
   / B=latencyランで n_latency_sleeps>0 / C=キー省略時に0(既定不変)。
4. OVL-1実装後に「overlap ON/OFF×latency固定」のL1バイト一致テストへ拡張=OVL-2本体。
