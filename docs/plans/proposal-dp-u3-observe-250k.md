## 0. 3行サマリ

1. **在場 25万が壊れたのは規模ではなく `presence` の層優先アルゴリズムである**。本提案書で名簿の実データを直接集計したところ、**cap を外せば平日の在場資格者は 336,962 人**(現実の平日日中同時滞在 36.4万 の **93%**)で、構成比も現実的だった。cap 25万 は `workday_shift`(25.4万)の途中で `break` するため、**来街者だけが構造的に全滅**する。→ 直し方は「人数を諦める」ではなく **層別クォータ**(§1-A)。
2. **資源の壁は LLM ではなく「測る側」である**。在場 25万 × 10 日でも、`day_plan` ON + step 予算 300 なら総呼数 **7.38 × 10⁶**・LLM 時間 **44〜112 h**(240h の枠内)。一方 **L1 は 42.7 GB・40.6 億イベント**で、`load_events` の全件 RAM 展開は確実に破綻する(§2-4)。**RSS 88〜110 GB** も単ノード RAM の実機確認が要る。
3. **推奨は「本線 10 日ランと 25万実証ランを分ける」**。本線 = 在場 **5万〜10万**(構成比は現実どおり・10 日間連続・全 ON セット)、別ラン = **在場 25万 × 数シミュ時間**(層別クォータ修正版 `smoke_wide`)で「25万が回る」を実証。両方セットで「25万規模で回した/10日間日常が続いた」を正直に主張できる。**最終確定は 8/15-16 の R_eff・RSS 実測**(§4)。

## 1. 25万転換の設計 — 「総人口 25万 × 在場制御」をどう作るか

### 1.1 第91 で何が壊れたのか(実測の再現と精密化)

第91 は「在場 25万は presence cap で来街者ゼロ化」を発見した。本提案書ではその**内訳を名簿の実データから直接集計**し、原因を数量で確定した。

`src/society/world/presence.py::present_for_day` は層優先で埋めて cap で `break` する:

```
resident(0) > duty(1) > workday_shift(2) > cadence(3) > stochastic(4)
```

**【実測】名簿(`data/persona_pool`・実測 1,000,000 件)の当日在場資格者**

| 層 | 名簿件数 | 平日の資格者 | 週末の資格者 | 資格の根拠(実測) |
|---|---:|---:|---:|---|
| resident(L1 住民+議員34) | 30,034 | **30,034** | **30,034** | 毎日 present |
| duty(L5 役割) | 986 | **986** | **986** | `duty_days="all"`(L5 サンプル 1,020 件で確認) |
| workday_shift(L2 域内従業者) | 253,702 | **253,702** | **0** | `work_days` が全件 `"mon-fri"`(L2 シャード 30,000 件サンプルで 100%) |
| cadence(L3 定期来街) | 36,690 | **27,357** | **6,946** | `school_day` 55.6% / `weekly_2` 15.0% / `weekly_3` 14.9% / `weekly_4` 14.5%(L3 30,000 件サンプル)→ 平日資格率 0.7456・週末 0.1893 |

| **合計** | 1,000,000 | **336,962** | **62,849** | |

> 出典: 本提案書のための新規サンプル集計(2026-08-06。`data/persona_pool/{L2,L3,L4,L5}/part-0000.jsonl` を読み取りのみ。シム本体・conf は無変更)。
> **限界**: L2/L3/L4 は先頭シャードのサンプルであり全数ではない。ただし週末合計 62,849 は第91 の「週末は概算 6 万人」と一致し、**独立に再現された**。

**cap=250,000 のときに起きること(層優先の帰結)**: 30,034 + 986 = 31,020 → 残 218,980 を `workday_shift`(253,702)が埋めて **cap 到達 → break** → `cadence` と `stochastic` は **1 人も入らない**。
つまり **25万人の街から来街者(5.2万人)が消え、従業者だけが 86% を占める街**になる。これが「日常が回らない」の正体である。

**【実測】現実との照合**(`docs/research/shibuya-concurrent-population.md`・国交省人流オープンデータ)

| 指標 | 現実(2019 基準・コア 4 メッシュ ≈4.2km²) | 名簿の資格者 | 比 |
|---|---:|---:|---:|
| 平日 日中ピーク同時滞在 | 371,829(14:00) | 336,962 | **0.91** |
| 平日 24h 平均同時滞在 | 235,279 | — | — |
| 平日 深夜最小(03:00) | 84,671 | — | — |
| 週末 ピーク同時滞在 | 227,361(14:00) | **62,849** | **0.28** |

★**新しい発見(本提案書)**: **名簿は平日にはよく合っているが、週末には現実の 28% しか居ない**。理由は明白で、週末は `workday_shift`(25.4万)が丸ごと失格になるのに、来街層(`cadence`+`stochastic` = 3.2万)がそれを補うようには較正されていない。現実の週末渋谷は「働く人が来ない代わりに遊びに来る人が来る」ので総数が 22.7万 に達する。名簿はこの入れ替わりを持っていない。
→ **10 日ラン 8/16〜8/26 には週末が 3 日(8/16 日・8/22 土・8/23 日)含まれる**。無修正だと **在場数が 33.7万 ⇄ 6.3万 の 5.4 倍で振れる**。これは「日常が回る」の観測にも資源計画にも効く。

### 1.2 設計案(3案)

| # | 案 | 名簿(総人口) | 在場の決め方 | 実装量 | メモリ(推定) | 現実整合 |
|---|---|---|---|---|---:|---|

| B | 名簿縮小 | 25万(`--fraction 0.25` の専用プール) | cap 不要(自然に平日 8.4万 / 週末 1.6万) | **極小**(CLI 1 本+`pool.dir` 差し替え・コード無変更) | 30〜38 GB | △ 常住が 7,500 人=現実の 1/4 |

#### 案 A の中身(推奨)

`present_for_day` の cap 充足を「優先順に埋めて break」から「**層別クォータ**」に変える。

```
quota[t] = round(present_cap × eligible[t] / Σ eligible)      # 既定 = 資格者比率を保存
present  = ∪_t  rank_t(eligible[t])[:quota[t]]                # 溢れた層のみ当日ランキングで切る
```

- **cap=250,000 のときの割当(上表の平日資格者比で計算・合計 249,999)**: resident 22,282 / duty 731 / workday_shift 188,228 / cadence 20,297 / stochastic **18,461**。→ 来街者(cadence+stochastic)が **3.88万人**入る(現行 = **0 人**)。
- **R1 との整合**: 追加する乱数は無い(既存の `presence_rank` stream をそのまま使う)。k 非依存・trait 非依存は不変。`present_cap` を触らない既定では**現行と完全一致**にできる(クォータ既定 = 現行の優先順=無効化フラグ `tier_quota.enabled: false`)。
- **週末問題への効き**: クォータは「資格者比率」なので、週末に `workday_shift` が 0 になれば残りの層で cap を埋めようとするが、**資格者総数 62,849 が上限**なので在場は 6.3万 に落ちる。**週末の総数を現実に近づけるには名簿側(L4 の `visit_rate` 週末増し)の較正が別途要る**。本選前にやるか否かは §5 の残論点 R-3。

> **正直な注記**: クォータ案は「構成比を保存する」だけで、**現実の週末人口を再現するものではない**。§1.1 で見つけた週末 0.28 のギャップは名簿の較正問題であり、presence のアルゴリズムでは直らない。

`data/jinryu/shibuya_concurrent_144step_curve.csv`(**実測** 144 step × 平日/休日の同時滞在数)が既にリポジトリにある。`presence.py` の docstring も「在場実測曲線は v1 では使わない(**将来拡張点**)」と明記している。

### 2.2 LLM 呼数の式と水準別予算

```
総呼数 = D × [ N × (plan + reflect + recall) + min(cap, N) × 144 ]
         ─────予算外(1人1日ごとに必ず出る)──   ─予算内(step 上限で縛られる)─
f(呼/人/シミュ日) = 総呼数 / (N × D)
```

★ **重要な構造**(`finals-llm-budget.md` §1 の実査): `lod.max_llm_per_step` が縛るのは `_phase_drive` の発火 2 箇所と返答保証 1 箇所の **計 3 箇所だけ**。**朝の計画と夜の内省は予算外の無条件呼び出し**である。したがって **N が大きいほど「予算外」が支配的**になる。

**読み方(ここが本提案書の核心)**

- **10 日ランの壁時間は 240 h**。悲観 R_eff(18.3)でも **在場 25万 × 構成 B(112 h)は入る**。「25万は LLM 予算で不可能」は**誤り**である。
- しかし **cap=300 での「予算内」= 43,200 呼/日 を 25万人で割ると 1人 1日 0.173 回**。つまり **25万の世界では、自発的な思考・会話はほぼ起きず、全員が朝 LLM で計画を立ててルールが 1 日を実行する**世界になる。これは `day_plan` の設計(決定と実行の分離)そのものだが、**「会話が生きている」水準ではない**。
- **会話の生きの良さ = `cap × 144 / N`(1人1日あたりの自発思考回数)**。25,000 人 × cap 300 = **1.73**。同じ密度を 25万で保つには **cap = 3,000** が要り、悲観 R_eff で **171 h**(240h の 71%)。**この 1 点の GO/NO-GO を決めるのが 8/15-16 の R_eff 実測**である。
- `lod.n_proportional.density: 0.15` は 25万で cap = 37,500/step = f 21.6 → **820 h で不成立**。**25万では n_proportional を OFF にするか density を 0.012 まで下げる**(= cap 3,000 相当)。

### 2.3 engine 時間・メモリ・出力

| 在場 N | engine 時間(c=5.22e-4) | peak RSS(推定) | L1 サイズ(線形下界) | イベント数 |
|---:|---:|---:|---:|---:|
| 25,000 | 5.2 h | 8.8〜11.0 GB | 4.3 GB | 4.1 億 |
| 50,000 | 10.4 h | 17.7〜22.1 GB | 8.5 GB | 8.1 億 |
| 100,000 | 20.9 h | 35.4〜44.1 GB | 17.1 GB | 16.2 億 |
| **250,000** | **52.2 h** | **88.4〜110.3 GB** | **42.7 GB** | **40.6 億** |

**正直な限界 3 つ**

1. **メモリ傾きは 24 step のランから取った**。`_rss_probe_10k` は 1/6 シミュ日である。10 日ランでは関係台帳・エピソード・beliefs が**累積**するので、**0.36 MB/体 は下界**。`pool.relations_cap`(20)/`episodes_cap`(30)は退避時にしか効かない。→ **8/15-16 に「1万体 × 1 シミュ日以上」の RSS を必ず測る**(§4)。
2. **イベント数は N に対し超線形**(同席由来の `hear`/`transmission` が二乗的)。`bench_scaling` 実測で 135 /体/日(N=10)→ 618 /体/日(N=1,000)→ 1,622 /体/日(N=1万)。線形外挿の 40.6 億は**下界**である。
3. **`observer.measure.load_events` は全件 RAM 展開**(`million-scale.md` §3(c))。10⁸ 件で破綻する。**在場 2.5万 × 10 日(4.1 億件)で既に 4 倍超過**。→ **回せても測れない**。緩和策は §3 の観測設定と `detect_regression.py --quick`(第91・完結 part のみ読む)。

### 2.4 律速の順序(本提案書の結論)

```
① 解析パイプライン(load_events 全件展開)  ← 在場 2.5万 で既に破綻線
② ホスト RAM(88〜110 GB @25万・実機未確認)
③ LLM 時間(会話枠を開けたときだけ効く)
④ engine 時間(52 h @25万・余裕)
```

`finals-llm-budget.md` §6 の「1万〜3万で最初に壊れるのは回す側ではなく**測る側**」が、25万でもそのまま成り立つ。

## 5. 推奨と残論点

### 5.1 推奨(★)

1. ★**案 A(層別クォータ)を 8/12 までに実装**する。50 行程度・乱数追加ゼロ・既定 OFF で現行一致。これが無いと「25万の街に来街者が 1 人もいない」ままになる。
2. ★**本線 10 日ラン = 在場 5万〜10万**(8/16 朝に §4.3 の表で確定)。**25万は別ラン(数シミュ時間)で実証**する。理由は LLM ではなく **① 解析パイプライン ② ホスト RAM** の 2 つ。
3. ★**`day_plan` ON + `lod.max_llm_per_step = 0.012 × N`**(= 自発思考 1.73 回/人/日 を N によらず一定に保つ)。**本線は全員内省(構成 B)**で k\* を測り、**25万実証ランだけ高解像度層 3% に絞る**(予算外呼数 2.78 → 1.05 /人/日)。内省を絞ると k の作用点が 3% になるので、両方を 1 本のランで兼ねない(R-8)。
4. ★**8/15-16 で R_eff と 144-step RSS を必ず測る**。この 2 つが未測定のまま 10 日ランの規模を決めてはいけない。
5. ★新機能の投入水準は §3.2 の表(day_plan/contingency/mind/rejection_notify=ON、v_of_s=OFF、regression は本線のみ ON、zones はスクランブル 1 ゾーンのみ)。

1. **R_eff(呼/s)は 1 つも実測がない**。§2.2 の時間はすべて推定であり、実測が推定の半分なら在場 25万 × 構成 C は 240h を超えて不成立になる。
2. **メモリ傾きは 24 step のランから**。10 日ランの累積を含んでいない(下界)。
3. **名簿の集計は先頭シャードのサンプル**(L2/L3 各 30,000 件・L4 50,000 件)。全数ではない。ただし週末合計が第91 の独立見積と一致した。
4. **`stochastic` の日次期待値 24,883 は解析的合成**(サンプル `visit_rate` 平均 × 名簿件数 + revisit の周期期待値)であり、`present_for_day` を実際に走らせた値ではない。**8/12 の縦煙で 1 回実走して照合すべき**。
5. ~~**層別クォータは未実装**~~ → **2026-08-07 に実装した**(`pool.tier_quota.enabled`・既定 false=現行の層優先と完全一致)。§1.2 の割当数は「実装したらこうなる」という計算だったが、実装は端数処理に**最大剰余法**を使うため合計が厳密に cap になる(提案書の素の round は合計 249,999)。実測の割当 = resident **22,283** / duty **732** / workday_shift **188,227** / cadence **20,297** / stochastic **18,461**(合計 250,000。§1.2 の表とは各層 ±1 人)。来街者は **38,758 人**。なお**この数字はまだ名簿の実走ではなく §1.1 のサンプル集計値を入力にした計算**であり、限界 3・4 はそのまま残る。
6. **イベント数・L1 サイズの外挿は線形**で、実測は超線形(135 → 618 → 1,622 /体/日)。42.7 GB は下界。
