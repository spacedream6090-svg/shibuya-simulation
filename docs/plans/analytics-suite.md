## 結論
8項目とも**既存資産への接木で済み、純粋な新規は2本だけ**(汎用グリッド器・LLM要約器)。
最大の省力ポイントは「**①ヒートマップ→③混雑LOS→②OD行列が同一の空間グリッド集計を共有できる**」こと。
全てL1(l1_events.parquet)の読み出し専用・シミュ本体/schema/measure.py は不変=R1・ゴールデン非抵触。

## 実装ウェーブ(Opus実行・ファイル所有は素集合・並列可)

### W1 — 土台2本(並列・互いに独立)
1. **scripts/analyze_flows_grid.py(新規)= ①人流ヒートマップ+③混雑ランキング**
   - 25mメッシュ×1時間ビンに (x,y) をビニング(渋谷1.0×0.7km≈40×28セル)。move_segment=通過数、
     arrive/stay/在館(建物centroid)=同時在圏数、unique_agents。→ panel/heatmap_grid.parquet
   - ③はその増分: 在圏数÷セル面積=人/m² → **FruinのLOS A-F 格付け**(閾値は原典で一次確認してから
     定数化=リサーチの🔶注意を継承)→ セル×時間帯の混雑ランキング表。crowd_surge イベントと突合して検証。
     建物内は延床面積が無いので LOS を出さず相対混雑に留める(捏造回避)。
   - 可視化: 単体HTML(ビューアと同じ自己完結方式・時間スライダつき密度面)+ ビューアの密度オーバーレイは第2段。
2. **panel_stats 拡張 = ⑦統計的有意性**
   - 追加: paired Cohen's d・Cliff's δ・Wilcoxon/置換検定 p・**BH-FDR補正 q**(指標13本併記のため必須)・
     n<30 は t分布CI。純Python(既存流儀)。
   - レポート冒頭に免責を明記: 「**シミュの p はラン数で任意に小さくできる。効果量とCI幅を主・p を従**」
     (JASSS の ABM出力解析標準)。

### W2 — 比較系2本(W1の⑦を流用)
3. **scripts/analyze_od.py(新規)= ②OD行列**
   - トリップ=route_start→arrive(明示目的地)+滞在遷移。ゾーン=W1のグリッドを束ねた地区+
     **exit_area/enter_area の gateway を域外ゾーン**として含める(渋谷の流出入が1枚に載る)。
   - 目的帰属=到着後の行動で近似(spend.cat・建物カテゴリ・day_plan)→ work/food/shop/leisure/home。
   - 出力 panel/od_matrix.parquet(origin, dest, hour_bin, purpose, trips)+ flow map(単体HTML)。
4. **scripts/compare_runs.py(新規)= ⑥介入前後の比較**
   - between-run: 既存の同seedペア比較(CRN)を⑦の置換検定で p 値化。
   - within-run DiD: scenario_shock.at を境に (after−before)_処置 − (after−before)_対照。
   - **CRN健全性チェック**(リサーチの要点): 介入ランと対照ランの L1 を介入 step まで突合し、
     実行パス破れ(=ペア比較の前提崩壊)を検出して警告。本シミュは rng_stream 分離設計なので優位。

### W3 — 拡張2本(既存スクリプトへの増設)
5. **⑤社会ネットワークの変化**: analyze_communities の窓グラフ構築を再利用し、
   window×(密度・平均次数・クラスタ係数・次数gini・最大連結成分比・平均紐帯重み)の時系列
   panel/network_ts.parquet+**tie decay(紐帯寿命分布)**+alluvial用の窓遷移データ(コミュニティの
   合流・分裂を帯で見る)。
6. **④エージェント行動統計**: build_panel に活動時間バジェット(カテゴリ別 分/日)、
   **tempogram(24h×活動カテゴリの在圏割合)**、calibrate_report に生活時間調査形式の時間配分表+
   分布一致(KS/EMD 自作)を増設。

### W4 — ⑧LLM自然言語要約(最後=上流の確定表が固まってから)
7. **scripts/summarize_run.py(新規)**: 各レポートの確定KPI表(JSON)を入力に、
   「**表の数値のみ使用・表に無い数値/比較/因果を作らない**」制約プロンプトで日本語要約を生成。
   - **数値照合ガード**: 生成文から数値を正規表現抽出→原表と exact-match、不一致は破棄・再生成
     (忠実性スコア=数値一致率を併記)。
   - 実装は llm/router を読み出し専用で流用。既定 mock(決定論)・実行時に ollama/API を選択。
     judge.py と同じ **R4防壁**(読み手向け projection・シミュ本体へ逆流させない)。
   - 既存の決定論テンプレ .md 群は**一次真実として据え置き**、LLM要約はその横に置く(置換しない)。

## 決定事項(Fable判断・実装時に従う)
- グリッド25m・時間ビン1h を既定(config でなくスクリプト引数)。
- 可視化は「単体HTML(自己完結・three.js/ビューアと同流儀)」を正とし、ビューア統合は後続。
- 数値の閾値(Fruin 面積基準)は**一次資料で確定してから**コードに定数化(リサーチが🔶指定)。
- 誠実性規約の継承: 0件は「データ不足」明記・warmup 除外は解析側選択・決定論(ソート・seed固定)。
