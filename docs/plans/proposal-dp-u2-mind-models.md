## 0. 3行サマリ

1. **選定基準は「性能」ではなく「D層(分散と裾)のプロファイルが互いに違うこと」**。第90 の実測で `qwen3:8b` は A/B/C 層すべてで `qwen3:4b` に勝ちながら、**D層で 6 サンプル全部が同一選択に潰れた**(`distinct_choices` 1・`choice_entropy` 0.000)。第92 は本体シムでも **移動の分散比 0.662 < 1**(分散が確実に痩せた)を初検出している。**一番賢い 1 本に心を全部任せる構成は、この研究の主張(個体差・裾・世界改変者の創発)を自分で潰す。**
2. **A5000 24GB × 7 という箱が、ショートリストの本数をほぼ決める**。1 GPU = 1 vLLM = 1 モデルが安全側で、**思考層に使える枠は最大 5〜6**(残り 1〜2 枚が高解像度層と `default`)。したがって「3B〜14B × 5〜6 本 + プラセボ 1 本」という指示は**ハード制約とちょうど一致**している。
3. **推奨は §2 案 B(3 モデル × 2 レプリカ + 高解像度層 1)を本線、案 A(6 モデル × 1)を予備**。MindRouter は**子の障害時にフォールバックしない**(コードで確認)ので、1 モデル 1 GPU 構成では **GPU 1 枚死 = その心を持つ全エージェントが停止**する。10 日連続ランでこれは受け入れがたい。**多様性を 6→3 に落としても冗長性を取る**のが 10 日ランの正解。

## 2. 混成 fleet 構成案

### 2.1 「性能でなく多様性」の実測根拠

| 根拠 | 実測 | 出典 |
|---|---|---|
| モデル間で D層が逆転する | 8b 0.244 < 4b 0.495(A/B/C は 8b が上) | 第90 |
| 本体シムでも分散が痩せている | **移動の分散比 0.662 < 1**(sim CV / 現実 CV 下界) | 第92 B3 |
| 文献側 | alignment–simulation tradeoff(instruction tuning は高エントロピー問題で性能を下げる=entropy reduction) | SimBench arXiv:2510.17516 / `docs/research/llm-human-fidelity.md` |
| 文献側 | LLM の応答変動性は人間の 1/20〜1/300 | `llm-human-fidelity.md`(**絶対比較は本リポジトリの材料では出せない**=D層参照が相対値のため) |

→ **混成は「性能を上げる」ためではなく「分散を供給する」ための実装**である。この主張は報告書に明記し、`summary.mind.confound_note`(第88 で自動同梱)と整合させる。

### 2.2 割当の仕組みと制約(第88 の設計と整合させる)

- 割当は **`(master_seed, agent_id)` の純関数**。専用 stream `mind_model` の一様値を **name 昇順**の重み累積分割にかける(conf の並び順に依らない)。
- **checkpoint に割当表は不要**(resume でも pool 再入場でも同じモデルに戻る)。
- **★重み・本数を 1 文字でも変えると、全エージェントの心が総入れ替えになる**(累積分割の境界が動くため)。→ **fleet 構成は 8/12-14 フリーズの対象に含める。ラン中の変更は不可。**
- **★MindRouter は子の障害でフォールバックしない**(`mind_router.py` の `_child`: 未知 `model_id` は default 行きだが、**子が例外を出す経路には退路がない**)。→ **1 モデル = 1 GPU だと、GPU 1 枚死でその心を持つ全エージェントが止まる。**
- `high` 層の選抜は **`select: uniform` を厳守**(traits 選抜は「誰が世界を変えるか」という問い自体を自壊させる=サーベイ S-08。ON にすると manifest に警告が残る)。

### 2.3 構成案(3案)

> 共通: 7 GPU。1 枚は **`default`**(機械的判断・`agent_id` を持たない呼び・D7 対照系列)と**高解像度層**が同居。

#### 案 A — 多様性最大(6 モデル × 1 GPU)

| GPU | 役割 | モデル | weight |
|---|---|---|---:|
| 0 | 思考層 | `qwen3-8b`(BF16) | 3 |
| 1 | 思考層 | `qwen3-14b`(AWQ-INT4) | 2 |
| 2 | 思考層 | `qwen3-4b`(BF16) | **2** |
| 3 | 思考層 | 日本語特化 8B(ELYZA or Swallow) | 2 |
| 4 | 思考層 | Nemotron Nano 9B JP or llm-jp | 1 |
| 5 | 思考層 | Gemma 3 12B(INT4)or Phi-4(INT4・非JA対照) | 1 |
| 6 | 高解像度層(3%)+ `default` | `qwen3-14b`(AWQ) | — |

- 長所: **心の種類が 6**。D層プロファイルの違いを最大限に取り込める。
- 短所: **冗長性ゼロ**。GPU 1 枚死 = その weight 分(9〜27%)のエージェントが停止。10 日連続ランでは危険。
- prefix cache: モデルごとに担当エージェント集合が固定される=**sticky routing が自動的に成立**(第88 の割当がそのまま sticky)。

#### 案 B ★推奨 — 冗長性優先(3 モデル × 2 レプリカ + 高解像度層 1)

| GPU | 役割 | モデル | weight |
|---|---|---|---:|
| 0, 1 | 思考層(2 レプリカ・プロキシ 1 口) | `qwen3-8b`(BF16) | **4** |
| 2, 3 | 思考層(2 レプリカ・プロキシ 1 口) | 日本語特化 8B(ELYZA or Swallow・BF16) | **4** |
| 4, 5 | 思考層(2 レプリカ・プロキシ 1 口) | `qwen3-4b`(BF16)= **裾供給枠** | **2** |
| 6 | 高解像度層(3%)+ `default` | `qwen3-14b`(AWQ-INT4) | — |

- **weight 4:4:2 の根拠**: §2.5 の二段規則。**A層足切りを通った 2 本で 80%**(D層分散比が測れるまでは暫定 50:50)、**足切りを落ちた `qwen3-4b` は裾供給枠 20%**(規則③の上限)。8/15 の正規版 D層測定でこの 4:4 が動く。
- **`qwen3-4b` を 20% 入れることの帰結(隠さない)**: 4b は A層 `schema_ok` 0.250 なので、**この 20% のエージェントは day_plan の検証を通らず「決定的修復 → フォールバック」へ落ちる頻度が高い**。第86 は再試行ゼロ設計なので**呼数は増えない**が、その個体は実質ルールベースの計画で 1 日を過ごす。第86 が持つ**修復/後退のモデル別集計**でこの比率を観測できる。**「賢い心と粗い心が同じ街に混ざっている」ことを観測量として引き受ける**のが本案の立場である。
- 長所: **各モデルが 2 GPU = 1 枚死んでも心は生きる**。運用が 10 日ランに耐える。
- 短所: 心の種類が 3(案 A の半分)。

> ★**実装上の重要な制約(本提案書でコードを読んで判明)**: `Simulation._build_router_child`(`simulation.py:1230`)が受ける子 spec の `backend` は **`mock | ollama | vllm | openai_compat | anthropic` の 5 種だけで、`fleet`(複数サーバ)が無い**。つまり **`model.mind.pool` の 1 モデルは 1 つの `base_url` しか持てない**。→ 2 レプリカを 1 モデルとして束ねるには次のどちらか。
>
> | 方法 | GPU | フェイルオーバ | prefix cache | src 変更 |
> |---|---|:--:|:--:|:--:|
> | **(i) ★推奨: リバースプロキシ(vLLM Router のプレフィクス認識ルーティング)を 2 レプリカの前に置き、`base_url` をプロキシに向ける** | 2 枚 = 独立レプリカ | **○** | ○(プロキシが sticky なら) | **不要** |
> | (ii) `--tensor-parallel-size 2` で 1 エンドポイント | 2 枚 = 1 TP グループ | **✕**(片方死ぬと TP ごと落ちる) | ◎ | 不要 |
> | (iii) `_build_router_child` に `fleet` を足す | 2 枚 | ○ | ○ | **要**(フリーズ期間に src 変更=避けたい) |
>
> **(i) を推奨**する。src を 1 バイトも触らずに冗長性が取れる([vLLM Router 公式](https://blog.vllm.ai/2025/12/13/vllm-router-release.html)は `llm-model-selection.md` §5 に既収)。**ただしプロキシの疎通は 8/15 に実測が要る**(未検証)。

#### 案 C — 小型同居で本数を稼ぐ(**未検証・非推奨**)

4B 級を 1 GPU に 2 本(`--gpu-memory-utilization 0.45` ずつ)同居させれば 8 モデルまで届く。
**★本リポジトリに vLLM 同居の実測は無い**。第90 実測の「同居で 3.3 倍遅い」は **ollama の `keep_alive` 由来**であって vLLM のプロセス分離とは別現象だが、**KV キャッシュが半減してスループットが落ちるのは確実**。→ **8/15-16 で実測しない限り採らない。**

### 2.4 conf の実体(案 B・8/12-14 フリーズの凍結対象)

```yaml
model:
  backend: vllm
  name: qwen3-society               # ★default(agent_id を持たない呼び・対照系列)のキャッシュキー
  servers: ["http://localhost:8006"]   # default = 高解像度層と同じ GPU6 に同居
  mind:
    enabled: true
    # purposes 省略 = 既定(deliberate / plan / reflect / recall)
    pool:
      - {backend: vllm, name: "qwen3-8b",     base_url: "http://localhost:9000", weight: 4}
      - {backend: vllm, name: "elyza-jp-8b",  base_url: "http://localhost:9001", weight: 4}
      - {backend: vllm, name: "qwen3-4b",     base_url: "http://localhost:9002", weight: 2}
    tiers:
      high:
        frac: 0.03                  # 3%。DP-U3 §2.2 の呼数節約レバーでもある
        name: "qwen3-14b"           # spec 省略時は pool 先頭と同じ backend 種別で名前だけ差し替え
        spec: {backend: vllm, name: "qwen3-14b", base_url: "http://localhost:8006"}
        reflect: true               # 夜の内省をこの層に集約(第87 reflect_frac から権威を移す)
        cap_mult: 1.5               # engaged の turn_cap / replan_cap を 1.5 倍
        select: uniform             # ★厳守(traits 選抜は問いの自壊)
```

- ポート `9000-9002` = **リバースプロキシ**(§2.3 (i))。その後ろに GPU0/1・GPU2/3・GPU4/5 の vLLM 実体が 2 本ずつ。
- `8006` = GPU6 の vLLM(`qwen3-14b` AWQ)。**default と高解像度層が同じ実体を指す**(キャッシュファイルは name 単位で別なので混ざらない)。
- **キャッシュファイルはモデルごとに `llm_cache.<name>.jsonl` に分離される**(第88 実装で確認)。混成でも再現性は各モデル内で独立に担保。
- **manifest に残るもの**: `run_manifest.mind`(pool 構成・三層の頭数・選抜方式・`by_model`)+ `summary.mind.confound_note`(**因果効果ではない旨**を自動同梱)+ `agents.json` / L1 `mind_assign` に agent→model_id。

### 2.5 重み配分の決め方(★二段規則)

「性能で重みを付ける」と分散が痩せる。「分散だけで重みを付ける」とスキーマを壊すモデルが厚くなる。**両方を避ける唯一の順序**:

```
① 足切り(合否): A層 schema_ok ≥ 0.90 かつ プラセボを全層で上回る
                 → 落ちたモデルは思考層の主力にしない(**裾供給枠**に限定)
② 重み(連続) : ①を通った候補を D層 分散比に比例させる(∝ variance_ratio)
③ 上限        : 1 モデルの weight は全体の 50% を超えない(単一モデル支配の禁止)
④ 裾供給枠    : ①を落ちたモデルの合計は全体の 20% を超えない
```

**第90 実測を①に当てると**: `qwen3-8b` は 5 層すべてでプラセボを上回り(A 0.828>0.705 / B 0.750>0.333 / C 0.753>0.445 / D 0.244>0.000 / E 0.644>0.624)`schema_ok` 1.000 = **合格**。`qwen3-4b` は A 0.531 < プラセボ 0.705・`schema_ok` 0.250 = **不合格 → 裾供給枠**。

- ①の根拠 = 第90 の「プラセボ健全性 FAIL は指標の欠陥とは限らず、**そのモデルが本当にテンプレート以下**でありうる」(`schema_ok` が低ければ後者)。
- ②の根拠 = 第90 の D層逆転 + 第92 の分散比 0.662。
- ③の根拠 = 正典 §5「異種モデルの混成は性能ではなく多様性の実装として正当化される」。
- **③を入れないと、正規版 D層で 1 本が突出したときに実質的な単一モデル艦隊に戻る**。

### 3.4 D層の限界(消せないもの)

1. **分散比は `relative_to_best_model`**(その回の最良モデル = 1.0)。**人間参照が無いので絶対比は出せない**。文献の「人間の 1/20〜1/300」との突き合わせは**できないと書く**。
2. 絶対比を出すには「渋谷で 1 時間空いた・8択」を**人間数十人**に配る小規模調査が要る(参照ファイルの `human_choice_entropy` に未取得として登録済み)。**本選前には間に合わない。**
3. C層は NUCC の平均発話長・あいづち率の公表値が無く、**相対比較のみ**(DP-U1 でユーザーが「無償で進める」を決定済み)。

## 4. 推奨と残論点

### 4.1 推奨(★)

1. ★**案 B(3 モデル × 2 レプリカ + 高解像度層 1)を本線**にする。心の種類 3・**weight 4:4:2**(8B 級 2 本で 80% + 4b を裾供給枠 20%)・`high.frac` 0.03 / `select: uniform` / `reflect: true`。
   理由 = MindRouter に障害フォールバックが無く、10 日連続ランで GPU 1 枚死は現実的リスクだから。**多様性 6→3 の損失より、心が止まるリスクの方が重い。**
2. ★**ショートリスト(測る対象)は 6 本 + プラセボ**: `qwen3-8b` / `qwen3-14b` / `qwen3-4b` / 日本語特化 8B(**ELYZA と Swallow のどちらか = M-2**)/ Nemotron Nano 9B JP / Gemma 3 12B、+ `placebo:template`。
   **測ってから 3 本に絞る**(§3.2 の 8/15 午後)。案 A に切り替える退路も conf 1 箇所で残る。
3. ★**weight は §2.5 の二段規則で機械的に決める**(A層足切り → D層分散比 → 単一 50% 上限)。**人が「賢そうだから」で決めない。**
4. ★**Non-Commercial ライセンス(Sarashina / PLaMo)は候補外**。公開ミラーと論文公開があるため。
5. ★**fleet 構成をフリーズ対象に含める**(8/12-14)。weight を 1 文字変えると全エージェントの心が入れ替わる。

### 4.3 本提案書の限界(正直な記載)

1. **候補 9 本のうち実測があるのは 2 本 + プラセボだけ**(第90・縮小版 scale=0.2)。残り 7 本は**すべて未測定**であり、表の (a) 列は空である。§3 の正規版測定が前提。
